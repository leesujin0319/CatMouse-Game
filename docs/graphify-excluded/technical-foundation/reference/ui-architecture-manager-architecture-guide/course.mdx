## [기술 기획안] UI 아키텍처 및 관리 시스템 (UI Architecture & Manager)

> 최종 수정일: 2026-05-04
> 문서 상태: `Reviewable`

---

## 1. 개요 및 설계 목적

이 문서는 UI를 `Canvas` 아래 프리팹을 켜고 끄는 수준으로 다루지 않고, **게임 상태, 입력 컨텍스트, 화면 스택, 데이터 바인딩, 비동기 로딩을 통합하는 UI 아키텍처**로 관리하기 위한 기준을 정의합니다.

UI는 게임플레이 시스템보다 가벼워 보이지만 실제로는 입력, 저장 데이터, 기획 데이터, 사운드, 카메라, 네트워크 상태, 튜토리얼, 접근성 옵션과 넓게 연결됩니다. 처음에는 `OpenInventory()`, `ClosePopup()` 같은 메서드 몇 개로 충분해 보여도, 뒤로가기, 중첩 팝업, 비동기 로딩, 화면 전환 애니메이션, 패드 포커스, UI 중 게임 입력 차단이 붙으면 구조가 빠르게 흔들립니다.

이 문서의 목적은 UI 패턴 이름을 고르는 것이 아닙니다. **화면의 소유권, 표시 수명주기, 입력 차단, 데이터 갱신, 이벤트 구독 해제, 뒤로가기 규칙**을 명확히 하는 데 있습니다.

**이 문서가 바로 답하는 질문**

- UI 화면은 누가 생성하고 누가 닫는가
- 일반 화면, 팝업, 토스트, HUD, 시스템 모달은 어떻게 구분하는가
- UI가 열렸을 때 게임플레이 입력은 어디서 막는가
- 버튼 콜백, View, Presenter, Model의 책임은 어떻게 나누는가
- 비동기 UI 로딩 중 중복 클릭과 닫기 요청은 어떻게 처리하는가
- `SceneDI`, `Input System`, `EventBus`, `SaveSystem`, `Camera`와 어디서 연결해야 하는가

---

## 2. 문제 정의

UI 구조가 없을 때 가장 먼저 생기는 문제는 화면 중첩입니다. 인벤토리 위에 옵션이 열리고, 옵션 위에 확인 팝업이 열렸는데 뒤로가기를 누르면 어떤 화면이 닫혀야 하는지 기준이 없어집니다. 여기에 게임패드 포커스나 모바일 back 버튼이 붙으면 버튼마다 서로 다른 닫기 로직을 갖게 됩니다.

두 번째 문제는 입력 충돌입니다. UI가 열려 있어도 플레이어 이동과 공격 입력이 살아 있으면 메뉴 조작 중 캐릭터가 움직입니다. 반대로 UI가 닫혔는데 입력 차단이 풀리지 않으면 게임이 멈춘 것처럼 보입니다.

세 번째 문제는 데이터와 이벤트 구독입니다. UI가 열릴 때마다 EventBus를 구독하고 닫을 때 해제하지 않으면, 닫힌 화면이 이벤트를 계속 받아 중복 갱신이나 메모리 누수가 생깁니다. 저장 데이터나 인벤토리 데이터가 바뀌었을 때 어떤 화면이 새로 그려져야 하는지도 불명확해집니다.

따라서 UI 설계의 핵심 문제는 "화면을 어떻게 예쁘게 배치할 것인가"보다, **화면 수명주기와 입력, 데이터, 이벤트 경계를 일관된 계약으로 관리할 수 있는가**입니다.

---

## 3. 설계 목표

- UI 화면을 종류별 계층과 스택 규칙으로 분리한다.
- 화면 생성, 표시, 갱신, 닫기, 해제를 명시적인 수명주기로 관리한다.
- UI가 게임플레이 입력을 직접 끄지 않고 `Input System`에 컨텍스트 또는 차단을 요청한다.
- View는 표시와 사용자 입력 전달에 집중하고, Presenter가 화면 로직을 소유한다.
- EventBus 구독과 해제 위치를 화면 수명주기에 맞춘다.
- 비동기 UI 로딩 중 중복 열기, 닫기, 실패 처리를 명시한다.
- 기획 데이터로 바꿀 수 있는 UI 항목과 코드 변경이 필요한 구조 변경을 구분한다.

---

## 4. 범위와 비범위

### In Scope

- HUD, Screen, Popup, Modal, Toast 계층 분리
- UI 스택과 뒤로가기 처리 규칙
- View / Presenter / Model 또는 MVVM 계열 책임 분리
- UI 입력 컨텍스트와 게임플레이 입력 차단
- 비동기 UI 로딩과 중복 요청 방어
- EventBus 구독, 데이터 갱신, 해제 규약
- `SceneDI` 기준의 UI 루트 조립

### Out of Scope

- 개별 화면의 시각 디자인 상세
- 모든 UI 애니메이션 제작 규칙
- 폰트, 컬러, 접근성 옵션 전체 설계
- 웹뷰, 결제 SDK, 플랫폼 별 UI 정책 전체
- 에디터 UI 빌더 툴 제작

이 문서는 UI의 **런타임 구조와 계약**을 다룹니다. 개별 UI 스타일, 디자인 시스템, 접근성 옵션, 플랫폼 인증 정책은 별도 문서에서 확장하는 편이 좋습니다.

---

## 5. 핵심 구조와 책임

### 5.1 책임 맵

- `UIRoot`: 씬 또는 전역 UI Canvas의 루트와 레이어를 소유한다.
- `UIManager`: 화면 생성, 열기, 닫기, 스택 관리를 담당한다.
- `UIScreen`: 화면 수명주기와 입력 가능 상태를 가진다.
- `UIPresenter`: View 이벤트를 받아 화면 로직과 데이터 갱신을 처리한다.
- `UIView`: 표시, 버튼 입력, 애니메이션 트리거 같은 뷰 책임을 가진다.
- `UIStack`: 뒤로가기와 중첩 팝업 순서를 관리한다.
- `UIAssetLoader`: UI 프리팹 또는 화면 리소스를 비동기로 로드한다.
- `InputContextService`: UI가 열릴 때 입력 컨텍스트를 전환하거나 차단한다.

핵심은 UI 화면을 "보이는 오브젝트"가 아니라 "수명주기를 가진 세션"으로 보는 것입니다. 화면은 열릴 때 데이터를 받고, 표시 중 이벤트를 구독하며, 닫힐 때 입력과 이벤트를 원래 상태로 돌려야 합니다.

### 5.2 화면 종류 구분

UI는 모두 같은 방식으로 닫히지 않습니다. 따라서 화면 종류를 먼저 나누는 편이 좋습니다.

- `HUD`: 게임플레이 중 계속 표시되는 상태 UI
- `Screen`: 인벤토리, 맵, 옵션처럼 화면 전체 전환이 필요한 UI
- `Popup`: 특정 화면 위에 중첩되는 선택 UI
- `Modal`: 사용자가 처리하기 전까지 아래 화면 입력을 막는 UI
- `Toast`: 입력을 막지 않는 짧은 알림
- `SystemOverlay`: 로딩, 네트워크 끊김, 치명 오류처럼 전역 우선순위가 높은 UI

이 구분은 디자인 분류가 아니라 입력과 스택 규칙을 정하기 위한 분류입니다. 예를 들어 `Toast`는 스택에 들어가지 않고, `Modal`은 아래 화면 입력을 막으며, `SystemOverlay`는 대부분의 UI보다 높은 우선순위를 가집니다.

## 6. UI 스택과 뒤로가기 규칙

뒤로가기는 UI 시스템의 품질을 빠르게 드러내는 지점입니다. 각 화면이 자기 방식대로 닫히면 중첩 화면에서 결과가 달라집니다.

권장 규칙은 아래와 같습니다.

1. 최상단 `Modal`이 있으면 먼저 처리한다.
2. 닫기 가능한 최상단 `Popup`을 닫는다.
3. 현재 `Screen`이 닫기 가능하면 이전 `Screen`으로 돌아간다.
4. 게임플레이 기본 화면이라면 pause 또는 confirm quit 정책을 따른다.
5. `SystemOverlay`가 활성화되어 있으면 별도 정책을 우선한다.

스택 항목은 단순 GameObject 참조가 아니라 화면 ID, 화면 종류, 닫기 가능 여부, 입력 차단 여부, owner를 가져야 합니다. 그래야 디버그 UI에서 현재 왜 뒤로가기가 막혔는지 확인할 수 있습니다.

---

## 7. 런타임 흐름

UI 시스템은 보통 아래 순서로 조립됩니다.

1. `SceneDI`가 `UIRoot`, `UIManager`, `UIAssetLoader`를 생성한다.
2. 씬 기본 HUD 또는 기본 Screen을 연다.
3. `Input System`과 연결해 UI 화면이 열릴 때 컨텍스트를 전환한다.
4. 화면 요청이 들어오면 `UIManager`가 중복 열기 여부와 현재 스택 정책을 확인한다.
5. 필요한 프리팹이나 화면 리소스를 비동기로 로드한다.
6. View와 Presenter를 연결하고 초기 데이터를 주입한다.
7. 화면이 닫힐 때 Presenter 구독을 해제하고 View를 반환하거나 파괴한다.
8. 스택 상태에 맞춰 입력 컨텍스트와 포커스를 복구한다.

이 흐름에서 중요한 점은 화면 로딩과 화면 표시가 같은 일이 아니라는 것입니다. 로딩 중에 닫기 요청이 들어오거나 같은 화면을 다시 열면, 화면이 늦게 도착해 잘못 표시될 수 있습니다. 요청 토큰이나 pending 상태가 필요합니다.

## 8. 인접 시스템 경계

### 8.1 Input System

UI는 게임플레이 입력을 직접 끄지 않습니다. UI가 열리면 `InputContextService`에 `UI` 컨텍스트 전환 또는 입력 차단 이유를 요청합니다. UI가 닫히면 스택 상태를 보고 이전 컨텍스트로 복구합니다.

### 8.2 EventBus

UI는 데이터 변경 이벤트를 구독할 수 있습니다. 하지만 닫힌 화면이 이벤트를 계속 받으면 안 됩니다. 구독은 Presenter의 `OnOpen` 또는 `Bind` 단계에서 하고, `OnClose` 또는 `Dispose`에서 해제해야 합니다.

### 8.3 SaveSystem

옵션, 키 바인딩, 화면 설정은 저장 시스템과 연결됩니다. UI는 저장 포맷을 직접 알기보다 설정 서비스에 변경 요청을 보내고, 저장 성공 또는 실패를 표시하는 편이 좋습니다.

### 8.4 Camera

대화 UI, 맵 UI, 포토 모드는 카메라 모드와 연결될 수 있습니다. UI가 카메라 컴포넌트를 직접 조작하지 않고, 카메라 시스템에 포커스 또는 모드 요청을 보내는 구조가 안전합니다.

### 8.5 SkillSystem과 Inventory

스킬 창, 장비 창, 인벤토리는 런타임 데이터를 표시합니다. UI는 데이터를 직접 수정하기보다 서비스에 명령을 보내고, 결과 이벤트 또는 조회 결과로 화면을 갱신해야 합니다.

## 9. 코어 구조 예시

Reference Example: UI 화면 세션과 스택 항목

```csharp
using System;
using System.Collections.Generic;

public enum UISurfaceType
{
    Hud,
    Screen,
    Popup,
    Modal,
    Toast,
    SystemOverlay
}

public sealed class UIStackEntry
{
    public UIStackEntry(string screenId, UISurfaceType type, bool canGoBack)
    {
        ScreenId = screenId;
        Type = type;
        CanGoBack = canGoBack;
    }

    public string ScreenId { get; }
    public UISurfaceType Type { get; }
    public bool CanGoBack { get; }
}

public interface UIScreenSession : IDisposable
{
    UIStackEntry Entry { get; }
    void Open();
    void Close();
}

public sealed class UIStack
{
    private readonly Stack<UIScreenSession> _sessions = new();

    public void Push(UIScreenSession session)
    {
        _sessions.Push(session);
        session.Open();
    }

    public bool TryBack()
    {
        if (_sessions.Count == 0)
        {
            return false;
        }

        var top = _sessions.Peek();

        if (!top.Entry.CanGoBack)
        {
            return false;
        }

        _sessions.Pop();
        top.Close();
        top.Dispose();
        return true;
    }
}
```

이 예제의 핵심 계약은 스택이 화면 닫기 순서를 소유한다는 점입니다. 화면 내부 버튼이 직접 다른 화면을 파괴하지 않고, 스택 정책을 통해 닫혀야 뒤로가기와 시스템 back 버튼이 같은 결과를 냅니다.

## 10. 성능과 트레이드오프

UI 성능 병목은 화면 하나의 렌더링보다, 반복적인 레이아웃 재계산, 리스트 전체 재생성, 잦은 EventBus 갱신, 비동기 로딩 중 중복 생성에서 자주 발생합니다. 특히 인벤토리, 스킬 목록, 퀘스트 목록처럼 데이터가 많은 화면은 열 때마다 모든 셀을 새로 만들면 프레임 드랍과 GC allocation이 함께 생길 수 있습니다.

권장 기준은 아래와 같습니다.

- 긴 목록은 셀 재사용 또는 가상화 정책을 검토한다.
- 데이터 변경 이벤트는 전체 화면 재생성보다 변경된 영역 갱신을 우선한다.
- 화면 open 요청은 pending 상태로 중복 생성을 막는다.
- 닫힌 화면의 Presenter는 이벤트를 받지 않게 해 불필요한 갱신을 차단한다.
- 자주 열리는 Popup은 풀링을 검토하되, Presenter 상태가 남지 않게 초기화 경로를 명확히 둔다.

트레이드오프도 있습니다. UI 화면을 Presenter와 세션으로 분리하면 파일과 클래스 수가 늘지만, 입력 복구, 이벤트 해제, 테스트, 비동기 실패 처리가 훨씬 명확해집니다. 반대로 View 하나에 모든 로직을 넣으면 빠르게 만들 수 있지만, 스택과 저장 데이터가 붙는 순간 변경 비용이 커집니다.

## 11. 실패 경로와 안티 패턴

### 11.1 화면 프리팹이 직접 다른 화면을 여는 경우

버튼 콜백에서 다른 UI 프리팹을 직접 생성하면 스택과 입력 컨텍스트가 우회됩니다. 화면 전환은 `UIManager`를 통해 요청되어야 합니다.

### 11.2 닫힌 UI가 이벤트를 계속 받는 경우

Presenter가 EventBus 구독을 해제하지 않으면 닫힌 화면이 데이터 변경 이벤트를 계속 받습니다. 중복 갱신, NRE, 메모리 누수로 이어질 수 있습니다.

### 11.3 UI 열기 중 중복 요청

비동기 로딩 중 같은 화면 열기 요청이 반복되면 화면이 두 번 생성될 수 있습니다. 화면 ID별 pending 상태나 요청 토큰으로 방어해야 합니다.

### 11.4 모든 UI를 하나의 Canvas와 하나의 depth로 처리하는 경우

HUD, Popup, Modal, SystemOverlay가 같은 depth에서 경쟁하면 중요한 오류 UI가 뒤에 깔리거나 토스트가 모달 위에 뜨는 문제가 생깁니다. 레이어와 surface type을 분리해야 합니다.

### 11.5 UI가 게임 규칙을 직접 수정하는 경우

인벤토리 UI가 아이템 배열을 직접 수정하거나 스킬 UI가 쿨다운 값을 직접 바꾸면 서비스 경계가 무너집니다. UI는 명령을 보내고 결과를 표시해야 합니다.

---

## 12. 기획 및 운영 우려사항

UI는 기획자가 텍스트, 노출 조건, 버튼 배치, 튜토리얼 문구를 자주 수정하는 영역입니다. 하지만 구조를 바꾸는 변경과 값만 바꾸는 변경을 구분해야 합니다.

기획자가 비교적 안전하게 다룰 수 있는 항목은 아래입니다.

- 버튼 라벨과 안내 문구
- 팝업 표시 조건의 일부 데이터 값
- 토스트 메시지와 지속 시간
- 화면에 표시할 정렬 기준과 필터 기본값
- 튜토리얼 강조 대상 ID

개발 협의가 필요한 변경은 아래입니다.

- 새 UI surface type 추가
- 뒤로가기 정책 변경
- 모달 입력 차단 정책 변경
- 비동기 로딩 방식 변경
- 저장 포맷이나 인벤토리 데이터 구조 변경
- 게임패드 포커스 이동 규칙 변경

특히 UI 노출 조건은 단순 텍스트 변경처럼 보여도 저장 데이터, 튜토리얼 진행도, 상품 상태, 퀘스트 상태와 연결될 수 있습니다. validator 없이 문자열 ID만으로 연결하면 런타임 누락이 늦게 발견됩니다.

---

## 13. 디버깅 및 검증 포인트

- 현재 UI 스택과 최상단 화면을 디버그 UI에서 확인할 수 있는가
- 각 화면의 surface type, owner, canGoBack 값이 보이는가
- UI가 열렸을 때 입력 컨텍스트가 `UI` 또는 차단 상태로 전환되는가
- UI가 닫힌 뒤 이전 입력 컨텍스트가 복구되는가
- 닫힌 Presenter가 EventBus 이벤트를 받지 않는가
- 비동기 로딩 실패 시 사용자에게 실패 상태가 표시되는가
- 시스템 back 버튼과 UI 닫기 버튼이 같은 정책을 쓰는가

---

## 14. 리뷰 체크리스트

- UI 화면 종류와 depth 정책이 정의되어 있는가
- 화면 생성과 닫기가 `UIManager` 또는 스택을 통해 일관되게 처리되는가
- View와 Presenter 책임이 분리되어 있는가
- 입력 컨텍스트 전환과 복구가 문서에 닫혀 있는가
- EventBus 구독 해제와 비동기 로딩 실패 경로가 보이는가
- 기획 변경 가능 범위와 개발 협의 범위가 분리되어 있는가

## [개발 가이드] UI 아키텍처 및 관리 시스템 (UI Architecture & Manager)

> 최종 수정일: 2026-05-04
> 문서 상태: `Reviewable`

---

## 1. 개요 및 읽는 순서

이 가이드는 UI 시스템을 실제 프로젝트에 붙이는 방법을 코드 기준으로 설명합니다. 핵심은 화면 프리팹을 여는 코드가 아니라, **UI 루트, 화면 스택, Presenter, 입력 컨텍스트, 비동기 로딩, 이벤트 구독 해제**를 한 묶음으로 조립하는 데 있습니다.

읽는 순서는 아래가 자연스럽습니다.

1. UI surface type과 레이어를 정의합니다.
2. `UIManager`와 `UIStack`을 구성합니다.
3. View와 Presenter의 책임을 분리합니다.
4. `SceneDI`에서 UI 루트와 입력 시스템을 연결합니다.
5. 비동기 로딩, 뒤로가기, 닫기 실패 경로를 검증합니다.

---

## 2. 이 가이드가 전제하는 계약

- 화면 열기와 닫기는 `UIManager`를 통해 수행한다.
- 화면 종류는 입력과 depth 정책을 결정한다.
- View는 표시와 입력 전달만 맡고 Presenter가 화면 로직을 맡는다.
- UI는 게임플레이 입력을 직접 끄지 않고 입력 서비스에 요청한다.
- EventBus 구독은 화면 수명주기에 맞춰 반드시 해제한다.

이 계약이 무너지면 화면은 보이지만 스택에는 없거나, 닫힌 화면이 이벤트를 받고, UI가 닫힌 뒤에도 게임플레이 입력이 복구되지 않는 문제가 생깁니다.

## 4. 최소 동작 예제

Reference Example: 화면 열기 요청

```csharp
using System;
using System.Collections.Generic;
using System.Threading.Tasks;

public sealed class UIManager
{
    private readonly UIStack _stack;
    private readonly IUIScreenFactory _factory;
    private readonly HashSet<string> _pending = new();

    public UIManager(UIStack stack, IUIScreenFactory factory)
    {
        _stack = stack;
        _factory = factory;
    }

    public async Task OpenAsync(string screenId)
    {
        if (!_pending.Add(screenId))
        {
            return;
        }

        try
        {
            var session = await _factory.CreateAsync(screenId);
            _stack.Push(session);
        }
        finally
        {
            _pending.Remove(screenId);
        }
    }

    public bool Back()
    {
        return _stack.TryBack();
    }
}
```

이 예제의 핵심 계약은 화면 ID별 pending 상태를 가진다는 점입니다. 비동기 로딩 중 같은 버튼을 여러 번 눌러도 같은 화면이 중복 생성되지 않아야 합니다.

## 5. 실무 예제

최소 동작 예제가 화면 요청 중복 방어를 보여준다면, 실무 예제는 View와 Presenter, 입력 컨텍스트, SceneDI 조립이 같은 수명주기로 묶이는지 확인하는 데 목적이 있습니다.

### 5.1 View와 Presenter 분리

Reference Example: View 인터페이스

```csharp
using System;

public interface IInventoryView
{
    event Action<int> SlotClicked;
    event Action CloseClicked;

    void SetTitle(string title);
    void SetSlots(InventorySlotViewModel[] slots);
    void SetEmptyState(bool visible);
}
```

View는 Unity UI 컴포넌트를 알고 있어도 됩니다. 하지만 인벤토리 규칙, 아이템 장착 가능 여부, 저장 데이터 변경 같은 게임 규칙은 알지 않는 편이 좋습니다.

Reference Example: Presenter

```csharp
using System;

public sealed class InventoryPresenter : IDisposable
{
    private readonly IInventoryView _view;
    private readonly IInventoryService _inventory;
    private readonly IUIManager _ui;

    public InventoryPresenter(IInventoryView view, IInventoryService inventory, IUIManager ui)
    {
        _view = view;
        _inventory = inventory;
        _ui = ui;
    }

    public void Bind()
    {
        _view.SlotClicked += OnSlotClicked;
        _view.CloseClicked += OnCloseClicked;
        Refresh();
    }

    public void Dispose()
    {
        _view.SlotClicked -= OnSlotClicked;
        _view.CloseClicked -= OnCloseClicked;
    }

    private void Refresh()
    {
        var slots = _inventory.GetSlots();
        _view.SetSlots(slots);
        _view.SetEmptyState(slots.Length == 0);
    }

    private void OnSlotClicked(int slotIndex)
    {
        _inventory.SelectSlot(slotIndex);
    }

    private void OnCloseClicked()
    {
        _ui.Back();
    }
}
```

이 예제의 핵심 계약은 Presenter가 화면 이벤트 구독과 해제를 소유한다는 점입니다. View가 직접 인벤토리 서비스를 수정하거나, 닫기 버튼이 화면 오브젝트를 직접 파괴하지 않습니다.

---

### 5.2 입력 컨텍스트 연결

UI 화면이 열릴 때 입력 컨텍스트를 전환하고 닫힐 때 복구해야 합니다. 이 책임은 각 버튼 콜백에 흩어져 있으면 안 됩니다.

Reference Example: UI 세션 스코프

```csharp
using System;

public sealed class UIScreenSession : IDisposable
{
    private readonly IInputContextService _input;
    private readonly IDisposable _presenter;
    private readonly UIView _view;

    public UIScreenSession(IInputContextService input, IDisposable presenter, UIView view)
    {
        _input = input;
        _presenter = presenter;
        _view = view;
    }

    public void Open()
    {
        _input.SwitchTo(InputContext.UI);
        _view.Show();
    }

    public void Close()
    {
        _view.Hide();
    }

    public void Dispose()
    {
        _presenter.Dispose();
        _input.RestorePrevious();
    }
}
```

실무에서는 스택 상태에 따라 `RestorePrevious()`가 단순히 `Gameplay`로 돌아가지 않을 수 있습니다. 아래에 다른 UI가 남아 있다면 계속 `UI` 컨텍스트를 유지해야 합니다.

### 5.3 SceneDI 조립 예시

Reference Example: UI 루트 등록

```csharp
public sealed class UISceneInstaller
{
    public void Install(SceneContainer container)
    {
        var root = new UIRoot();
        var stack = new UIStack();
        var factory = new AddressableUIScreenFactory(root);
        var manager = new UIManager(stack, factory);

}
```

`SceneDI`는 UI 루트와 팩토리, 매니저를 조립합니다. 개별 화면 Presenter는 화면 생성 시점에 필요한 서비스와 함께 만들어지는 편이 좋습니다.

---

## 6. 통합 시나리오

UI 시스템은 화면 스택만으로 끝나지 않습니다. 인벤토리, 옵션, 대화, 포토 모드처럼 서로 다른 화면이 입력, 데이터, 카메라를 함께 바꾸는 상황에서 같은 규칙을 유지해야 합니다.

### 6.1 EventBus 구독 규칙

UI는 EventBus를 사용할 수 있지만, 화면 생명주기와 맞아야 합니다.

권장 기준은 아래입니다.

1. Presenter `Bind()`에서 구독한다.
2. Presenter `Dispose()`에서 해제한다.
3. 닫힌 화면은 이벤트를 받지 않는다.
4. HUD처럼 항상 살아 있는 UI만 장기 구독을 허용한다.
5. 데이터가 빈번히 바뀌는 화면은 필요 시 throttling이나 diff 갱신을 검토한다.

EventBus 이벤트를 View가 직접 구독하는 구조는 피하는 편이 좋습니다. View가 게임 데이터 이벤트를 알기 시작하면 표시 책임과 게임 규칙 책임이 섞입니다.

---

### 6.2 비동기 로딩 실패 처리

UI 프리팹이나 화면 데이터를 비동기로 불러올 때는 실패 경로를 닫아야 합니다.

- 로딩 중 같은 화면 요청은 무시하거나 기존 요청을 재사용한다.
- 로딩 중 닫기 요청이 들어오면 도착한 화면을 표시하지 않는다.
- 로딩 실패 시 pending 상태를 반드시 해제한다.
- 중요한 화면이면 실패 팝업 또는 fallback 화면을 표시한다.
- 씬 종료 중인 경우 늦게 도착한 UI는 즉시 폐기한다.

이 기준이 없으면 버튼을 빠르게 여러 번 누르거나 씬을 빠르게 나갈 때 유령 UI가 남을 수 있습니다.

---

## 7. 자주 하는 실수

### 7.1 버튼에서 직접 `Destroy` 호출

닫기 버튼이 자기 화면 오브젝트를 직접 파괴하면 스택, 입력 컨텍스트, Presenter 해제가 우회됩니다. 닫기 요청은 `UIManager.Back()` 또는 명시적인 `Close(screenId)`로 보내야 합니다.

### 7.2 Presenter가 해제되지 않는 구조

화면 GameObject만 꺼지고 Presenter가 살아 있으면 이벤트 구독과 데이터 참조가 남습니다. 화면 세션이 Presenter의 수명도 함께 닫아야 합니다.

### 7.3 HUD와 Popup을 같은 규칙으로 처리

HUD는 기본적으로 게임플레이와 함께 살아 있고, Popup은 스택과 입력 차단을 가집니다. 둘을 같은 화면 타입으로 처리하면 뒤로가기와 입력 정책이 섞입니다.

### 7.4 UI가 저장 데이터를 직접 수정

옵션 UI가 저장 파일을 직접 쓰거나 인벤토리 UI가 데이터 배열을 직접 수정하면 검증과 실패 처리가 사라집니다. UI는 서비스에 요청하고 결과를 표시해야 합니다.

---

## 8. 디버깅 보조

UI 문제가 생기면 아래 순서로 확인합니다.

1. 현재 UI 스택을 확인합니다.
2. 최상단 surface type과 canGoBack 값을 확인합니다.
3. 입력 컨텍스트가 현재 UI 상태와 일치하는지 확인합니다.
4. pending 화면 요청이 남아 있는지 확인합니다.
5. 닫힌 Presenter가 EventBus 이벤트를 받는지 확인합니다.
6. 화면 닫기 버튼과 시스템 back 버튼이 같은 경로를 타는지 확인합니다.

디버그 패널에는 현재 스택, pending 화면 ID, 입력 컨텍스트, EventBus 구독 수를 표시하는 편이 좋습니다.

---

## 9. 쓰지 말아야 하는 경우

단일 HUD만 있고 팝업, 화면 전환, 비동기 로딩이 없는 작은 프로토타입이라면 전체 UI 스택 구조는 과할 수 있습니다. 하지만 인벤토리, 옵션, 확인 팝업, 로딩 오버레이 중 둘 이상이 들어가면 초기에 스택과 입력 컨텍스트를 분리하는 편이 안전합니다.

---

## 10. 검증 체크리스트

- 화면 열기와 닫기가 `UIManager`를 통해 처리되는가
- 화면별 surface type과 depth 정책이 있는가
- View가 게임 규칙 서비스를 직접 수정하지 않는가
- Presenter가 이벤트 구독과 해제를 모두 소유하는가
- 비동기 로딩 중 중복 요청과 취소 요청이 처리되는가
- UI 종료 후 입력 컨텍스트가 올바르게 복구되는가
