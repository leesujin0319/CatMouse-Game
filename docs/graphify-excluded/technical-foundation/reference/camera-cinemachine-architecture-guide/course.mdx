## [기술 기획안] 카메라 연출 및 제어 시스템 (Camera & Cinemachine Management)

> 최종 수정일: 2026-05-04
> 문서 상태: `Reviewable`

---

## 1. 개요 및 설계 목적

이 문서는 카메라를 각 씬의 `Camera`, `Cinemachine`, 애니메이션 타임라인 설정에 맡겨 두지 않고, **게임플레이 상태와 연출 요청을 통합하는 카메라 제어 계약**으로 관리하기 위한 기준을 정의합니다.

카메라는 플레이어 조작, 전투 판정, UI 가독성, 컷신, 피격 반응, 보스 연출, 씬 전환을 동시에 건드립니다. 작은 프로젝트에서는 가상 카메라 우선순위를 직접 바꾸거나, 피격 순간에 카메라 흔들림을 즉시 호출하는 방식으로도 동작합니다. 하지만 시스템이 늘어나면 스킬 줌인, 대화 카메라, 보스 등장 컷신, 사망 연출, 포토 모드가 서로 카메라를 빼앗는 문제가 생깁니다.

이 문서의 목적은 카메라 기능을 많이 나열하는 것이 아닙니다. **누가 카메라 제어권을 요청하고, 어떤 요청이 우선하며, 언제 원래 상태로 복귀하고, 실패했을 때 어떤 화면을 보장할지**를 닫는 데 있습니다.

**이 문서가 바로 답하는 질문**

- 게임플레이 카메라와 연출 카메라를 어떻게 분리해야 하는가
- 스킬, 피격, 컷신, 대화, UI가 동시에 카메라를 요청하면 무엇이 우선인가
- 카메라 흔들림, 줌, 타임 슬로우는 누가 생성하고 누가 해제하는가
- 씬 전환 시 카메라 상태는 어디서 초기화되어야 하는가
- `SceneDI`, `Input System`, `State Machine`, `SkillSystem`, UI와 어디서 연결해야 하는가

---

## 2. 문제 정의

카메라 버그는 대개 기능이 없어서가 아니라 **소유권이 여러 곳에 흩어져서** 발생합니다. 스킬 시스템이 직접 줌을 바꾸고, 몬스터 AI가 보스 카메라를 켜고, UI 팝업이 포커스 카메라를 열고, 컷신 타임라인이 메인 카메라를 덮어쓰면 어느 요청이 언제 끝나는지 추적하기 어렵습니다.

실제 프로젝트에서 흔한 증상은 아래와 같습니다.

- 스킬 줌인이 끝난 뒤 기본 시야각으로 돌아오지 않는다.
- 피격 흔들림과 컷신 블렌딩이 겹쳐 화면이 과도하게 흔들린다.
- 대화 카메라가 열린 상태에서 전투 카메라 입력이 살아 있다.
- 씬 전환 후 이전 씬의 카메라 우선순위가 남아 첫 프레임이 튄다.
- 타임 슬로우 연출이 끝났는데 실제 게임 시간 배율이 복구되지 않는다.

따라서 카메라 설계의 핵심 문제는 "어떤 카메라 효과를 쓸 것인가"보다, **카메라 제어권과 연출 수명주기를 중앙에서 추적할 수 있는가**입니다.

---

## 3. 설계 목표

- 기본 게임플레이 카메라와 일시 연출 카메라를 분리한다.
- 카메라 요청을 우선순위와 수명주기로 관리한다.
- 줌, 흔들림, 포커스, 컷신, 타임 슬로우를 독립 효과가 아니라 연출 요청의 일부로 취급한다.
- `Input System`과 연동해 카메라 입력 가능 상태를 명확히 한다.
- `State Machine`과 `SkillSystem`은 카메라를 직접 소유하지 않고 요청만 보낸다.
- 씬 진입과 종료 시 카메라 상태 초기화와 복구를 `SceneDI` 흐름 안에서 보장한다.
- 디버그 UI에서 현재 카메라 소유자와 활성 효과를 확인할 수 있게 한다.

---

## 4. 범위와 비범위

### In Scope

- 게임플레이 카메라 리그와 연출 카메라 리그 분리 기준
- 카메라 요청 우선순위와 복구 규약
- 흔들림, 줌, 포커스, 블렌딩, 타임 슬로우 요청 수명주기
- 씬 전환과 컷신 시작/종료 시 카메라 초기화 기준
- `SceneDI`, 입력, 상태 머신, 스킬 시스템, UI와의 경계

### Out of Scope

- 특정 Cinemachine 버전의 세부 컴포넌트 API 설명
- 개별 장르별 감도 수치 튜닝
- 물리 기반 카메라 충돌 보정 알고리즘 상세
- 컷신 타임라인 제작 툴링 전체
- 포토 모드 편집 UI 전체

이 문서는 카메라의 **설계 계약과 연출 수명주기**를 다룹니다. 개별 장르별 카메라 감도, 특정 패키지의 세부 설정값, 아티스트용 컷신 제작 워크플로는 별도 문서에서 확장하는 편이 안전합니다.

---

## 5. 핵심 구조와 책임

### 5.1 책임 맵

- `CameraDirector`: 현재 카메라 제어권과 요청 우선순위를 관리한다.
- `CameraRig`: 게임플레이, 대화, 컷신, 보스전 같은 카메라 모드를 표현한다.
- `CameraRequest`: 줌, 포커스, 흔들림, 블렌드, 시간 배율 같은 일시 연출 요청이다.
- `CameraEffectHandle`: 요청 종료와 복구를 보장하는 핸들이다.
- `CameraInputController`: 카메라 회전, 줌, 락온 전환 같은 입력을 소비한다.
- `SceneDI`: 씬 진입 시 카메라 리그와 디렉터를 조립하고, 종료 시 상태를 정리한다.
- `Actor / Skill / UI`: 카메라를 직접 조작하지 않고 연출 요청을 만든다.

`CameraDirector`는 모든 카메라 기능을 직접 구현하는 거대한 매니저가 아닙니다. 핵심 책임은 현재 어떤 카메라 리그가 유효한지, 어떤 일시 효과가 적용 중인지, 종료 시 무엇을 되돌려야 하는지를 추적하는 것입니다.

### 5.2 카메라 리그와 카메라 효과

카메라 리그는 장기적으로 유지되는 모드입니다. `Gameplay`, `Dialogue`, `BossIntro`, `Cutscene`, `PhotoMode`처럼 입력, 타겟, 블렌딩, UI 노출 규칙이 달라지는 경우 리그로 분리합니다.

카메라 효과는 짧게 적용되는 변화입니다. 피격 흔들림, 스킬 줌인, 타격 순간 프리즈, 타겟 포커스, 화면 가장자리 강조처럼 기본 리그 위에 잠깐 얹히는 변화는 요청으로 관리합니다.

이 둘을 섞으면 문제가 생깁니다. 피격 흔들림을 새 리그로 만들면 우선순위가 과도하게 커지고, 컷신 카메라를 단순 효과로 만들면 입력 차단과 복구 규칙이 빠지기 쉽습니다.

---

## 6. 우선순위와 수명주기

카메라 요청은 모두 같은 무게가 아닙니다. 기본 게임플레이 카메라는 가장 낮은 우선순위를 가지며, 플레이어 입력에 따라 계속 움직입니다. 반대로 사망 연출, 컷신, 보스 등장처럼 플레이어 통제를 일시적으로 빼앗는 카메라는 높은 우선순위를 가져야 합니다.

권장 우선순위는 아래에 가깝습니다.

1. `Fatal / SceneTransition`: 사망, 씬 전환, 로딩 실패
2. `Cutscene`: 타임라인, 보스 등장, 중요한 대화 연출
3. `ForcedFocus`: 락온 강제, 튜토리얼 포커스, 목표 오브젝트 강조
4. `CombatMoment`: 스킬 줌, 피격 흔들림, 타격 정지
5. `Gameplay`: 플레이어 카메라 입력과 기본 추적

수명주기는 반드시 닫혀야 합니다. 요청은 시작 시점에 핸들을 받고, 종료 시 핸들이 복구를 요청합니다. 시간 기반 요청은 만료 시간이 있어야 하고, 상태 기반 요청은 상태 종료나 씬 종료에서 반드시 해제되어야 합니다.

---

## 7. 런타임 흐름

카메라 시스템은 보통 아래 순서로 붙습니다.

1. `SceneDI`가 씬의 기본 카메라 리그와 `CameraDirector`를 생성한다.
2. 기본 리그를 `Gameplay` 또는 씬 전용 리그로 설정한다.
3. `Input System`이 카메라 입력 가능 상태를 연결한다.
4. 액터, 스킬, UI, 컷신 시스템이 `CameraDirector`에 요청을 보낼 수 있게 연결된다.
5. 게임플레이 중 가장 높은 우선순위의 리그와 활성 효과를 합성해 카메라 상태를 적용한다.
6. 요청이 만료되거나 핸들이 해제되면 이전 상태로 복구한다.
7. 씬 종료 시 모든 활성 요청을 취소하고 기본 시간 배율, 시야각, 입력 상태를 복구한다.

이 흐름에서 중요한 점은 기본 카메라 리그가 항상 복귀 지점으로 남아 있어야 한다는 것입니다. 연출 요청이 끝났는데 돌아갈 기준이 없으면, 마지막 요청의 값이 다음 플레이 구간까지 잔류합니다.

---

## 8. 인접 시스템 경계

### 8.1 SceneDI

`SceneDI`는 카메라 리그를 씬 구성에 맞게 조립합니다. 하지만 매 프레임 연출 우선순위를 판단하는 위치는 `CameraDirector`입니다. 씬 디렉터가 카메라 요청 리스트까지 직접 관리하면 씬 로딩 책임과 연출 책임이 섞입니다.

### 8.2 Input System

카메라 회전, 줌, 락온 전환은 입력 시스템에서 정리된 입력으로 들어옵니다. 카메라 시스템은 현재 리그가 입력을 허용하는지 판단합니다. 컷신이나 대화 리그에서는 카메라 입력을 무시하거나 제한해야 합니다.

### 8.3 State Machine

상태 머신은 피격, 사망, 회피, 공격 같은 상태 전환을 알고 있습니다. 하지만 카메라 값을 직접 바꾸면 안 됩니다. 상태 진입 시 `CameraDirector`에 요청을 만들고, 상태 종료 시 핸들을 해제하는 방식이 더 안전합니다.

### 8.4 SkillSystem

스킬 데이터는 "이 스킬은 타격 시점에 줌을 요청한다" 정도의 연출 키를 가질 수 있습니다. 실제 줌 강도, 블렌딩, 중복 처리, 복구는 카메라 시스템이 소유해야 합니다.

### 8.5 UI

대화, 인벤토리, 맵, 포토 모드 UI는 카메라 입력과 화면 구성을 바꿀 수 있습니다. UI는 직접 카메라 컴포넌트를 조작하지 않고, 모드 전환 또는 포커스 요청을 보내야 합니다.

## 9. 코어 구조 예시

Reference Example: 카메라 요청과 핸들

```csharp
using System;
using System.Collections.Generic;

public enum CameraPriority
{
    Gameplay = 0,
    CombatMoment = 10,
    ForcedFocus = 20,
    Cutscene = 30,
    SceneTransition = 40
}

public readonly struct CameraRequest
{
    public CameraRequest(string owner, CameraPriority priority, float durationSeconds)
    {
        Owner = owner;
        Priority = priority;
        DurationSeconds = durationSeconds;
    }

    public string Owner { get; }
    public CameraPriority Priority { get; }
    public float DurationSeconds { get; }
}

public sealed class CameraEffectHandle : IDisposable
{
    private readonly Action _release;
    private bool _disposed;

    public CameraEffectHandle(Action release)
    {
        _release = release;
    }

    public void Dispose()
    {
        if (_disposed)
        {
            return;
        }

        _disposed = true;
        _release.Invoke();
    }
}

public sealed class CameraDirector
{
    private readonly List<CameraRequest> _requests = new();

    public CameraEffectHandle Push(CameraRequest request)
    {
        _requests.Add(request);
        ApplyTopRequest();

        return new CameraEffectHandle(() =>
        {
            _requests.Remove(request);
            ApplyTopRequest();
        });
    }

    private void ApplyTopRequest()
    {
        // Select highest priority request and apply rig/effect values.
    }
}
```

이 예제의 핵심 계약은 카메라 요청이 반드시 해제 가능한 핸들을 가진다는 점입니다. 스킬, 피격, 컷신이 카메라를 직접 되돌리는 것이 아니라, 요청 수명주기가 끝날 때 디렉터가 현재 최고 우선순위를 다시 계산합니다.

## 10. 성능과 트레이드오프

카메라 시스템의 성능 병목은 대개 렌더링 자체보다, 매 프레임 타겟 탐색, 리그 전환, 효과 중첩, 물리 충돌 보정, 불필요한 할당에서 발생합니다. 카메라 요청이 들어올 때마다 씬 전체에서 타겟을 찾거나, 문자열 기반 owner를 반복 생성하거나, 흔들림 효과를 매 프레임 새 객체로 만들면 전투 중 GC pressure가 쌓일 수 있습니다.

권장 기준은 아래와 같습니다.

- 타겟 참조는 요청 생성 시점에 확정하고 매 프레임 탐색하지 않는다.
- 카메라 요청과 핸들은 가능하면 짧은 수명 객체로 제한하고 장기 effect는 갱신 방식으로 관리한다.
- 동일 카테고리 흔들림은 무제한 누적하지 않고 갱신, 최대값 선택, 감쇠 중 하나로 제한한다.
- 컷신과 전투 연출이 동시에 들어올 때 불필요한 블렌드 계산이 반복되지 않게 최고 우선순위만 적용한다.
- 시간 배율 변경은 전투 판정과 입력 버퍼에 영향을 주므로 카메라 연출만의 최적화로 다루지 않는다.

트레이드오프도 있습니다. 중앙 `CameraDirector`를 두면 요청 흐름은 추적하기 쉬워지지만, 모든 연출 요청이 이 경로를 거쳐야 하므로 간단한 프로토타입보다 초기 구조가 무겁습니다. 반대로 각 시스템이 직접 카메라를 조작하면 빠르게 만들 수 있지만, 컷신, 전투, UI가 겹치는 순간 복구 비용과 디버깅 비용이 커집니다.

---

## 11. 실패 경로와 안티 패턴

### 11.1 스킬 코드가 직접 시야각을 바꾸는 경우

스킬 코드가 카메라 시야각을 직접 바꾸고 직접 복구하면, 피격 흔들림이나 컷신과 겹칠 때 원래 값이 무엇인지 잃어버릴 수 있습니다. 스킬은 연출 요청만 만들고 복구는 `CameraDirector`가 처리해야 합니다.

### 11.2 컷신 종료 시 입력과 시간 배율이 남는 경우

컷신은 카메라뿐 아니라 입력 차단과 시간 배율을 함께 건드립니다. 컷신 종료 경로가 예외로 빠지면 게임플레이 입력이 돌아오지 않거나 시간이 느린 상태로 남을 수 있습니다. 종료 핸들 또는 스코프 단위 복구가 필요합니다.

### 11.3 모든 카메라를 우선순위 숫자로만 해결하는 경우

숫자 우선순위는 필요하지만 충분하지 않습니다. 요청의 owner, 만료 조건, 복구 대상, 입력 차단 여부가 함께 기록되어야 디버깅할 수 있습니다.

### 11.4 씬 전환 후 이전 요청이 남는 경우

씬 전환 시 활성 요청을 정리하지 않으면 이전 씬의 연출 카메라가 다음 씬 첫 프레임에 영향을 줍니다. `SceneDI` 종료 단계에서 모든 카메라 핸들을 강제 해제해야 합니다.

---

## 12. 기획 및 운영 우려사항

카메라 값은 기획과 연출에서 자주 조정합니다. 하지만 모든 값을 자유롭게 바꾸면 멀미, 조작성 저하, UI 가림, 타격 판정 오해가 생길 수 있습니다.

기획자가 비교적 안전하게 다룰 수 있는 항목은 아래입니다.

- 스킬별 카메라 흔들림 강도와 지속 시간
- 연출 줌의 목표 거리와 블렌딩 시간
- 보스 등장 컷신의 카메라 리그 선택
- 튜토리얼 포커스 대상과 지속 시간

개발 협의가 필요한 변경은 아래입니다.

- 새 카메라 리그 추가
- 입력 차단 정책 변경
- 시간 배율 변경이 포함된 연출 추가
- 카메라 충돌 보정 방식 변경
- UI 레이아웃과 카메라 framing이 함께 바뀌는 기능

특히 타임 슬로우와 카메라 흔들림은 값만 조정하는 것처럼 보이지만, 전투 판정 체감과 접근성에 직접 영향을 줍니다. 강한 흔들림은 옵션에서 줄이거나 끌 수 있는 정책을 함께 고려해야 합니다.

---

## 13. 디버깅 및 검증 포인트

- 현재 활성 카메라 리그와 최고 우선순위 요청을 확인할 수 있는가
- 요청 owner와 만료 조건이 디버그 UI에 표시되는가
- 컷신, 대화, 포토 모드 종료 후 입력과 시간 배율이 복구되는가
- 스킬 줌, 피격 흔들림, 보스 카메라가 겹칠 때 우선순위가 재현 가능한가
- 씬 전환 후 이전 카메라 요청이 남지 않는가
- UI 중요한 요소가 카메라 framing에 의해 가려지지 않는가

---

## 14. 리뷰 체크리스트

- 카메라 리그와 카메라 효과가 구분되어 있는가
- 카메라 요청의 owner, 우선순위, 수명주기가 명시되어 있는가
- 상태 머신과 스킬 시스템이 카메라를 직접 소유하지 않는가
- 씬 종료 시 모든 활성 요청이 정리되는가
- 기획자가 조정 가능한 값과 개발 협의가 필요한 변경이 분리되어 있는가

## [개발 가이드] 카메라 연출 및 제어 시스템 (Camera & Cinemachine Management)

> 최종 수정일: 2026-05-04
> 문서 상태: `Reviewable`

---

## 1. 개요 및 읽는 순서

이 가이드는 카메라 시스템을 실제 프로젝트에 붙이는 기준을 설명합니다. 핵심은 특정 카메라 패키지의 옵션을 외우는 것이 아니라, **카메라 리그, 연출 요청, 우선순위, 입력 차단, 씬 정리**를 하나의 흐름으로 조립하는 데 있습니다.

읽는 순서는 아래가 자연스럽습니다.

1. 카메라 리그와 요청 타입을 먼저 정의합니다.
2. `CameraDirector`가 요청 우선순위를 관리하게 합니다.
3. `SceneDI`에서 기본 리그와 인접 시스템을 연결합니다.
4. 스킬, 피격, 컷신, UI에서 직접 카메라를 만지지 않고 요청을 보내게 합니다.
5. 씬 종료와 예외 종료에서 모든 요청이 해제되는지 검증합니다.

---

## 2. 이 가이드가 전제하는 계약

- 카메라 리그는 장기 모드이고 카메라 효과는 일시 요청이다.
- 카메라 제어권은 `CameraDirector`가 관리한다.
- 스킬, 상태, UI는 카메라 값을 직접 변경하지 않는다.
- 모든 일시 연출은 해제 가능한 핸들을 가진다.
- 씬 종료 시 활성 요청과 시간 배율, 입력 차단이 복구된다.

이 계약이 무너지면 스킬 줌, 피격 흔들림, 컷신 카메라가 서로 값을 덮어쓰고, 연출 종료 후 이전 값이 잔류하는 문제가 생깁니다.

## 4. 최소 동작 예제

Reference Example: 카메라 요청 모델

```csharp
public enum CameraMode
{
    Gameplay,
    Dialogue,
    Cutscene,
    PhotoMode
}

public sealed class CameraRigRequest
{
    public CameraRigRequest(string owner, CameraMode mode, int priority)
    {
        Owner = owner;
        Mode = mode;
        Priority = priority;
    }

    public string Owner { get; }
    public CameraMode Mode { get; }
    public int Priority { get; }
}
```

이 모델은 최소 구조입니다. 실무에서는 블렌딩 시간, 타겟, 시야각, 입력 허용 여부, 만료 조건을 함께 가질 수 있습니다. 중요한 점은 owner와 priority가 있어야 어떤 시스템이 카메라를 점유 중인지 추적할 수 있다는 점입니다.

Reference Example: 디렉터와 핸들

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

public sealed class CameraDirector
{
    private readonly List<CameraRigRequest> _requests = new();
    private readonly Action<CameraRigRequest> _apply;
    private readonly CameraRigRequest _gameplay;

    public CameraDirector(Action<CameraRigRequest> apply)
    {
        _apply = apply;
        _gameplay = new CameraRigRequest("Default", CameraMode.Gameplay, 0);
    }

    public IDisposable Push(CameraRigRequest request)
    {
        _requests.Add(request);
        ApplyCurrent();

        return new Scope(() =>
        {
            _requests.Remove(request);
            ApplyCurrent();
        });
    }

    public void ClearAll()
    {
        _requests.Clear();
        ApplyCurrent();
    }

    private void ApplyCurrent()
    {
        var top = _requests
            .OrderByDescending(request => request.Priority)
            .FirstOrDefault() ?? _gameplay;

        _apply.Invoke(top);
    }

    private sealed class Scope : IDisposable
    {
        private readonly Action _dispose;
        private bool _disposed;

        public Scope(Action dispose)
        {
            _dispose = dispose;
        }

        public void Dispose()
        {
            if (_disposed)
            {
                return;
            }

            _disposed = true;
            _dispose.Invoke();
        }
    }
}
```

이 예제의 핵심 계약은 `ClearAll()`과 `Dispose()` 경로가 모두 있다는 점입니다. 정상 종료는 핸들이 닫고, 씬 종료나 예외 종료는 디렉터가 남은 요청을 한 번에 정리합니다.

## 5. 실무 예제

최소 동작 예제가 카메라 요청과 스택 복구만 보여준다면, 실무 예제는 씬 조립, 스킬 상태, 컷신, 입력 차단이 같은 계약으로 연결되는지 확인하는 데 목적이 있습니다.

### 5.1 SceneDI 조립 예시

Reference Example: 씬 진입 시 조립 흐름

```csharp
public sealed class BattleSceneInstaller
{
    public void Install(SceneContainer container)
    {
        var cameraRigApplier = new UnityCameraRigApplier();
        var cameraDirector = new CameraDirector(cameraRigApplier.Apply);

        container.RegisterInstance(cameraDirector);
        container.RegisterInstance<ICameraDirector>(cameraDirector);
    }
}
```

`SceneDI`는 `CameraDirector`와 실제 Unity 카메라 적용기를 연결합니다. 액터나 스킬 시스템은 `ICameraDirector`에만 의존하고, 실제 카메라 컴포넌트 이름이나 리그 오브젝트 구조는 알지 않는 편이 좋습니다.

---

### 5.2 스킬 연출 연결

Reference Example: 스킬 상태에서 카메라 요청 사용

```csharp
using System;

public sealed class SkillCastState
{
    private readonly ICameraDirector _cameraDirector;
    private IDisposable _cameraScope;

    public SkillCastState(ICameraDirector cameraDirector)
    {
        _cameraDirector = cameraDirector;
    }

    public void OnEnter(string skillId)
    {
        _cameraScope = _cameraDirector.PushCombatMoment($"Skill:{skillId}");
    }

    public void OnExit()
    {
        _cameraScope?.Dispose();
        _cameraScope = null;
    }
}
```

스킬 상태는 카메라 값을 알지 않습니다. "이 스킬이 전투 순간 연출을 요청한다"는 사실만 전달합니다. 실제 줌 강도, 흔들림, 블렌드 시간은 카메라 시스템이나 연출 데이터가 결정해야 합니다.

---

## 6. 통합 시나리오

컷신과 대화는 단순 카메라 효과가 아니라 입력 차단과 UI 상태를 함께 바꾸는 경우가 많습니다. 따라서 컷신 시작 시 아래 작업을 하나의 스코프로 묶는 편이 안전합니다.

1. 카메라 리그를 `Cutscene` 또는 `Dialogue`로 전환한다.
2. 입력 시스템에 `Cutscene` 또는 `Dialogue` 차단 이유를 등록한다.
3. 필요한 경우 시간 배율 또는 UI 표시 상태를 변경한다.
4. 컷신 종료, 스킵, 실패, 씬 이탈 중 어떤 경로에서도 동일하게 복구한다.

이 절차가 분산되면 스킵 버튼으로 빠져나갔을 때만 입력이 돌아오지 않는 식의 버그가 생깁니다.

---

## 7. 자주 하는 실수

### 7.1 카메라 컴포넌트를 직접 찾는 코드

`FindObjectOfType<Camera>()`나 씬 오브젝트 이름 기반 탐색을 스킬, UI, 액터에 넣으면 씬 구조 변경에 취약합니다. 카메라 접근은 인터페이스와 디렉터를 통해 닫는 편이 좋습니다.

### 7.2 연출 종료를 타이머 하나에만 맡기는 구조

타이머 종료는 정상 경로일 뿐입니다. 상태가 강제로 종료되거나, 씬이 바뀌거나, 컷신이 스킵되는 경로에서도 핸들이 해제되어야 합니다.

### 7.3 흔들림 효과를 중첩 제한 없이 누적하는 구조

여러 타격이 한 프레임에 들어오면 흔들림이 과도하게 커질 수 있습니다. 동일 owner나 동일 카테고리 효과는 갱신, 누적, 무시 중 하나의 정책을 가져야 합니다.

### 7.4 시간 배율 복구 누락

카메라 연출이 타임 슬로우를 함께 쓰는 경우, 카메라 복구와 시간 복구가 함께 닫혀야 합니다. 타임 슬로우는 카메라 시스템 단독 책임으로 두기보다 연출 스코프에서 같이 관리하는 편이 안전합니다.

---

## 8. 디버깅 보조

카메라가 의도와 다르게 동작할 때는 아래 순서로 확인합니다.

1. 현재 활성 카메라 리그를 확인합니다.
2. 최고 우선순위 요청의 owner를 확인합니다.
3. 만료 시간이 지난 요청이 남아 있는지 확인합니다.
4. 입력 차단 이유가 카메라 모드와 일치하는지 확인합니다.
5. 씬 전환 시 `ClearAll()`이 호출되는지 확인합니다.
6. 시간 배율과 시야각이 기본값으로 복구되는지 확인합니다.

디버그 패널에는 최소한 현재 리그, 요청 owner 목록, 우선순위, 입력 허용 여부, 시간 배율을 표시하는 편이 좋습니다.

---

## 9. 쓰지 말아야 하는 경우

아주 작은 프로토타입에서 카메라가 하나이고 연출이 전혀 없다면 이 구조는 과할 수 있습니다. 하지만 스킬 줌, 피격 흔들림, 컷신, 대화 포커스 중 둘 이상이 들어간다면 초기부터 디렉터 구조를 두는 편이 이후 비용이 낮습니다.

---

## 10. 검증 체크리스트

- 스킬, UI, 상태 코드가 카메라 컴포넌트를 직접 조작하지 않는가
- 카메라 요청은 owner와 우선순위를 가지는가
- 모든 요청은 정상 종료와 강제 종료 경로에서 해제되는가
- 컷신과 대화 종료 시 입력 차단도 함께 복구되는가
- 씬 종료 시 `ClearAll()` 또는 동등한 정리 경로가 있는가
