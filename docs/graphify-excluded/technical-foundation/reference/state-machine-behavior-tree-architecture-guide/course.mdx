## [기술 기획안] 상태 머신 및 행동 트리 (State Machine & Behavior Tree)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 설계 목적

이 문서는 플레이어, 몬스터, 전투 액터의 행동을 `if`, `bool`, `switch` 조합으로 흩어 놓지 않고, **상태 전환 계약**으로 관리하기 위한 기준을 정의합니다.

실제 프로젝트에서 상태 관리는 입력 시스템 바로 다음에 문제가 커지는 영역입니다. 이동 중 공격, 공격 중 피격, 피격 중 넉백, 넉백 중 사망, 대화 중 이동 차단처럼 서로 다른 시스템이 같은 액터를 움직이려 하기 때문입니다. 이 기준이 없으면 액터 코드는 `isAttacking`, `isStunned`, `isGrounded`, `isInvincible`, `isDead` 같은 플래그 조합으로 빠르게 부풀고, 새 상태 하나를 추가할 때마다 기존 조건을 전부 다시 확인해야 합니다.

이 문서의 목적은 상태를 예쁘게 분류하는 것이 아닙니다. **어떤 상태에서 무엇을 허용하고, 어떤 전이가 더 우선하며, 누가 상태 전환을 요청할 수 있는지**를 명확히 하는 데 있습니다.

**이 문서가 바로 답하는 질문**

- 언제 단순 `enum`이나 `bool`이 아니라 FSM이 필요한가
- 플레이어 입력, 애니메이션, 물리, 스킬 실행은 상태 머신과 어떻게 연결되는가
- 피격, 넉백, 기절, 사망처럼 강제 상태는 어떤 우선순위로 처리해야 하는가
- 몬스터 AI에는 FSM과 Behavior Tree 중 무엇이 더 적합한가
- 상태가 많아질 때 계층형 FSM이나 Behavior Tree로 어디서 확장해야 하는가

---

## 2. 문제 정의

초기 캐릭터 컨트롤러는 보통 간단한 조건문으로 시작합니다. 지면에 있으면 점프하고, 입력이 있으면 이동하고, 공격 버튼을 누르면 공격합니다. 이 정도는 `Update()` 안에서도 충분히 읽힙니다.

문제는 상태가 서로 개입하기 시작할 때입니다. 공격 중에는 이동을 줄여야 하고, 점프 중에는 구르기를 막아야 하며, 피격은 대부분의 행동보다 우선되어야 합니다. 넉백이 들어오면 기존 이동 입력을 잠시 무시해야 하고, 사망 상태는 모든 행동을 종료해야 합니다. 여기에 애니메이션 이벤트, 콤보 입력 창, 상태이상, AI 판단까지 붙으면 조건은 한곳에 모이지 않고 여러 메서드로 흩어집니다.

이 상태에서 흔히 생기는 실패는 아래와 같습니다.

- 공격 중 피격됐는데 공격 후딜이 계속 적용된다.
- 기절 상태인데 이동 입력이 한 프레임 들어간다.
- 사망 후에도 AI 트리가 계속 Tick을 돈다.
- 애니메이션 상태와 코드 상태가 서로 다르다.
- 상태 플래그 조합이 많아져 새 상태 추가 비용이 커진다.

따라서 상태 시스템의 핵심 문제는 "상태 이름을 몇 개 만들 것인가"가 아니라, **전이 조건과 우선순위를 코드에서 한눈에 추적할 수 있게 만드는 것**입니다.

---

## 3. 설계 목표

- 액터의 주된 행동 mode를 명시적인 상태로 관리한다.
- 상태별 허용 입력, 금지 입력, 전이 조건을 한 지점에서 확인할 수 있게 한다.
- `OnEnter`, `Tick`, `FixedTick`, `OnExit` 수명주기를 통일한다.
- 강제 전이인 피격, 넉백, 기절, 사망은 일반 입력 전이보다 높은 우선순위로 처리한다.
- 애니메이션 상태 이름과 코드 상태를 무작정 동일시하지 않는다.
- 플레이어 FSM과 몬스터 AI 판단 구조를 분리하되, 액터 실행 API는 일관되게 유지한다.
- 상태 전환은 `Input System`, `SkillSystem`, `EventBus`, `SceneDI`와 충돌하지 않게 경계를 닫는다.

---

## 4. 범위와 비범위

### In Scope

- 플레이어와 몬스터 액터의 주 상태 FSM 설계
- 상태 전이 우선순위와 강제 상태 처리
- 애니메이션, 입력, 물리, 스킬 실행과의 연결 기준
- 계층형 FSM과 Behavior Tree 확장 기준
- 상태 디버깅과 검증 포인트

### Out of Scope

- 구체적인 몬스터 패턴 기획 전체
- 복잡한 AI blackboard 툴 제작
- 네트워크 롤백과 예측 상태 동기화
- Animator Controller 그래프 상세 제작
- 모든 버프/상태이상 계산 공식

이 문서는 상태 전환 프레임워크의 기준을 다룹니다. 몬스터별 세부 패턴, 난이도 곡선, 전투 밸런스는 별도 기획 데이터와 AI 데이터 설계에서 확장하는 편이 좋습니다.

## 5. 핵심 구조와 책임

### 5.1 책임 맵

- `StateMachine`: 현재 상태를 소유하고 전이를 수행한다.
- `State`: 특정 행동 mode의 진입, 갱신, 종료 규칙을 가진다.
- `Transition Request`: 입력, 피격, AI 판단 같은 전이 요청을 표현한다.
- `State Context`: 이동, 애니메이션, 스킬, 체력 같은 외부 기능에 접근하는 통로다.
- `Behavior Tree`: 몬스터 AI의 의사결정이 커질 때 어떤 전이 요청을 만들지 판단한다.
- `Actor`: 상태 머신을 Tick하고, 외부 시스템에서 받은 요청을 상태 머신에 전달한다.

`StateMachine`은 액터 전체를 대체하지 않습니다. 액터가 가진 물리, 애니메이션, 스킬 실행, HP 관리 기능을 상태 객체가 직접 소유하는 것도 아닙니다. 상태는 "지금 어떤 행동 mode인가"와 "다음에 어떤 mode로 갈 수 있는가"를 관리하고, 실제 기능 실행은 context를 통해 필요한 서비스에 위임합니다.

### 5.2 상태로 만들 것과 만들지 않을 것

상태로 만들 기준은 단순합니다. **허용 행동과 전이 규칙이 실질적으로 달라지는가**를 보면 됩니다.

상태로 만들기 좋은 예시는 아래입니다.

- `Idle`: 이동, 점프, 공격, 상호작용을 받을 수 있다.
- `Move`: 이동 방향을 반영하고, 공격과 점프 전이가 가능하다.
- `Attack`: 이동 입력 일부 제한, 콤보 입력 창, 피격 우선순위가 있다.
- `HitStun`: 입력 무시, 짧은 경직, 넉백과 사망 전이가 있다.
- `Dead`: 대부분의 Tick과 입력을 종료한다.

반대로 아래는 상태보다 별도 데이터나 태그가 더 적합할 수 있습니다.

- 독, 화상, 버프 같은 동시에 겹치는 속성
- 무기 장착 여부처럼 다른 상태와 병렬로 존재하는 정보
- 이동 속도 배율처럼 상태 전체 규칙을 바꾸지 않는 수치
- 무적 여부처럼 상태에 붙는 보조 조건

겹쳐 존재하는 속성을 전부 상태 이름으로 밀어 넣으면 `PoisonedArmedRunningAttack` 같은 조합 폭발이 생깁니다. FSM은 주 행동 mode를 관리하고, 독립 속성은 태그, 버프, 컴포넌트, 별도 레이어로 분리하는 편이 안전합니다.

## 6. FSM과 Behavior Tree 선택 기준

### 6.1 FSM이 적합한 경우

FSM은 현재 상태와 다음 전이가 명확한 액터 제어에 적합합니다.

- 플레이어 이동, 점프, 공격, 피격, 사망
- 보스 페이즈별 큰 상태
- UI 패널 단계
- 단순 몬스터의 순찰, 추적, 공격, 복귀

FSM의 장점은 전이가 명확하다는 점입니다. "현재 상태에서 어떤 상태로 갈 수 있는가"가 보이기 때문에 애니메이션, 입력, 피격 같은 전투 흐름을 통제하기 좋습니다.

### 6.2 Behavior Tree가 적합한 경우

Behavior Tree는 의사결정 조건이 많고 우선순위 평가가 반복되는 AI에 적합합니다.

- 시야 안에 플레이어가 있으면 추적한다.
- 체력이 낮으면 후퇴하거나 회복 패턴을 선택한다.
- 스킬 쿨다운과 거리 조건에 따라 다른 공격을 고른다.
- 전투 중 환경 오브젝트나 소환수를 고려한다.

Behavior Tree의 역할은 액터를 직접 움직이는 것이 아니라, **어떤 행동 상태로 전이할지 결정하는 판단 레이어**에 가깝습니다. 실제 이동, 공격, 피격, 사망은 FSM 상태가 수행하고, Behavior Tree는 `Chase`, `Attack`, `Retreat` 같은 전이 요청을 만들도록 두는 편이 경계가 깔끔합니다.

### 6.3 둘을 함께 쓰는 기준

몬스터 AI가 커질수록 Behavior Tree가 현재 행동을 직접 실행하려는 유혹이 생깁니다. 하지만 실행까지 트리에 넣으면 상태 수명주기와 애니메이션 종료 처리가 흐려집니다.

권장 구조는 아래입니다.

```text
Behavior Tree
  -> 지금 무엇을 해야 하는지 판단
  -> 상태 전이 요청 생성

FSM
  -> 실제 상태 진입, 실행, 종료
  -> 애니메이션, 이동, 스킬, 피격 처리
```

이 구조를 유지하면 AI 판단을 바꿔도 액터 실행 규약은 유지됩니다.

## 7. 전이 우선순위

상태 전이는 모두 같은 무게가 아닙니다. 입력 전이보다 전투 강제 전이가 우선되어야 하는 경우가 많습니다.

권장 우선순위는 아래에 가깝습니다.

1. `Dead`
2. `HitStun` 또는 `Knockback`
3. `Stun`, `Freeze`, `Root` 같은 행동 제한 상태
4. `Attack`, `Skill`, `Dodge` 같은 명시 행동
5. `Move`, `Idle` 같은 기본 행동

예를 들어 공격 버튼과 피격 이벤트가 같은 프레임에 들어왔다면, 일반적으로 피격이 우선입니다. 사망 조건이 충족됐다면 넉백이나 공격 후딜보다 사망이 우선입니다. 이 우선순위가 없으면 프레임 순서에 따라 결과가 달라지고, 버그가 재현되지 않는 형태로 남습니다.

---

## 8. 런타임 흐름

상태 시스템은 보통 아래 순서로 조립됩니다.

1. `SceneDI`가 액터와 필요한 상태 context를 준비한다.
2. 액터가 `StateMachine`을 생성하고 기본 상태를 등록한다.
3. 입력 시스템, AI 판단기, 전투 시스템이 액터에 전이 요청을 보낼 수 있게 연결된다.
4. 액터 활성화 시 기본 상태인 `Idle` 또는 AI 초기 상태로 진입한다.
5. 매 프레임 `Tick`, 물리 프레임에서 `FixedTick`을 호출한다.
6. 입력, 애니메이션, 피격, AI 판단에 따라 전이 요청이 들어온다.
7. 상태 머신은 우선순위와 허용 조건을 확인하고 상태를 변경한다.
8. 씬 종료 또는 액터 파괴 시 현재 상태의 `OnExit`를 호출하고 구독을 해지한다.

중요한 점은 상태 머신이 `Awake`나 `Start`에서 바로 실행되지 않아야 한다는 것입니다. `SceneDI` 기준으로 조립과 주입이 끝난 뒤 활성화되어야 입력, 애니메이션, 스킬 서비스가 빈 상태로 접근되는 문제를 막을 수 있습니다.

## 9. 인접 시스템 경계

### 9.1 Input System

입력 시스템은 `JumpPressed`, `AttackPressed`, `MoveInput` 같은 정리된 입력을 제공합니다. 상태 머신은 현재 상태에서 그 입력을 받을지 결정합니다.

입력 시스템이 "지금 공격 가능한가"까지 판단하기 시작하면 `SkillSystem`과 상태 머신의 책임이 섞입니다. 입력은 요청이고, 상태 머신은 현재 mode 기준의 허용 여부를 판단합니다.

### 9.2 SkillSystem

`SkillSystem`은 스킬 데이터, 쿨다운, 자원, 효과 실행을 책임집니다. 상태 머신은 스킬 실행을 시작할 수 있는 상태인지, 스킬 중 이동과 피격을 어떻게 처리할지 결정합니다.

예를 들어 `AttackState`는 `SkillCaster.TryCast(skillId)`를 호출할 수 있지만, 피해량 계산이나 버프 적용을 직접 품으면 안 됩니다.

### 9.3 Animator

Animator는 시각 상태를 표현합니다. 코드 상태와 Animator 상태를 완전히 동일하게 맞추려 하면 관리가 어려워질 수 있습니다.

권장 기준은 아래입니다.

- 코드 FSM: 게임 규칙과 전이 권한을 소유한다.
- Animator: 재생 상태와 블렌딩을 담당한다.
- 브리지: 코드 상태 진입 시 파라미터를 설정하고, 필요한 완료 신호만 상태 머신에 전달한다.

### 9.4 EventBus

피격, 사망, 타겟 변경 같은 사실은 이벤트로 외부에 알릴 수 있습니다. 하지만 상태 전이 자체를 전역 이벤트로만 처리하면 추적이 어려워집니다. 액터 내부의 직접 전이 요청과 외부 알림 이벤트를 구분해야 합니다.

## 10. 코어 구조 예시

Reference Example: 상태 인터페이스와 전이 요청

```csharp
public enum StatePriority
{
    Base = 0,
    Action = 10,
    CrowdControl = 20,
    Hit = 30,
    Dead = 100
}

public readonly struct StateChangeRequest
{
    public readonly string StateId;
    public readonly StatePriority Priority;

    public StateChangeRequest(string stateId, StatePriority priority)
    {
        StateId = stateId;
        Priority = priority;
    }
}

public interface IActorState
{
    string Id { get; }
    StatePriority Priority { get; }

    bool CanEnter(StateChangeRequest request);
    void OnEnter();
    void Tick(float deltaTime);
    void FixedTick(float fixedDeltaTime);
    void OnExit();
}
```

이 구조의 핵심은 상태 전이를 단순 문자열 호출로 끝내지 않는다는 점입니다. 전이 요청에 우선순위를 포함하면 같은 프레임에 여러 요청이 들어와도 어떤 요청이 이겨야 하는지 판단할 수 있습니다.

---

## 11. 실패 경로와 엣지 케이스

### 11.1 `OnExit` 누락

공격 상태에서 이동 제한을 걸었는데 `OnExit`에서 풀지 않으면, 다음 상태에서도 계속 이동이 막힐 수 있습니다. 상태가 획득한 임시 권한은 상태가 종료될 때 반드시 정리해야 합니다.

### 11.2 상태 전이 중 재전이

`OnEnter` 안에서 다시 상태 전이를 호출하면 전이 순서가 꼬일 수 있습니다. 전이 중에는 요청을 큐에 넣거나, 다음 Tick에서 처리하는 규칙을 두는 편이 안전합니다.

### 11.3 Animator 상태와 코드 상태 불일치

애니메이션은 `Attack`인데 코드 FSM은 이미 `Idle`이면 입력 허용과 시각 표현이 어긋납니다. 애니메이션 완료 신호를 어떤 방식으로 받을지 명확히 해야 합니다.

### 11.4 모든 플래그를 상태로 만드는 경우

버프, 장비, 지형 효과처럼 동시에 겹치는 속성까지 상태로 만들면 상태 수가 폭발합니다. 주 행동 mode와 병렬 속성은 분리해야 합니다.

### 11.5 AI 판단과 실행이 섞이는 경우

Behavior Tree 노드가 직접 애니메이션과 이동을 오래 붙잡으면, 피격이나 사망 같은 강제 전이가 늦어집니다. AI 트리는 판단을 만들고, 실행은 FSM 상태가 맡도록 경계를 둡니다.

---

## 12. 기획 및 운영 우려사항

상태 시스템은 기획 변경과 매우 가깝습니다. 공격 중 구르기 가능 여부, 피격 중 스킬 취소 가능 여부, 보스 패턴의 강제 전이 여부는 전투 감각을 크게 바꿉니다.

기획자가 비교적 안전하게 조정할 수 있는 영역은 아래입니다.

- 상태별 허용 입력 목록
- 공격 상태의 입력 버퍼 허용 시간
- 경직, 넉백, 회복 시간
- 몬스터 AI의 판단 조건 수치

개발 협의가 필요한 변경은 아래입니다.

- 상태 우선순위 체계 변경
- 새로운 상태 레이어 추가
- Behavior Tree와 FSM 경계 변경
- 애니메이션 완료 신호 방식 변경
- 상태 동기화가 필요한 네트워크 전투 구조 추가

상태 변경은 코드 구조와 전투 감각을 동시에 건드립니다. 데이터로 노출할 항목과 코드 계약으로 닫을 항목을 구분해야 안정적으로 운영할 수 있습니다.

## 13. 디버깅 및 검증 포인트

- 현재 상태와 이전 상태를 런타임에서 확인할 수 있는가
- 마지막 전이 요청과 거절 사유를 볼 수 있는가
- `OnEnter`와 `OnExit`가 항상 쌍으로 호출되는가
- 피격, 넉백, 사망 전이가 입력 전이보다 우선되는가
- 애니메이션 완료 신호가 상태 전이와 일관되게 연결되어 있는가
- Behavior Tree가 실행을 직접 오래 붙잡지 않고 전이 요청만 만드는가

- 상태로 만들 항목과 태그/버프로 둘 항목이 구분되어 있는가
- 전이 우선순위가 문서와 코드에 드러나는가
- 입력, 스킬, 애니메이션, AI의 책임 경계가 충돌하지 않는가
- 상태 전이 중 재전이와 `OnExit` 누락을 방지하는 규칙이 있는가
- 새 상태를 추가할 때 어느 파일과 어느 등록 지점을 수정해야 하는지 보이는가

## [개발 가이드] 상태 머신 및 행동 트리 (State Machine & Behavior Tree)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 읽는 순서

이 가이드는 상태 머신을 실제 액터 코드에 붙이는 방법을 설명합니다. 핵심은 상태 클래스를 많이 만드는 것이 아니라, **전이 요청, 우선순위, 상태 수명주기, 애니메이션/입력/스킬 연결**을 한 흐름으로 고정하는 데 있습니다.

읽는 순서는 아래가 자연스럽습니다.

1. 공통 `StateMachine` 코어를 먼저 봅니다.
2. 플레이어 상태 예제로 입력과 애니메이션 연결을 봅니다.
3. 피격과 사망 같은 강제 전이를 봅니다.
4. 몬스터 AI가 필요할 때 Behavior Tree가 어떤 전이 요청을 만드는지 봅니다.

---

## 2. 이 가이드가 전제하는 계약

- 액터는 하나의 주 행동 상태를 가진다.
- 상태는 `OnEnter`, `Tick`, `FixedTick`, `OnExit` 수명주기를 따른다.
- 전이는 요청으로 들어오고, 상태 머신이 우선순위와 허용 여부를 판단한다.
- 입력 시스템은 요청을 만들고, 상태 머신은 현재 상태에서 허용할지 판단한다.
- 스킬 실행, 피해 계산, 애니메이션 재생은 상태가 직접 소유하지 않고 context로 위임한다.
- Behavior Tree는 AI 판단을 맡고, 실제 실행은 FSM 상태로 넘긴다.

이 계약이 없으면 상태 객체가 늘어나도 결국 조건문이 다른 파일로 이동했을 뿐입니다.

## 3. 코어 상태 머신 코드

Reference Example: `StateMachine`

```csharp
using System;
using System.Collections.Generic;

public enum StatePriority
{
    Base = 0,
    Action = 10,
    CrowdControl = 20,
    Hit = 30,
    Dead = 100
}

public readonly struct StateChangeRequest
{
    public readonly string StateId;
    public readonly StatePriority Priority;

    public StateChangeRequest(string stateId, StatePriority priority)
    {
        StateId = stateId;
        Priority = priority;
    }
}

public interface IActorState
{
    string Id { get; }
    StatePriority Priority { get; }

    bool CanEnter(StateChangeRequest request);
    void OnEnter();
    void Tick(float deltaTime);
    void FixedTick(float fixedDeltaTime);
    void OnExit();
}

public sealed class StateMachine
{
    private readonly Dictionary<string, IActorState> _states = new();
    private bool _isChanging;

    public IActorState Current { get; private set; }

    public void Register(IActorState state)
    {
        _states.Add(state.Id, state);
    }

    public void Start(string initialStateId)
    {
        if (!_states.TryGetValue(initialStateId, out var initialState))
        {
            throw new InvalidOperationException($"State not found: {initialStateId}");
        }

        Current = initialState;
        Current.OnEnter();
    }

    public bool TryChange(StateChangeRequest request)
    {
        if (_isChanging)
        {
            return false;
        }

        if (!_states.TryGetValue(request.StateId, out var next))
        {
            return false;
        }

        if (Current != null && request.Priority < Current.Priority)
        {
            return false;
        }

        if (!next.CanEnter(request))
        {
            return false;
        }

        _isChanging = true;
        Current?.OnExit();
        Current = next;
        Current.OnEnter();
        _isChanging = false;

        return true;
    }

    public void Tick(float deltaTime)
    {
        Current?.Tick(deltaTime);
    }

    public void FixedTick(float fixedDeltaTime)
    {
        Current?.FixedTick(fixedDeltaTime);
    }
}
```

이 코드는 최소 코어입니다. 실무에서는 전이 거절 사유, 전이 로그, 큐 처리, 상태 팩토리까지 붙일 수 있습니다. 다만 처음부터 크게 만들기보다 이 계약이 프로젝트에 맞는지 검증한 뒤 확장하는 편이 좋습니다.

## 5. 기본 상태 예시

### 5.1 Idle 상태

```csharp
using UnityEngine;

public sealed class IdleState : IActorState
{
    private readonly PlayerStateContext _context;
    private readonly StateMachine _stateMachine;

    public IdleState(PlayerStateContext context, StateMachine stateMachine)
    {
        _context = context;
        _stateMachine = stateMachine;
    }

    public string Id => "Idle";
    public StatePriority Priority => StatePriority.Base;

    public bool CanEnter(StateChangeRequest request)
    {
        return true;
    }

    public void OnEnter()
    {
        _context.PlayAnimation("Idle");
    }

    public void Tick(float deltaTime)
    {
        if (_context.Input.Move.sqrMagnitude > 0.01f)
        {
            _stateMachine.TryChange(new StateChangeRequest("Move", StatePriority.Base));
            return;
        }

        if (_context.Input.AttackPressed)
        {
            _stateMachine.TryChange(new StateChangeRequest("Attack", StatePriority.Action));
        }
    }

    public void FixedTick(float fixedDeltaTime) { }
    public void OnExit() { }
}
```

`IdleState`는 기본 입력을 받아 다른 상태로 넘깁니다. 이동과 공격을 실제로 처리하는 것은 각각 `MoveState`, `AttackState`입니다.

### 5.2 Move 상태

```csharp
using UnityEngine;

public sealed class MoveState : IActorState
{
    private readonly PlayerStateContext _context;
    private readonly StateMachine _stateMachine;
    private readonly float _moveSpeed;

    public MoveState(PlayerStateContext context, StateMachine stateMachine, float moveSpeed)
    {
        _context = context;
        _stateMachine = stateMachine;
        _moveSpeed = moveSpeed;
    }

    public string Id => "Move";
    public StatePriority Priority => StatePriority.Base;

    public bool CanEnter(StateChangeRequest request)
    {
        return true;
    }

    public void OnEnter()
    {
        _context.PlayAnimation("Run");
    }

    public void Tick(float deltaTime)
    {
        if (_context.Input.Move.sqrMagnitude <= 0.01f)
        {
            _stateMachine.TryChange(new StateChangeRequest("Idle", StatePriority.Base));
            return;
        }

        if (_context.Input.AttackPressed)
        {
            _stateMachine.TryChange(new StateChangeRequest("Attack", StatePriority.Action));
        }
    }

    public void FixedTick(float fixedDeltaTime)
    {
        var input = _context.Input.Move;
        var direction = new Vector3(input.x, 0f, input.y).normalized;
        _context.Move(direction * _moveSpeed, fixedDeltaTime);
    }

    public void OnExit() { }
}
```

입력은 `Update` 흐름에서 읽고, 실제 물리 이동은 `FixedTick` 쪽에서 처리할 수 있습니다. 이 분리는 `Input System` 문서의 입력 캡처 흐름과도 맞습니다.

### 5.3 Attack 상태

```csharp
public sealed class AttackState : IActorState
{
    private readonly PlayerStateContext _context;
    private readonly StateMachine _stateMachine;
    private float _elapsed;
    private readonly float _duration;

    public AttackState(PlayerStateContext context, StateMachine stateMachine, float duration)
    {
        _context = context;
        _stateMachine = stateMachine;
        _duration = duration;
    }

    public string Id => "Attack";
    public StatePriority Priority => StatePriority.Action;

    public bool CanEnter(StateChangeRequest request)
    {
        return _context.SkillCaster.CanCast("BasicAttack");
    }

    public void OnEnter()
    {
        _elapsed = 0f;
        _context.PlayAnimation("Attack");
        _context.SkillCaster.TryCast("BasicAttack");
    }

    public void Tick(float deltaTime)
    {
        _elapsed += deltaTime;

        if (_elapsed >= _duration)
        {
            _stateMachine.TryChange(new StateChangeRequest("Idle", StatePriority.Action));
        }
    }

    public void FixedTick(float fixedDeltaTime) { }
    public void OnExit() { }
}
```

`AttackState`는 공격 상태의 시작과 종료를 관리하지만, 피해량 계산이나 버프 적용은 `SkillCaster`에 맡깁니다. 이렇게 해야 `SkillSystem`과 상태 머신의 책임이 분리됩니다.

public sealed class PlayerActorStateDriver : MonoBehaviour

## 8. Behavior Tree 최소 구조

몬스터 AI 판단이 커지면 Behavior Tree를 상태 머신 위에 얹을 수 있습니다.

Reference Example: Behavior Tree core

```csharp
public enum BehaviorStatus
{
    Success,
    Failure,
    Running
}

public interface IBehaviorNode
{
    BehaviorStatus Tick();
}

public sealed class SequenceNode : IBehaviorNode
{
    private readonly IBehaviorNode[] _children;

    public SequenceNode(params IBehaviorNode[] children)
    {
        _children = children;
    }

    public BehaviorStatus Tick()
    {
        foreach (var child in _children)
        {
            var status = child.Tick();

            if (status != BehaviorStatus.Success)
            {
                return status;
            }
        }

        return BehaviorStatus.Success;
    }
}

public sealed class SelectorNode : IBehaviorNode
{
    private readonly IBehaviorNode[] _children;

    public SelectorNode(params IBehaviorNode[] children)
    {
        _children = children;
    }

    public BehaviorStatus Tick()
    {
        foreach (var child in _children)
        {
            var status = child.Tick();

            if (status != BehaviorStatus.Failure)
            {
                return status;
            }
        }

        return BehaviorStatus.Failure;
    }
}
```

`Sequence`는 모든 조건이 성공해야 성공하고, `Selector`는 성공 가능한 첫 행동을 선택합니다. 여기까지는 판단 구조이고, 실제 이동과 공격 실행은 FSM 상태로 넘깁니다.

### 조건과 행동 노드

```csharp
using System;

public sealed class ConditionNode : IBehaviorNode
{
    private readonly Func<bool> _condition;

    public ConditionNode(Func<bool> condition)
    {
        _condition = condition;
    }

    public BehaviorStatus Tick()
    {
        return _condition() ? BehaviorStatus.Success : BehaviorStatus.Failure;
    }
}

public sealed class ChangeStateNode : IBehaviorNode
{
    private readonly StateMachine _stateMachine;
    private readonly StateChangeRequest _request;

    public ChangeStateNode(StateMachine stateMachine, StateChangeRequest request)
    {
        _stateMachine = stateMachine;
        _request = request;
    }

    public BehaviorStatus Tick()
    {
        return _stateMachine.TryChange(_request)
            ? BehaviorStatus.Success
            : BehaviorStatus.Failure;
    }
}
```

이 노드는 상태 전이 요청만 만듭니다. `ChangeStateNode`가 직접 이동 루프나 공격 애니메이션 완료 대기를 품기 시작하면 FSM과 역할이 섞입니다.

## 9. 몬스터 AI에 붙이는 방법

```csharp
public sealed class EnemyBrain
{
    private readonly IBehaviorNode _root;

    public EnemyBrain(EnemySensors sensors, StateMachine stateMachine)
    {
        _root = new SelectorNode(
            new SequenceNode(
                new ConditionNode(() => sensors.IsDead),
                new ChangeStateNode(stateMachine, new StateChangeRequest("Dead", StatePriority.Dead))
            ),
            new SequenceNode(
                new ConditionNode(() => sensors.CanAttackTarget),
                new ChangeStateNode(stateMachine, new StateChangeRequest("Attack", StatePriority.Action))
            ),
            new SequenceNode(
                new ConditionNode(() => sensors.CanSeeTarget),
                new ChangeStateNode(stateMachine, new StateChangeRequest("Chase", StatePriority.Base))
            ),
            new ChangeStateNode(stateMachine, new StateChangeRequest("Patrol", StatePriority.Base))
        );
    }

    public void Tick()
    {
        _root.Tick();
    }
}
```

`EnemyBrain`은 판단만 수행합니다. `ChaseState`, `AttackState`, `PatrolState`는 FSM 쪽에 따로 존재하고, 실제 이동과 애니메이션은 각 상태가 처리합니다.

## 10. SceneDI와 연결하기

`SceneDI`에서 액터, 입력, 스킬, AI 서비스를 조립한 뒤 상태 머신을 시작합니다.

```csharp
using Cysharp.Threading.Tasks;
using UnityEngine;

public sealed class CombatSceneDirector : BaseSceneDirectorAsync
{
    [SerializeField] private PlayerActorStateDriver _player;
    [SerializeField] private EnemyActorStateDriver[] _enemies;

    protected override async UniTask LoadAsync()
    {
        _player.Initialize();

        foreach (var enemy in _enemies)
        {
            enemy.Initialize();
        }

        await UniTask.CompletedTask;
    }
}
```

상태 머신은 씬 조립이 끝난 뒤 시작되어야 합니다. 특히 입력 서비스와 스킬 데이터가 아직 준비되지 않은 상태에서 `IdleState`가 시작되면 첫 Tick부터 누락 참조가 발생할 수 있습니다.

## 11. 디버깅 보조

상태 머신은 반드시 현재 상태와 최근 전이 기록을 볼 수 있어야 합니다.

```csharp
public readonly struct StateTransitionLog
{
    public readonly string From;
    public readonly string To;
    public readonly StatePriority Priority;

    public StateTransitionLog(string from, string to, StatePriority priority)
    {
        From = from;
        To = to;
        Priority = priority;
    }
}
```

실무에서는 에디터 전용 오버레이에 아래 정보를 표시하면 좋습니다.

- 현재 상태
- 이전 상태
- 마지막 전이 요청
- 전이 거절 사유
- 현재 Behavior Tree에서 성공한 노드

## 12. 자주 하는 실수

### 실수 1. Animator 상태를 코드 상태로 그대로 쓰는 것

Animator는 시각 표현이고, FSM은 게임 규칙입니다. 이름이 같을 수는 있지만 책임은 다릅니다.

### 실수 2. 모든 버프와 태그를 상태로 만드는 것

동시에 겹치는 속성은 상태보다 버프, 태그, 컴포넌트가 더 적합합니다.

### 실수 3. `OnExit` 정리를 빼먹는 것

이동 제한, 무적, 입력 차단 같은 임시 변경은 상태 종료 시 반드시 정리해야 합니다.

### 실수 4. Behavior Tree가 실행을 직접 오래 붙잡는 것

AI 판단은 트리가 맡고, 실제 실행은 FSM 상태가 맡는 편이 강제 전이를 처리하기 쉽습니다.

### 실수 5. 상태 전이를 전역 이벤트로만 처리하는 것

외부 알림과 내부 전이는 구분해야 합니다. 상태 머신 내부 전이는 추적 가능한 직접 요청으로 두는 편이 좋습니다.

## 13. 검증 체크리스트

- 같은 프레임에 공격 입력과 피격이 들어왔을 때 피격이 우선되는가
- 사망 상태 이후 입력, AI, 스킬 Tick이 멈추는가
- `OnEnter`와 `OnExit` 로그가 쌍으로 남는가
- 새 상태 추가 시 등록 지점과 전이 요청 지점이 분명한가
- Behavior Tree는 판단만 하고 실제 실행은 FSM 상태가 맡는가
- `SceneDI` 조립 이전에 상태 머신이 시작되지 않는가
