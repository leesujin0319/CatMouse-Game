## [기술 기획안] 비동기 리소스 및 메모리 관리 (Addressables Pooling)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 핵심 관점

이 문서는 `Addressables` 기반 비동기 로딩과 오브젝트 풀링을 한 구조 안에서 어떻게 나눠야 하는지 정의합니다. 핵심은 "Addressables로 다 해결한다"가 아닙니다. **원본 에셋의 메모리 수명**과 **복제 인스턴스의 런타임 수명**을 같은 방식으로 다루지 않는 데 있습니다.

그래서 이 문서는 두 개의 트랙으로 구조를 나눕니다.

- `Track 1 (Non-Pooled)`: 오디오, 텍스처, `ScriptableObject` 같은 일반 에셋 로딩과 해제
- `Track 2 (Pooled)`: 몬스터, 투사체, 이펙트 같은 복제 객체의 생성과 재사용

`SceneDI`는 이 두 트랙이 **언제 로드되고 언제 예열되는지**를 통제하고, 이 문서는 각 트랙이 **어떻게 메모리를 소유하고 언제 반환하는지**를 정의합니다.

**이 문서가 바로 답하는 질문**

- 어떤 자원은 단순 캐싱으로 충분하고, 어떤 자원은 풀링해야 하는가
- `Addressables.Release`는 누가 언제 호출해야 하는가
- 원본 에셋과 복제 인스턴스의 책임을 왜 분리해야 하는가
- 로딩 씬에서 무엇을 예열하고, 전투 중에는 무엇을 재사용해야 하는가

---

## 2. 문제 정의

`Addressables`를 도입해도 메모리 문제는 자동으로 사라지지 않습니다. 가장 흔한 실패는 두 가지입니다.

첫째, 원본 에셋의 수명을 제대로 반납하지 않는 경우입니다. `AsyncOperationHandle`을 해제하지 않으면 씬이 바뀌어도 메모리가 남습니다. 둘째, 복제 객체의 수명을 에셋 수명과 같은 방식으로 다루는 경우입니다. 전투 중 반복 생성되는 객체를 매번 `Instantiate`와 `Destroy`로 처리하면 프레임 스파이크와 자료구조 오염이 같이 발생합니다.

문제의 본질은 "비동기로 읽느냐"가 아니라, **원본 에셋과 복제 객체를 같은 생명주기로 다루고 있느냐**에 있습니다. 이 둘은 분리되어야 합니다. 원본 에셋은 로드와 릴리즈가 중요하고, 복제 객체는 생성 비용과 재사용 전략이 중요합니다.

---

## 3. 설계 목표

- 원본 에셋의 메모리 수명과 복제 객체의 런타임 수명을 분리한다.
- 일반 에셋은 캐싱과 `Release` 기준을 명확히 한다.
- 반복 생성 객체는 풀링을 통해 프레임 스파이크를 줄인다.
- 로딩 씬에서 예열 가능한 작업과 전투 중 즉시 임대해야 하는 작업을 나눈다.
- Race condition, double release, 메인 스레드 위반 같은 실패 경로를 구조적으로 방어한다.

---

## 4. 범위와 비범위

### In Scope

- `Addressables.LoadAssetAsync` 기반 일반 에셋 로딩
- `Addressables.Release` 호출 규칙
- 원본 에셋 캐시와 로딩 중 작업 병합
- 풀링 대상 객체의 예열, 임대, 반환 규칙
- `SceneDI`와 연결되는 로딩/예열 시점

### Out of Scope

- 씬 로딩 UI 설계 자체
- 게임별 풀 크기 튜닝 수치
- 개별 무기나 몬스터의 전투 로직
- 특정 CDN, 번들 그룹 운영 정책 상세

---

## 5. 두 개의 트랙

### 5.1 Track 1: 일반 에셋 로딩

일반 에셋은 메모리에 원본 하나만 올라가면 충분한 경우가 많습니다. 예를 들어 배경음, 아이콘, `ScriptableObject`, 텍스처는 복제 인스턴스를 여러 개 만들 필요보다 **언제 로드하고 언제 해제하느냐**가 더 중요합니다.

### 5.2 Track 2: 복제 객체 풀링

몬스터, 투사체, 이펙트처럼 런타임 중 자주 생성되는 객체는 원본 프리팹을 한 번 로드한 뒤, 실제 전투에서는 풀에서 꺼내고 돌려보내는 구조가 더 적합합니다. 여기서 중요한 것은 원본 에셋의 수명과, 그 원본으로 만든 복제 객체의 수명을 분리하는 것입니다.

---

## 6. 코어 구조 예시

Reference Example: `AsyncResourceManager`, `AsyncPoolManager`

```csharp
using Cysharp.Threading.Tasks;
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.AddressableAssets;
using UnityEngine.Pool;

public class AsyncResourceManager : MonoBehaviour
{
    private readonly Dictionary<string, AsyncOperationHandle> _handles = new();
    private readonly Dictionary<string, UniTask<Object>> _loadTasks = new();

    public async UniTask<T> LoadAssetAsync<T>(AssetReference assetRef) where T : Object
    {
        var key = assetRef.AssetGUID;

        if (_handles.TryGetValue(key, out var cachedHandle))
        {
            return (T)cachedHandle.Result;
        }

        if (_loadTasks.TryGetValue(key, out var pendingTask))
        {
            return (T)await pendingTask;
        }

        async UniTask<Object> LoadInternalAsync()
        {
            var handle = assetRef.LoadAssetAsync<T>();
            await handle.Task;
            _handles[key] = handle;
            _loadTasks.Remove(key);
            return handle.Result;
        }

        _loadTasks[key] = LoadInternalAsync();
        return (T)await _loadTasks[key];
    }

    public void ReleaseAsset(AssetReference assetRef)
    {
        var key = assetRef.AssetGUID;

        if (_handles.TryGetValue(key, out var handle))
        {
            Addressables.Release(handle);
            _handles.Remove(key);
        }
    }
}

public class AsyncPoolManager : MonoBehaviour
{
    private readonly Dictionary<string, ObjectPool<GameObject>> _pools = new();

    public async UniTask<GameObject> SpawnAsync(AssetReference assetRef, Vector3 position)
    {
        var key = assetRef.AssetGUID;

        if (!_pools.TryGetValue(key, out var pool))
        {
            var prefab = await AsyncResourceManager.Instance.LoadAssetAsync<GameObject>(assetRef);
            pool = new ObjectPool<GameObject>(
                createFunc: () => Instantiate(prefab),
                actionOnGet: obj =>
                {
                    obj.transform.position = position;
                    obj.SetActive(true);
                },
                actionOnRelease: obj => obj.SetActive(false),
                actionOnDestroy: Destroy,
                collectionCheck: true,
                defaultCapacity: 20
            );
            _pools[key] = pool;
        }

        return pool.Get();
    }
}
```

이 구조에서 `AsyncResourceManager`는 원본 에셋을, `AsyncPoolManager`는 복제 객체를 책임집니다. 두 매니저가 서로 다른 수명을 다루기 때문에, 메모리 누수와 인스턴스화 스파이크를 한 곳에서 동시에 처리하려 들지 않아도 됩니다.

---

## 7. SceneDI와의 연결

이 구조는 `SceneDI`의 로딩 파이프라인과 직접 연결됩니다.

- SceneDI는 어떤 에셋을 먼저 로드할지 정합니다.
- SceneDI는 로딩 화면에서 어떤 풀을 미리 예열할지 정합니다.
- `AsyncResourceManager`는 원본 에셋 수명을 관리합니다.
- `AsyncPoolManager`는 전투 중 즉시 임대와 반환을 처리합니다.

예를 들어 월드 번들, 전투용 이펙트, 주요 적 프리팹 예열은 `LoadingSceneDirector`나 `GameplaySceneDirector`가 로딩 단계에서 호출할 수 있습니다. 반면 전투 도중의 실제 발사와 스폰은 이미 예열된 풀을 통해 처리하는 편이 맞습니다.

---

## 8. 성능과 트레이드오프

### 8.1 얻는 것

- 원본 에셋 로딩 중복을 줄일 수 있습니다.
- 전투 중 `Instantiate`/`Destroy` 스파이크를 줄일 수 있습니다.
- Race condition과 double release를 구조적으로 막기 쉬워집니다.

### 8.2 주의할 점

- 풀링 대상이 아닌 자원을 과하게 풀링하면 구조만 복잡해집니다.
- 예열 수치를 과하게 잡으면 로딩 시간이 늘어납니다.
- 메모리 반납 시점이 불명확하면 Track 1과 Track 2가 서로 책임을 미루게 됩니다.

---

## 9. 실패 경로와 안티 패턴

### 9.1 `Release` 누락

일반 에셋을 로드한 뒤 씬 종료나 사용 종료 시 `Addressables.Release`를 호출하지 않으면 메모리가 남습니다.

### 9.2 풀링 대상 객체의 직접 `Destroy`

풀링 객체를 매니저 밖에서 직접 파괴하면 자료구조가 오염되고 다음 임대에서 문제가 생깁니다.

### 9.3 중복 로딩 레이스

같은 에셋에 대해 동시에 여러 `LoadAssetAsync`가 들어오면 불필요한 다운로드와 메모리 중복이 생길 수 있습니다. 로딩 중 작업 캐싱이 필요합니다.

### 9.4 메인 스레드 위반

백그라운드 작업에서 유니티 객체 생성과 활성화를 바로 시도하면 문제가 생깁니다. 실제 스폰과 활성화는 메인 스레드에서 이뤄져야 합니다.

---

## 10. 검증 포인트

- 일반 에셋과 풀링 객체의 책임이 분리되어 있는가
- 같은 에셋의 중복 로드가 병합되는가
- 씬 종료 시 일반 에셋 핸들이 제대로 반납되는가
- 풀링 객체가 `Destroy` 대신 반환 경로를 타는가
- SceneDI가 예열 시점과 전투 시점을 분리해 호출하고 있는가

---

## 11. 리뷰 체크리스트

- Track 1과 Track 2의 구분이 명확한가
- 로딩과 반환 책임 주체가 문서에서 닫혀 있는가
- Race condition과 double release 방어가 있는가
- SceneDI와의 연결 시점이 명확한가
- 핫패스에서 직접 생성과 파괴가 남아 있지 않은가

## [개발 가이드] 비동기 리소스 및 메모리 관리 (Addressables Pooling)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 읽는 순서

이 가이드는 일반 에셋 로딩과 복제 객체 풀링을 실제 프로젝트에서 어떻게 적용할지 설명합니다. 핵심은 두 트랙을 같은 매니저로 뭉개지 않고, 원본 에셋과 복제 인스턴스를 다른 규칙으로 다루는 것입니다.

읽는 순서는 아래가 자연스럽습니다.

1. 일반 에셋 로딩 매니저를 봅니다.
2. 풀링 매니저를 봅니다.
3. 로딩 씬 예열과 전투 중 임대 흐름을 봅니다.
4. 반환 규약과 디버깅 포인트를 확인합니다.

---

## 2. 이 가이드가 전제하는 계약

- 일반 에셋은 `AsyncResourceManager`가 로드와 릴리즈를 책임진다.
- 복제 객체는 `AsyncPoolManager`가 예열, 임대, 반환을 책임진다.
- 원본 에셋과 복제 인스턴스는 같은 수명주기로 다루지 않는다.
- 로딩 씬에서 예열할 것과 전투 중 즉시 쓸 것을 구분한다.

이 계약이 무너지면 메모리 반납 시점도 흐려지고, 전투 중 스파이크도 다시 생깁니다.

---

## 3. 일반 에셋 로딩 매니저

Reference Example: `AsyncResourceManager`

```csharp
using Cysharp.Threading.Tasks;
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

public class AsyncResourceManager : MonoBehaviour
{
    private readonly Dictionary<string, AsyncOperationHandle> _handles = new();
    private readonly Dictionary<string, UniTask<Object>> _loadTasks = new();

    public async UniTask<T> LoadAssetAsync<T>(AssetReference assetRef) where T : Object
    {
        var key = assetRef.AssetGUID;

        if (_handles.TryGetValue(key, out var cachedHandle))
        {
            return (T)cachedHandle.Result;
        }

        if (_loadTasks.TryGetValue(key, out var pendingTask))
        {
            return (T)await pendingTask;
        }

        async UniTask<Object> LoadInternalAsync()
        {
            var handle = assetRef.LoadAssetAsync<T>();
            await handle.Task;
            _handles[key] = handle;
            _loadTasks.Remove(key);
            return handle.Result;
        }

        _loadTasks[key] = LoadInternalAsync();
        return (T)await _loadTasks[key];
    }

    public void ReleaseAsset(AssetReference assetRef)
    {
        var key = assetRef.AssetGUID;

        if (_handles.TryGetValue(key, out var handle))
        {
            Addressables.Release(handle);
            _handles.Remove(key);
        }
    }
}
```

이 매니저는 일반 에셋의 로딩 중복을 줄이고, 씬 종료나 사용 종료 시점에 정확히 반납할 수 있게 만듭니다.

---

## 4. 복제 객체 풀링 매니저

Reference Example: `AsyncPoolManager`

```csharp
using Cysharp.Threading.Tasks;
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.AddressableAssets;
using UnityEngine.Pool;

public class AsyncPoolManager : MonoBehaviour
{
    private readonly Dictionary<string, ObjectPool<GameObject>> _pools = new();

    public async UniTask<GameObject> SpawnAsync(AssetReference assetRef, Vector3 position)
    {
        var key = assetRef.AssetGUID;

        if (!_pools.TryGetValue(key, out var pool))
        {
            var prefab = await AsyncResourceManager.Instance.LoadAssetAsync<GameObject>(assetRef);
            pool = new ObjectPool<GameObject>(
                createFunc: () => Instantiate(prefab),
                actionOnGet: obj =>
                {
                    obj.transform.position = position;
                    obj.SetActive(true);
                },
                actionOnRelease: obj => obj.SetActive(false),
                actionOnDestroy: Destroy,
                collectionCheck: true,
                defaultCapacity: 20
            );
            _pools[key] = pool;
        }

        return pool.Get();
    }

    public async UniTask PrewarmAsync(AssetReference assetRef, int count, int batchSize = 10)
    {
        for (var i = 0; i < count; i++)
        {
            var spawned = await SpawnAsync(assetRef, Vector3.zero);
            Release(assetRef, spawned);

            if ((i + 1) % batchSize == 0)
            {
                await UniTask.Yield(PlayerLoopTiming.Update);
            }
        }
    }

    public void Release(AssetReference assetRef, GameObject instance)
    {
        var key = assetRef.AssetGUID;

        if (_pools.TryGetValue(key, out var pool))
        {
            pool.Release(instance);
        }
    }
}
```

전투 중 스폰은 이 매니저만 통해야 합니다. 외부에서 직접 `Instantiate`하거나 `Destroy`하면 풀 구조와 실제 객체 수명이 어긋납니다.

---

## 5. 로딩 씬 예열

`SceneDI`와 가장 자연스럽게 연결되는 지점은 로딩 씬 예열입니다.

```csharp
public class LoadingSceneDirector : BaseSceneDirectorAsync
{
    [SerializeField] private AssetReference _fireballRef;

    protected override async UniTask InitializeSceneAsync(CancellationToken token)
    {
        await AsyncPoolManager.Instance.PrewarmAsync(_fireballRef, 50, batchSize: 10);
    }
}
```

이 단계에서는 전투 중 자주 쓰일 객체를 미리 준비할 수 있습니다. 다만 모든 풀을 무조건 크게 예열하는 것은 좋지 않습니다. 자주 쓰는 핵심 객체부터 시작하는 편이 안전합니다.

---

## 6. 일반 에셋 반납 규약

일반 에셋은 필요 없어졌을 때 명시적으로 반납해야 합니다.

```csharp
public class SceneBgmPlayer : MonoBehaviour
{
    [SerializeField] private AssetReference _bossPhaseBgmRef;
    private AudioClip _clip;

    private async void Start()
    {
        _clip = await AsyncResourceManager.Instance.LoadAssetAsync<AudioClip>(_bossPhaseBgmRef);
        AudioSource.PlayClipAtPoint(_clip, Vector3.zero);
    }

    private void OnDestroy()
    {
        AsyncResourceManager.Instance.ReleaseAsset(_bossPhaseBgmRef);
    }
}
```

이 반납 규약이 없으면 씬이 끝난 뒤에도 메모리가 남습니다.

---

## 7. 풀링 객체 반환 규약

풀링 객체는 스스로 파괴되지 않고 반환 경로를 타야 합니다.

```csharp
public class Fireball : MonoBehaviour
{
    [SerializeField] private AssetReference _selfRef;

    private void OnCollisionEnter(Collision collision)
    {
        AsyncPoolManager.Instance.Release(_selfRef, gameObject);
    }
}
```

객체 내부 상태 초기화는 `OnSpawned()` 같은 별도 훅으로 정리하는 편이 안전합니다.

---

## 8. 자주 하는 실수

### 실수 1. 일반 에셋을 반납하지 않는 것

`ReleaseAsset` 호출이 빠지면 메모리가 남습니다.

### 실수 2. 풀링 객체를 직접 `Destroy`하는 것

풀 구조와 객체 수명이 분리되지 않아 다음 임대 시 문제가 생깁니다.

### 실수 3. 같은 에셋을 여러 곳에서 각각 로드하는 것

로딩 중 작업 병합이 없으면 중복 비용이 발생합니다.

### 실수 4. 예열을 전투 시작 이후에 몰아넣는 것

전투 중 첫 스폰 때 스파이크가 생길 수 있습니다.

---

## 9. 디버깅 포인트

- 일반 에셋 핸들이 씬 종료 후 반납되는지 확인합니다.
- 풀링 객체가 실제로 재사용되고 있는지 확인합니다.
- 예열 수치가 과도해 로딩 시간을 잡아먹고 있지 않은지 봅니다.
- 전투 중 직접 생성과 파괴가 남아 있지 않은지 확인합니다.
- 메인 스레드가 아닌 곳에서 활성화/생성이 일어나지 않는지 확인합니다.
