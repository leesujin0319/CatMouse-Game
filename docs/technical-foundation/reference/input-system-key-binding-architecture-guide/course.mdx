## [기술 기획안] 입력 레이어 및 키 바인딩 (Input System & Key Binding)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 설계 목적

이 문서는 입력을 `Input.GetKeyDown()` 호출 몇 개로 처리하는 수준이 아니라, **플레이 상태와 씬 조립 구조를 따라 확장 가능한 입력 레이어**로 정리하는 기준서입니다.

실제 프로젝트에서 입력은 곧바로 아래 문제와 연결됩니다.

- `Gameplay` 입력과 `UI` 입력이 동시에 살아서 오작동하는 문제
- 로딩, 컷신, 팝업, 대화 중 입력을 어디서 막아야 하는지 모호한 문제
- 키보드, 패드, 터치 입력을 같은 행동 vocabulary로 묶지 못하는 문제
- 리바인딩 저장 위치와 적용 시점이 제각각인 문제
- 액터가 입력 수집과 게임 규칙까지 함께 떠안는 문제

이 문서의 목적은 입력을 장치 API가 아니라 **행동 계약, 상태 전환, 차단 규약, 저장 규약** 기준으로 정리하는 데 있습니다.

**이 문서가 바로 답하는 질문**

- 어떤 기준으로 `Action Map`을 나누어야 하는가
- 입력은 누가 읽고, 누가 게임 규칙에 전달해야 하는가
- 팝업, 컷신, 로딩, 대화 중 입력 차단은 어디서 책임지는가
- 키 리바인딩은 어디서 저장하고 언제 복원해야 하는가
- `SceneDI`, `UI`, `SkillSystem`, `Vehicle` 같은 하위 시스템과 어디서 연결해야 하는가

---

## 2. 문제 정의

작은 프로토타입에서는 액터가 `Update()`에서 직접 입력을 읽어도 바로 문제가 드러나지 않습니다. 하지만 실제 프로젝트로 가면 입력은 곧바로 씬 상태와 시스템 경계 문제로 커집니다.

예를 들어 인벤토리가 열린 상태에서 `Gameplay` 입력이 그대로 살아 있으면, 버튼을 누르는 동시에 캐릭터가 이동하거나 스킬이 발동될 수 있습니다. 로딩 씬에서 입력을 막았다고 생각했는데 다른 액션 맵이 남아 있으면 뒤에서 이동 입력이 계속 쌓일 수도 있습니다. 키 바인딩을 옵션 팝업에서 바꾸더라도 다음 씬 진입 시 다시 기본값으로 돌아오면, 사용자는 설정이 저장되지 않았다고 느낍니다.

더 큰 문제는 책임 혼합입니다. 플레이어 액터가 입력 수집, 리바인딩 복원, 팝업 차단, 장치 변경 감지, 스킬 발동 판단까지 모두 맡기 시작하면, 입력 구조를 바꿀 때마다 액터 코드와 UI 코드와 로딩 코드가 같이 흔들립니다.

따라서 입력 설계의 핵심 문제는 "어떤 키를 쓸 것인가"보다, **어떤 상태에서 어떤 행동을 허용하고, 그 결정을 누가 소유하는가**를 명확히 하는 데 있습니다.

---

## 3. 설계 목표

- 장치별 입력을 행동 vocabulary 기준으로 통합한다.
- `Gameplay`, `UI`, `Dialogue`, `Vehicle`처럼 함께 켜고 끄는 입력 묶음을 분리한다.
- 액터는 입력 원천이 아니라 입력 소비자로 두고, 입력 수집 책임을 별도 레이어로 분리한다.
- 로딩, 팝업, 컷신, 대화 중 입력 차단을 중앙에서 통제한다.
- 키 바인딩 변경과 저장, 복원을 명시적 서비스로 관리한다.
- `SceneDI`가 입력 서비스를 조립하고, 실제 액터와 시스템은 그 결과를 소비하는 구조를 만든다.
- `SkillSystem`, `UI`, `EventBus` 같은 인접 시스템과의 연결 규약을 문서 수준에서 닫는다.

---

## 4. 범위와 비범위

### In Scope

- 입력 행동 vocabulary 정의
- `Input Action Asset`과 `Action Map` 분리 기준
- 입력 수집 레이어와 게임 규칙 소비 레이어 분리
- 입력 차단과 현재 입력 컨텍스트 전환
- 키 리바인딩 저장 및 복원 규약
- `SceneDI`와 입력 서비스 조립 시점

### Out of Scope

- 특정 장치별 상세 UX 튜닝
- 모바일 제스처 인식 세부 구현
- 네트워크 입력 예측과 롤백 처리
- 접근성 옵션 전체 설계
- 에디터 툴링과 입력 아이콘 자동 교체 세부 구현

이 문서는 입력 시스템의 **코어 구조와 계약**을 다룹니다. 장치별 감도 조정, 복합 제스처, 멀티플레이 입력 예측은 이후 하위 문서나 기능 문서에서 확장하는 편이 안전합니다.

---

## 5. 핵심 구조와 책임

### 5.1 책임 맵

- `Input Action Asset`: 행동과 바인딩 정의를 담는다.
- `Action Map`: 현재 상태에서 함께 유효한 입력 묶음을 표현한다.
- `InputReader`: 엔진 입력을 읽어 프레임 데이터나 콜백으로 변환한다.
- `InputContextService`: 어떤 `Action Map`이 현재 유효한지 결정한다.
- `InputBlockService`: 로딩, 팝업, 컷신 같은 상위 이유로 입력을 막는다.
- `InputRebindService`: 리바인딩 적용, 저장, 복원을 담당한다.
- `Actor / System`: 이미 정리된 입력만 소비해 게임 규칙에 반영한다.

핵심은 입력을 읽는 계층과 입력을 해석해 행동으로 바꾸는 계층을 나누는 것입니다. 입력 서비스는 "어떤 행동이 지금 유효한가"를 보장하고, 액터는 그 결과를 받아 이동, 점프, 상호작용, 스킬 요청 같은 게임 규칙으로 넘깁니다.

### 5.2 왜 액터에서 직접 읽지 않는가

액터에서 직접 입력을 읽으면 간단해 보이지만 다음 문제가 빠르게 생깁니다.

- UI가 열렸을 때 입력 차단을 액터마다 따로 넣게 된다.
- 동일한 행동을 플레이어, 탈것, 포탑, 관전자 모드가 각자 다른 방식으로 읽는다.
- 키 바인딩이 바뀌어도 액터가 문자열이나 키코드를 직접 알고 있어서 치환이 어렵다.
- 테스트에서 입력을 가짜로 주입하기 어렵다.

따라서 액터는 입력 원천을 직접 알지 않고, `IMovementInputSource`, `ICombatInputSource` 같은 계약을 통해 이미 정리된 입력을 받는 편이 더 안정적입니다.

---

## 6. Action Map 분리 기준

`Action Map`은 장치별로 나누는 것이 아니라, **함께 켜고 끄는 상태 묶음**으로 나누는 편이 실무적입니다.

권장 예시는 아래와 같습니다.

- `Gameplay`: 이동, 점프, 상호작용, 공격, 회피
- `UI`: 확인, 취소, 탭 이동, 커서 이동
- `Dialogue`: 다음 대사, 스킵, 선택지 이동
- `Vehicle`: 가속, 감속, 조향, 하차
- `PhotoMode`: 카메라 이동, 줌, 필터 전환

반대로 아래 구조는 피하는 편이 좋습니다.

- 키보드용 맵, 패드용 맵처럼 장치 기준으로 분리
- 모든 액션을 `All` 맵 하나에 몰아넣는 구조
- `Jump`, `Attack`, `Interact`를 각각 독립 맵으로 잘게 쪼개는 구조

장치 차이는 `Control Scheme`과 바인딩이 흡수하고, 상태 차이는 `Action Map`이 흡수하는 쪽이 읽기 쉽습니다.

---

## 7. 런타임 흐름

입력은 보통 아래 순서로 붙습니다.

1. `SceneDI`가 씬 진입 시점에 입력 관련 서비스를 조립한다.
2. `Input Action Asset` 또는 `PlayerInput` 루트를 생성한다.
3. 저장된 바인딩 오버라이드를 복원한다.
4. 기본 입력 컨텍스트를 `Gameplay` 또는 씬 전용 맵으로 설정한다.
5. 액터와 UI는 입력 서비스에 구독하거나 프레임 입력을 읽는다.
6. 팝업, 컷신, 대화가 열리면 `InputBlockService` 또는 `InputContextService`가 맵을 전환한다.
7. 씬 종료 시 입력 구독을 해지하고 필요 시 바인딩 저장을 반영한다.

이 흐름에서 중요한 점은 리바인딩 복원이 액터 활성화보다 먼저 끝나야 한다는 것입니다. 그래야 첫 프레임부터 사용자가 기대한 키 구성이 적용됩니다.

---

## 8. SceneDI와 인접 시스템 경계

### 8.1 SceneDI

`SceneDI`는 입력 서비스를 **조립하고 연결하는 책임**을 가집니다. 하지만 실제 입력 판독 루프를 매 프레임 직접 실행하는 위치는 아닙니다.

- `SceneDI`: 입력 서비스 생성, 저장 데이터 주입, 액터/매니저 연결
- 입력 서비스: 액션 맵 전환, 차단, 리바인딩 관리
- 액터/시스템: 정리된 입력 소비

즉 `SceneDI`는 입력 구조를 붙이는 composition root이고, 입력 동작 그 자체는 입력 레이어가 책임집니다.

### 8.2 UI

UI는 게임플레이 입력을 직접 꺼서는 안 됩니다. 팝업, 메뉴, 인벤토리, 옵션 화면은 `InputBlockService`나 `InputContextService`에 이유를 전달하고, 중앙 서비스가 현재 입력 상태를 바꾸는 구조가 더 안전합니다.

### 8.3 SkillSystem

입력 시스템은 "공격 버튼이 눌렸다"까지만 다루고, 실제 스킬 발동 가능 여부 판단은 `SkillSystem` 쪽이 맡아야 합니다. 쿨다운, 마나 부족, 상태이상, 콤보 창 판단까지 입력 레이어가 품기 시작하면 책임이 뒤섞입니다.

### 8.4 EventBus

입력 그 자체를 무조건 이벤트로 흘릴 필요는 없습니다. 지속 입력(`Move`, `Look`)은 프레임 데이터나 직접 호출이 더 자연스럽고, 일회성 의미 이벤트(`PauseRequested`, `OpenMapRequested`)만 필요한 범위에서 이벤트화하는 편이 좋습니다.

## 9. 코어 구조 예시

Reference Example: 입력 컨텍스트와 차단 서비스 분리

```csharp
using System;
using System.Collections.Generic;

public enum InputContext
{
    Gameplay,
    UI,
    Dialogue,
    Vehicle
}

public sealed class InputContextService
{
    private readonly Action<InputContext> _applyContext;
    private InputContext _currentContext;

    public InputContextService(Action<InputContext> applyContext)
    {
        _applyContext = applyContext;
    }

    public InputContext CurrentContext => _currentContext;

    public void SwitchTo(InputContext next)
    {
        if (_currentContext == next)
        {
            return;
        }

        _currentContext = next;
        _applyContext.Invoke(next);
    }
}

public sealed class InputBlockService
{
    private readonly HashSet<string> _reasons = new();
    private readonly Action<bool> _applyBlockState;

    public InputBlockService(Action<bool> applyBlockState)
    {
        _applyBlockState = applyBlockState;
    }

    public bool IsBlocked => _reasons.Count > 0;

    public void Push(string reason)
    {
        if (_reasons.Add(reason))
        {
            _applyBlockState.Invoke(true);
        }
    }

    public void Pop(string reason)
    {
        if (_reasons.Remove(reason) && _reasons.Count == 0)
        {
            _applyBlockState.Invoke(false);
        }
    }
}
```

이 구조는 `Action Map` 전환과 입력 차단을 분리합니다. 현재 플레이 상태가 `Dialogue`인지 `Vehicle`인지는 컨텍스트 문제이고, 로딩 중이라 어떤 입력도 받지 않아야 하는지는 차단 문제입니다. 둘을 한 메서드에 섞어 넣으면 디버깅이 어려워집니다.

## 10. 실패 경로와 엣지 케이스

### 10.1 Gameplay와 UI가 동시에 살아 있는 경우

가장 흔한 버그입니다. 메뉴를 조작하는 동안 이동, 공격, 확인 키가 함께 작동합니다. 해결책은 UI가 액터 입력을 직접 끄는 것이 아니라, 입력 컨텍스트를 전환하거나 차단 서비스를 통해 상위 이유를 등록하는 것입니다.

### 10.2 차단 해제를 놓친 경우

로딩이나 컷신 종료 후 `Pop()`이 빠지면, 입력이 영구적으로 막힌 것처럼 보일 수 있습니다. 차단 이유를 문자열 또는 enum으로 추적하고, 디버그 UI에서 현재 차단 이유를 확인할 수 있게 두는 편이 좋습니다.

### 10.3 리바인딩 저장은 했지만 복원 시점이 늦은 경우

씬이 열린 뒤 한참 후에 오버라이드를 적용하면 첫 프레임 입력은 기본 키로 처리됩니다. 바인딩 복원은 액터 활성화 이전 단계에서 끝내야 합니다.

### 10.4 장치별 맵 분리

키보드용 맵과 패드용 맵을 분리하면 같은 행동을 서로 다른 시스템처럼 다루게 됩니다. 장치 교체, 튜토리얼 표기, 리바인딩 UI까지 전부 복잡해집니다.

### 10.5 입력 레이어가 스킬 규칙까지 품는 경우

입력 서비스가 콤보 윈도우, 마나 체크, 타겟 탐색까지 직접 하게 되면 `SkillSystem`과 경계가 무너집니다. 입력 레이어는 요청까지만 만들고, 실제 허용 판단은 하위 시스템에 넘겨야 합니다.

## 11. 기획 및 운영 우려사항

입력은 기획 변경이 잦은 영역입니다. 그래서 더더욱 "기획자가 바꿔도 되는 것"과 "개발 협의가 필요한 것"을 나눠야 합니다.

기획자가 비교적 안전하게 다룰 수 있는 영역은 아래에 가깝습니다.

- 액션 이름과 기본 바인딩 배치
- `Gameplay`, `UI`, `Dialogue` 같은 상태별 동작 목록
- 옵션 메뉴에 노출할 리바인딩 허용 액션

반대로 개발 협의가 필요한 변경은 아래에 가깝습니다.

- `Action Map` 경계 자체 변경
- 새로운 입력 컨텍스트 추가
- 저장 포맷 변경
- 리바인딩 불가 바인딩이나 복합 바인딩 정책 변경
- 입력 차단 정책과 씬 전환 정책 변경

특히 `Pause`, `Confirm`, `Cancel`처럼 UI와 시스템 전반에 영향을 주는 액션은 이름만 바뀌어도 연계 범위가 큽니다.

## 12. 디버깅 및 검증 포인트

- 현재 활성 `Action Map`이 무엇인지 런타임에서 확인할 수 있는가
- 차단 중이라면 어떤 이유가 등록되어 있는지 볼 수 있는가
- 리바인딩 적용 후 다음 씬 진입에서도 유지되는가
- UI 팝업, 대화, 컷신, 로딩 전환에서 입력 유실이나 중복 허용이 없는가
- 액터가 키코드 문자열이나 `Input.GetKeyDown()`에 직접 의존하지 않는가
- `SkillSystem`, `Vehicle`, `Dialogue`가 입력 서비스의 결과를 소비하는 구조인지 확인하는가

---

## 13. 리뷰 체크리스트

- `Action Map`이 상태 기준으로 나뉘어 있는가
- 입력 수집과 게임 규칙 소비가 분리되어 있는가
- 입력 차단과 컨텍스트 전환이 다른 책임으로 분리되어 있는가
- 리바인딩 저장과 복원 시점이 문서에 닫혀 있는가
- `SceneDI`, UI, 스킬 시스템과의 경계가 충돌하지 않는가

## [개발 가이드] 입력 레이어 및 키 바인딩 (Input System & Key Binding)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 읽는 순서

이 가이드는 입력 구조를 실제 프로젝트에 붙이는 방법을 코드 기준으로 설명합니다. 핵심은 `PlayerInput` 하나를 씬에 올리는 데 있지 않고, **입력 자산, 컨텍스트 전환, 차단, 리바인딩 저장, 액터 연결**을 한 묶음으로 조립하는 데 있습니다.

읽는 순서는 아래가 자연스럽습니다.

1. 입력 자산과 액션 맵 구성을 봅니다.
2. 코어 서비스인 컨텍스트, 차단, 리바인딩 코드를 봅니다.
3. `SceneDI`에서 이 서비스들을 어떻게 조립하는지 봅니다.
4. 액터, UI, 탈것 같은 소비자가 어떻게 붙는지 봅니다.

---

## 2. 이 가이드가 전제하는 계약

- 입력 시스템은 행동 vocabulary를 제공한다.
- 액터는 입력을 직접 읽지 않고 정리된 입력을 소비한다.
- UI는 게임플레이 입력을 직접 끄지 않고 컨텍스트 또는 차단 서비스를 요청한다.
- 리바인딩은 저장과 복원을 서비스가 담당한다.
- 씬 진입 시 조립은 `SceneDI`에서, 런타임 전환은 입력 서비스에서 담당한다.

이 계약이 무너지면 키 맵은 바뀌었는데 액터는 여전히 기본 키를 읽거나, UI가 열렸는데도 게임플레이 입력이 살아 있는 구조가 됩니다.

---

## 3. 입력 자산 구성 예시

입력 자산은 아래처럼 상태 기준으로 나누는 편이 실무적입니다.

```text
InputActions
  Gameplay
    Move            (Vector2)
    Look            (Vector2)
    Jump            (Button)
    Interact        (Button)
    Attack          (Button)
    Dodge           (Button)
    Pause           (Button)

  UI
    Navigate        (Vector2)
    Submit          (Button)
    Cancel          (Button)
    TabLeft         (Button)
    TabRight        (Button)

  Dialogue
    Next            (Button)
    Skip            (Button)
    Select          (Button)

  Vehicle
    Steer           (Vector2)
    Accelerate      (Button)
    Brake           (Button)
    ExitVehicle     (Button)
```

여기서 중요한 것은 장치 이름이 아니라 행동 이름입니다. 키보드, 패드, 터치는 각 액션의 바인딩과 `Control Scheme`이 흡수하고, 문서와 코드에서는 `Move`, `Attack`, `Submit` 같은 의미 이름만 사용합니다.

## 4. 코어 서비스 코드

### 4.1 입력 루트

Reference Example: `GameInputRoot`

```csharp
using System;
using UnityEngine;
using UnityEngine.InputSystem;

public sealed class GameInputRoot : IDisposable
{
    private readonly InputActionAsset _asset;

    public GameInputRoot(InputActionAsset asset)
    {
        _asset = UnityEngine.Object.Instantiate(asset);
    }

    public InputActionAsset Asset => _asset;

    public InputActionMap GetMap(string mapName)
    {
        return _asset.FindActionMap(mapName, throwIfNotFound: true);
    }

    public void EnableOnly(string mapName)
    {
        foreach (var map in _asset.actionMaps)
        {
            if (map.name == mapName)
            {
                map.Enable();
            }
            else
            {
                map.Disable();
            }
        }
    }

    public void DisableAll()
    {
        foreach (var map in _asset.actionMaps)
        {
            map.Disable();
        }
    }

    public void Dispose()
    {
        UnityEngine.Object.Destroy(_asset);
    }
}
```

런타임에서 자산 원본을 직접 건드리기보다 인스턴스를 복제해 쓰는 편이 안전합니다. 그래야 씬별 바인딩 복원과 테스트 목업을 다루기 쉽습니다.

### 4.2 입력 컨텍스트 서비스

```csharp
public enum InputContext
{
    Gameplay,
    UI,
    Dialogue,
    Vehicle
}

public sealed class InputContextService
{
    private readonly GameInputRoot _root;
    private InputContext _current;

    public InputContextService(GameInputRoot root)
    {
        _root = root;
    }

    public InputContext Current => _current;

    public void SwitchTo(InputContext next)
    {
        _current = next;
        _root.EnableOnly(next.ToString());
    }
}
```

상태 전환은 가능하면 `enum`이나 고정된 이름 집합으로 다루는 편이 안전합니다. UI 코드 곳곳에서 `"Gameplay"` 문자열을 직접 쓰기 시작하면 오타와 추적 비용이 커집니다.

### 4.3 입력 차단 서비스

```csharp
using System.Collections.Generic;

public sealed class InputBlockService
{
    private readonly GameInputRoot _root;
    private readonly HashSet<string> _reasons = new();
    private InputContext _fallbackContext;

    public InputBlockService(GameInputRoot root)
    {
        _root = root;
    }

    public bool IsBlocked => _reasons.Count > 0;

    public void Push(string reason, InputContext fallbackContext)
    {
        _fallbackContext = fallbackContext;

        if (_reasons.Add(reason))
        {
            _root.DisableAll();
        }
    }

    public void Pop(string reason)
    {
        if (_reasons.Remove(reason) && _reasons.Count == 0)
        {
            _root.EnableOnly(_fallbackContext.ToString());
        }
    }
}
```

`InputContextService`와 `InputBlockService`를 분리해 두면, "지금은 UI 상태다"와 "지금은 어떤 상태든 입력을 받으면 안 된다"를 서로 다른 책임으로 유지할 수 있습니다.

### 4.4 리바인딩 저장 서비스

Reference Example: `InputRebindService`

```csharp
using Cysharp.Threading.Tasks;
using UnityEngine;
using UnityEngine.InputSystem;

public interface IInputBindingStore
{
    string Load();
    void Save(string json);
}

public sealed class PlayerPrefsInputBindingStore : IInputBindingStore
{
    private const string SaveKey = "input.binding.overrides";

    public string Load()
    {
        return PlayerPrefs.GetString(SaveKey, string.Empty);
    }

    public void Save(string json)
    {
        PlayerPrefs.SetString(SaveKey, json);
        PlayerPrefs.Save();
    }
}

public sealed class InputRebindService
{
    private readonly InputActionAsset _asset;
    private readonly IInputBindingStore _store;

    public InputRebindService(InputActionAsset asset, IInputBindingStore store)
    {
        _asset = asset;
        _store = store;
    }

    public void RestoreOverrides()
    {
        var json = _store.Load();

        if (!string.IsNullOrWhiteSpace(json))
        {
            _asset.LoadBindingOverridesFromJson(json);
        }
    }

    public void SaveOverrides()
    {
        var json = _asset.SaveBindingOverridesAsJson();
        _store.Save(json);
    }
}
```

리바인딩 저장을 옵션 UI가 직접 맡기지 않는 편이 좋습니다. 옵션 UI는 서비스 호출만 하고, 실제 저장 포맷과 복원은 입력 서비스가 닫는 쪽이 경계가 더 깔끔합니다.

## 5. SceneDI에서 조립하는 방법

`SceneDI`는 입력을 읽는 위치가 아니라, 입력 서비스와 소비자를 연결하는 위치입니다.

Reference Example: `GameplaySceneDirector`

```csharp
using UnityEngine;
using UnityEngine.InputSystem;

public sealed class GameplaySceneDirector : BaseSceneDirectorAsync
{
    [Header("Input")]
    [SerializeField] private InputActionAsset _inputActions;
    [SerializeField] private PlayerActor _playerActor;
    [SerializeField] private InventoryPopup _inventoryPopup;

    private GameInputRoot _inputRoot;
    private InputContextService _inputContext;
    private InputBlockService _inputBlock;
    private InputRebindService _inputRebind;

    protected override async UniTask LoadAsync()
    {
        _inputRoot = new GameInputRoot(_inputActions);
        _inputContext = new InputContextService(_inputRoot);
        _inputBlock = new InputBlockService(_inputRoot);
        _inputRebind = new InputRebindService(_inputRoot.Asset, new PlayerPrefsInputBindingStore());

        _inputRebind.RestoreOverrides();
        _inputContext.SwitchTo(InputContext.Gameplay);

        _playerActor.BindInput(_inputRoot.GetMap("Gameplay"));
        _inventoryPopup.BindInputServices(_inputContext, _inputBlock);

        await UniTask.CompletedTask;
    }

    protected override UniTask UnloadAsync()
    {
        _inputRebind.SaveOverrides();
        _inputRoot.Dispose();
        return UniTask.CompletedTask;
    }
}
```

핵심은 바인딩 복원을 액터 연결보다 먼저 끝내는 것입니다. 그래야 플레이어 액터가 첫 프레임부터 올바른 키 구성으로 동작합니다.

## 6. 액터는 입력을 소비만 하도록 붙이기

Reference Example: `PlayerActor`

```csharp
using UnityEngine;
using UnityEngine.InputSystem;

public sealed class PlayerActor : MonoBehaviour
{
    private InputAction _move;
    private InputAction _jump;
    private InputAction _attack;

    public void BindInput(InputActionMap gameplayMap)
    {
        _move = gameplayMap.FindAction("Move", throwIfNotFound: true);
        _jump = gameplayMap.FindAction("Jump", throwIfNotFound: true);
        _attack = gameplayMap.FindAction("Attack", throwIfNotFound: true);
    }

    private void Update()
    {
        var move = _move.ReadValue<Vector2>();

        Move(move);

        if (_jump.WasPressedThisFrame())
        {
            Jump();
        }

        if (_attack.WasPressedThisFrame())
        {
            TryAttack();
        }
    }

    private void Move(Vector2 move) { }
    private void Jump() { }
    private void TryAttack() { }
}
```

이 예제에서도 액터는 여전히 입력을 읽고 있습니다. 하지만 키 코드나 액션 자산 전체를 직접 아는 것이 아니라, 이미 정리된 `Gameplay` 맵을 주입받아 소비만 합니다. 더 나아가면 `InputActionMap` 대신 별도 `IPlayerInputSource` 인터페이스를 두어 테스트성을 높일 수 있습니다.

## 7. UI에서 입력 차단과 전환 요청하기

Reference Example: `InventoryPopup`

```csharp
public sealed class InventoryPopup : MonoBehaviour
{
    private InputContextService _inputContext;
    private InputBlockService _inputBlock;

    public void BindInputServices(
        InputContextService inputContext,
        InputBlockService inputBlock)
    {
        _inputContext = inputContext;
        _inputBlock = inputBlock;
    }

    public void Open()
    {
        _inputBlock.Push("InventoryPopup", InputContext.UI);
        _inputContext.SwitchTo(InputContext.UI);
        gameObject.SetActive(true);
    }

    public void Close()
    {
        gameObject.SetActive(false);
        _inputBlock.Pop("InventoryPopup");
        _inputContext.SwitchTo(InputContext.Gameplay);
    }
}
```

실무에서는 `Push()`와 `SwitchTo()`의 순서를 한 서비스 안에 묶거나, UI 팝업 베이스 클래스가 책임지게 만들 수도 있습니다. 중요한 것은 UI가 플레이어 액터를 직접 찾아가 `enabled = false` 같은 방식으로 입력을 끄지 않는다는 점입니다.

## 9. 리바인딩 UI 연결 포인트

리바인딩 UI는 저장 서비스와 분리되어야 합니다. UI는 "어떤 액션의 어떤 바인딩을 바꿀지"만 결정하고, 실제 적용과 저장은 서비스에 넘깁니다.

```csharp
public sealed class InputOptionPresenter
{
    private readonly InputRebindService _rebindService;

    public InputOptionPresenter(InputRebindService rebindService)
    {
        _rebindService = rebindService;
    }

    public void ApplyAndSave()
    {
        _rebindService.SaveOverrides();
    }
}
```

실제 인터랙티브 리바인딩 시작 코드는 프로젝트별 UX 차이가 커서 이 문서에서는 다루지 않았습니다. 다만 저장과 복원 책임은 서비스에 남기고, UI는 그 결과만 반영하는 구조를 유지하는 편이 좋습니다.

## 10. 디버깅 보조

입력 디버깅에서는 아래 정보가 바로 보여야 합니다.

- 현재 입력 컨텍스트
- 활성 `Action Map`
- 현재 차단 이유 목록
- 리바인딩 오버라이드 저장 여부

에디터 전용 오버레이나 개발자 팝업으로 이 정보를 확인할 수 있게 두면, "왜 입력이 안 들어오는가"를 훨씬 빨리 좁힐 수 있습니다.

## 11. 자주 하는 실수

### 실수 1. 액터가 키코드를 직접 아는 것

리바인딩과 장치 확장을 어렵게 만듭니다.

### 실수 2. UI가 플레이어 입력을 직접 끄는 것

입력 차단 책임이 여러 객체로 흩어집니다.

### 실수 3. 차단과 컨텍스트 전환을 같은 조건문으로 처리하는 것

상태 전환과 완전 차단은 다른 문제입니다.

### 실수 4. 리바인딩 저장을 옵션 팝업에 넣는 것

복원 시점과 저장 포맷이 UI에 종속됩니다.

### 실수 5. 모든 입력을 이벤트로만 흘리는 것

지속 입력은 프레임 데이터나 직접 소비가 더 자연스러운 경우가 많습니다.

## 12. 검증 체크리스트

- 팝업을 열면 `Gameplay` 입력이 실제로 멈추는가
- 팝업을 닫으면 이전 컨텍스트로 안정적으로 복귀하는가
- 씬 재진입 후에도 리바인딩이 유지되는가
- 탈것, 대화, 컷신처럼 상태가 바뀔 때 맵 전환이 한 지점에서 보이는가
- 액터가 `Input.GetKeyDown()`이나 키 문자열에 직접 의존하지 않는가
