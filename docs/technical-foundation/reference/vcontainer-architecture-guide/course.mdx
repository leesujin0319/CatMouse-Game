## [기술 기획안] 모던 IoC 프레임워크 (VContainer)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 도입 배경

`VContainer`는 수동 의존성 주입이 커졌을 때 생기는 조립 코드 비대화와 인스턴스 전파 복잡도를 줄이기 위한 **자동 DI 컨테이너**입니다. 목표는 모든 객체 생성을 컨테이너에 맡기는 데 있지 않습니다. 전역과 씬 단위의 수명주기를 기준으로 의존성을 정리하고, 수동 조립에서 반복되던 연결 코드를 더 안정적으로 관리하는 데 있습니다.

이 문서는 특히 `SceneDI`와의 경계를 분명히 합니다. `SceneDI`가 **언제 씬 조립을 시작할지**를 통제한다면, `VContainer`는 **그 조립 안에서 어떤 의존성을 어떻게 해소할지**를 맡습니다.

**이 문서가 바로 답하는 질문**

- 언제 수동 `Init(...)` 조립에서 `VContainer`로 넘어갈 가치가 있는가
- `ProjectLifetimeScope`와 `SceneLifetimeScope`는 어떤 책임을 나누는가
- 자동 주입을 도입해도 SceneDI의 상위 조립 권한은 어떻게 유지되는가
- 어떤 경우에 `Resolve`와 동적 생성이 오히려 문제를 만드는가

---

## 2. 문제 정의

초기 프로젝트에서는 수동 주입이 가장 명확한 경우가 많습니다. 하지만 씬 수가 늘고 액터, 서비스, 데이터 조합이 많아지면 디렉터나 상위 매니저가 `Init(A, B, C, D)`를 계속 늘려 가게 됩니다. 이 상태가 오래가면 두 가지 문제가 생깁니다.

첫째, 씬 조립 코드가 비대해집니다. 어떤 의존성이 어디서 오는지 추적은 되지만, 새 시스템을 추가할 때마다 상위 조립부가 계속 커집니다. 둘째, 공통 서비스와 씬 전용 서비스의 경계가 불명확해집니다. 전역 서비스, 씬 서비스, 임시 팩토리, 동적 생성 경로가 여기저기 흩어지기 시작합니다.

`VContainer`는 이 문제를 수명주기 기반 등록과 자동 해소로 정리합니다. 다만 자동화가 들어오는 만큼, 수동 조립에서 보이던 흐름 일부가 컨테이너 내부로 숨겨집니다. 그래서 이 문서의 핵심은 "컨테이너가 편하다"가 아니라, **어떤 책임을 자동화하고 어떤 책임은 상위 조립부에 남겨야 하는가**를 정하는 데 있습니다.

---

## 3. 설계 목표

- 전역 서비스와 씬 전용 서비스의 수명주기를 명확히 분리한다.
- 반복적인 수동 주입 코드를 줄이되, 상위 조립 권한은 유지한다.
- `SceneDI`와 충돌하지 않는 자동 조립 구조를 만든다.
- 동적 생성과 `Resolve` 오남용으로 서비스 로케이터 패턴이 되지 않게 한다.
- 전투 핫패스에서 컨테이너 탐색 비용이 누적되지 않도록 경계를 둔다.
- 신규 개발자가 수명주기와 등록 위치를 문서만으로 따라갈 수 있게 한다.

---

## 4. 범위와 비범위

### In Scope

- `LifetimeScope` 기반 의존성 수명주기 설계
- 전역 스코프와 씬 스코프의 책임 분리
- 생성자 주입, 메서드 주입, 등록 규칙
- SceneDI와 결합할 때의 조립 경계
- 동적 생성, 팩토리, `Resolve` 사용 제한

### Out of Scope

- SceneDI 자체의 로딩 순서 설계
- Addressables 핸들 관리 정책 자체
- 풀링 시스템의 세부 구현
- 모든 런타임 객체를 컨테이너로 직접 생성하는 구조

`VContainer`는 씬을 여는 구조를 대체하지 않습니다. 씬 진입과 초기화 파이프라인은 여전히 `SceneDI`나 상위 조립 구조가 통제하고, `VContainer`는 그 안에서 의존성 연결을 더 구조적으로 관리합니다.

---

## 5. 핵심 구조와 수명주기

`VContainer`의 기본 단위는 `LifetimeScope`입니다. 등록된 의존성은 아무 곳에나 떠다니지 않고, 특정 스코프 아래에서 생성되고 소멸합니다.

### 5.1 책임 맵

- `ProjectLifetimeScope`: 앱 전역에서 유지되는 서비스와 설정을 소유한다.
- `SceneLifetimeScope`: 특정 씬에서만 살아야 하는 서비스와 데이터를 소유한다.
- `SceneDI`: 씬 초기화 시작 시점과 로딩 페이즈를 통제한다.
- `VContainer`: 해당 시점에 필요한 의존성을 해소하고 주입한다.

### 5.2 코어 베이스 예시

Reference Example: `BaseProjectLifetimeScope`, `BaseSceneLifetimeScope`

```csharp
using VContainer;
using VContainer.Unity;

public abstract class BaseProjectLifetimeScope : LifetimeScope
{
    protected override void Configure(IContainerBuilder builder)
    {
        ConfigureGlobalDependencies(builder);
    }

    protected abstract void ConfigureGlobalDependencies(IContainerBuilder builder);
}

public abstract class BaseSceneLifetimeScope : LifetimeScope
{
    protected override void Configure(IContainerBuilder builder)
    {
        ConfigureSceneDependencies(builder);
    }

    protected abstract void ConfigureSceneDependencies(IContainerBuilder builder);
}
```

이 구조를 쓰면 전역 서비스와 씬 전용 서비스를 등록 위치부터 분리할 수 있습니다. 예를 들어 오디오, 네트워크 세션, 전역 설정은 `ProjectLifetimeScope`에 두고, 전투용 점수 집계기나 씬별 팩토리, 로컬 정책 객체는 `SceneLifetimeScope`에 둘 수 있습니다.

---

## 6. SceneDI와의 결합 방식

`SceneDI`와 `VContainer`는 경쟁 구조가 아닙니다. 둘은 서로 다른 문제를 풉니다.

- `SceneDI`: 씬이 언제 열리고, 어떤 단계로 로딩하고, 언제 액터를 켤지 정한다.
- `VContainer`: 그 과정에서 필요한 의존성을 어떤 스코프에서 해소할지 정한다.

수동 `SceneDI`에서는 디렉터가 `player.Init(data, sound, skillCaster)`처럼 직접 꽂아줄 수 있습니다. `VContainer`를 도입하면 디렉터는 여전히 로딩 완료 시점과 활성화 타이밍을 통제하지만, 실제 서비스 결합 일부는 컨테이너가 해소할 수 있습니다.

중요한 점은 컨테이너가 있다고 해서 액터가 스스로 `Resolve`하기 시작하면 안 된다는 것입니다. 조립 권한은 여전히 상위에 있어야 하고, 말단 객체는 주입을 받는 구조를 유지해야 합니다.

---

## 7. 장점과 트레이드오프

### 7.1 얻는 것

- 반복적인 수동 연결 코드를 줄일 수 있습니다.
- 전역과 씬 수명주기를 등록 위치로 명확히 나눌 수 있습니다.
- 공통 서비스 조합이 커져도 상위 조립부의 보일러플레이트를 줄일 수 있습니다.

### 7.2 잃는 것

- 의존성 해소 경로 일부가 코드 한눈에 보이지 않게 됩니다.
- 신규 개발자가 등록 위치와 스코프 구조를 먼저 이해해야 합니다.
- `Resolve` 오남용 시 서비스 로케이터 패턴으로 쉽게 무너집니다.

따라서 `VContainer`는 단순히 더 편한 방식이 아니라, **구조적 복잡도를 다른 형태의 규율로 바꾸는 도구**로 보는 편이 맞습니다.

---

## 8. 성능과 핫패스 경계

`VContainer`는 빌드 시점 코드 생성으로 런타임 반사 비용을 줄일 수 있지만, 그렇다고 전투 중 실시간 `Resolve`를 남발해도 된다는 뜻은 아닙니다.

특히 아래는 분리해야 합니다.

- 초기화 구간: 컨테이너가 의존성을 해소해도 괜찮다.
- 핫패스 구간: 풀링, 캐시, 전담 매니저를 사용하고 컨테이너 탐색을 반복하지 않는다.

예를 들어 투사체 100개를 쏠 때마다 `IObjectResolver.Instantiate()`를 호출하는 구조는 누적 비용을 만듭니다. 이런 구간은 초기화 단계에서 풀 매니저나 팩토리를 주입받고, 실제 전투 중에는 그 객체만 호출하는 편이 맞습니다.

---

## 9. 실패 경로와 안티 패턴

### 9.1 순환 참조

서비스 A가 B를 필요로 하고, B가 다시 A를 요구하면 초기화 시점에 실패합니다. 등록 구조는 단방향으로 정리해야 합니다.

### 9.2 말단 객체의 `Resolve` 남발

`PlayerController`, `EnemyUnit`, `Projectile` 같은 말단 객체가 컨테이너를 직접 들고 아무 때나 `Resolve<T>()`를 호출하면, 구조는 다시 서비스 로케이터 패턴으로 돌아갑니다.

### 9.3 씬 스코프와 전역 스코프 혼합

씬에서만 써야 하는 객체를 전역 스코프에 올리면 수명주기가 불필요하게 길어지고, 반대로 전역 서비스가 씬 스코프에 묶이면 씬 전환마다 재생성되며 오류 원인이 됩니다.

### 9.4 모든 생성 경로를 컨테이너에 억지로 넣는 것

컨테이너는 모든 문제의 해답이 아닙니다. 단순 값 객체, 핫패스 풀링 객체, 엔진 수명주기에 강하게 묶인 일부 구조는 수동 관리가 더 명확할 수 있습니다.

---

## 10. 검증 포인트

- 전역 서비스와 씬 전용 서비스의 등록 위치가 명확한가
- SceneDI와 VContainer가 같은 조립 권한을 두고 충돌하지 않는가
- 말단 객체가 컨테이너를 직접 들고 다니지 않는가
- 핫패스에서 `Resolve`나 컨테이너 기반 생성이 반복되지 않는가
- 신규 서비스 추가 시 어디에 등록해야 하는지 문서만으로 판단 가능한가

---

## 11. 리뷰 체크리스트

- `ProjectLifetimeScope`와 `SceneLifetimeScope`의 경계가 분명한가
- 자동 주입을 도입해도 상위 조립 권한이 유지되는가
- 생성자 주입과 메서드 주입의 기준이 정리되어 있는가
- 컨테이너가 서비스 로케이터로 변질될 가능성을 막고 있는가
- 핫패스 성능 경계가 문서에 포함되어 있는가

## [개발 가이드] 모던 IoC 프레임워크 (VContainer)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 읽는 순서

이 가이드는 `VContainer`를 실제 씬 구조에 붙일 때 어떤 형태로 등록하고, 어떤 주입 방식을 선택하고, 어디서 `Resolve`를 멈춰야 하는지를 구현 기준으로 설명합니다.

읽는 순서는 아래가 자연스럽습니다.

1. 스코프 베이스 클래스로 전역과 씬 수명주기를 나눕니다.
2. 씬 스코프 예제로 실제 등록 위치를 확인합니다.
3. 생성자 주입과 메서드 주입을 상황별로 나눕니다.
4. 비동기 초기화와 팩토리, 핫패스 경계를 확인합니다.

---

## 2. 이 가이드가 전제하는 계약

- `SceneDI`가 씬 초기화 타이밍을 통제한다.
- `VContainer`는 그 안에서 필요한 의존성을 해소한다.
- 말단 객체는 가능한 한 주입만 받고 직접 `Resolve`하지 않는다.
- 핫패스에서는 컨테이너 탐색보다 풀링과 전담 매니저를 우선한다.

이 계약이 무너지면 자동 DI를 도입해도 구조는 더 투명해지지 않고, 오히려 추적이 어려워집니다.

---

## 3. 스코프 베이스 구성

Reference Example: `BaseProjectLifetimeScope`, `BaseSceneLifetimeScope`

```csharp
using VContainer;
using VContainer.Unity;

public abstract class BaseProjectLifetimeScope : LifetimeScope
{
    protected override void Configure(IContainerBuilder builder)
    {
        ConfigureGlobalDependencies(builder);
    }

    protected abstract void ConfigureGlobalDependencies(IContainerBuilder builder);
}

public abstract class BaseSceneLifetimeScope : LifetimeScope
{
    protected override void Configure(IContainerBuilder builder)
    {
        ConfigureSceneDependencies(builder);
    }

    protected abstract void ConfigureSceneDependencies(IContainerBuilder builder);
}
```

전역 서비스는 `BaseProjectLifetimeScope`에서, 씬 전용 서비스는 `BaseSceneLifetimeScope`에서 등록합니다. 이 기준이 먼저 고정돼야 실제 등록 코드도 읽기 쉬워집니다.

---

## 4. 씬 스코프 등록 예제

Reference Example: `BattleSceneLifetimeScope`

```csharp
using UnityEngine;
using VContainer;
using VContainer.Unity;

public class BattleSceneLifetimeScope : BaseSceneLifetimeScope
{
    [SerializeField] private PlayerConfig _playerConfig;
    [SerializeField] private PlayerController _playerPrefab;

    protected override void ConfigureSceneDependencies(IContainerBuilder builder)
    {
        builder.RegisterInstance(_playerConfig);
        builder.Register<BattleScoreManager>(Lifetime.Scoped).As<IScoreTracker>();
        builder.Register<BattleEngineSystem>(Lifetime.Scoped);
        builder.RegisterComponentInNewPrefab(_playerPrefab, Lifetime.Scoped);
    }
}
```

이 예제에서 중요한 점은 등록 위치가 한곳에 모인다는 것입니다. 어떤 씬이 어떤 데이터와 서비스를 쓰는지, 어떤 프리팹이 컨테이너를 통해 생성되는지 스코프 클래스만 보면 바로 파악할 수 있어야 합니다.

---

## 5. 주입 패턴 선택

### 5.1 생성자 주입

순수 C# 서비스나 시스템 객체에는 생성자 주입이 가장 명확합니다.

```csharp
public class BattleEngineSystem
{
    private readonly PlayerConfig _config;
    private readonly IScoreTracker _scoreTracker;

    public BattleEngineSystem(PlayerConfig config, IScoreTracker scoreTracker)
    {
        _config = config;
        _scoreTracker = scoreTracker;
    }
}
```

생성자 시그니처만 보면 필요한 의존성이 드러나므로, 순수 서비스에는 이 방식이 기본값이 됩니다.

### 5.2 메서드 주입

`MonoBehaviour` 기반 액터에는 메서드 주입이 더 자연스러운 경우가 많습니다.

```csharp
using VContainer;
using UnityEngine;

public class PlayerController : MonoBehaviour
{
    private PlayerConfig _config;
    private IScoreTracker _scoreTracker;

    [Inject]
    public void Construct(PlayerConfig config, IScoreTracker scoreTracker)
    {
        _config = config;
        _scoreTracker = scoreTracker;
    }
}
```

이 방식은 엔진이 생성한 객체에 필요한 의존성을 꽂아 넣는 데 적합합니다. 다만 액터가 이후에 컨테이너를 들고 다른 것을 찾아가기 시작하면 구조가 흐려집니다.

---

## 6. 비동기 초기화 결합

컨테이너로 등록한 서비스 중 일부는 시작 시점에 비동기 초기화가 필요할 수 있습니다. 이런 경우 `IAsyncStartable` 같은 구조를 사용할 수 있습니다.

Reference Example: `AsyncLobbyInitializer`

```csharp
using Cysharp.Threading.Tasks;
using System.Threading;
using VContainer;
using VContainer.Unity;

public class AsyncLobbyInitializer : IAsyncStartable
{
    private readonly NetworkApiService _apiService;

    [Inject]
    public AsyncLobbyInitializer(NetworkApiService apiService)
    {
        _apiService = apiService;
    }

    public async UniTask StartAsync(CancellationToken cancellationToken)
    {
        await _apiService.FetchGlobalLobbyDataAsync(cancellationToken);
    }
}
```

이 구조는 유용하지만, 씬 전체 로딩 순서를 대신 설계해 주지는 않습니다. 어떤 페이즈에서 무엇을 기다릴지는 여전히 SceneDI나 상위 초기화 흐름과 맞춰야 합니다.

---

## 7. 팩토리와 동적 생성

동적 생성이 필요할 때는 모든 것을 `Resolve`로 뽑기보다, 상위에서 필요한 팩토리나 풀 매니저를 한 번 주입받는 편이 낫습니다.

```csharp
public class CombatSpawner
{
    private readonly AsyncPoolManager _poolManager;

    public CombatSpawner(AsyncPoolManager poolManager)
    {
        _poolManager = poolManager;
    }

    public UniTask<GameObject> SpawnProjectileAsync(AssetReference bulletRef, Vector3 position)
    {
        return _poolManager.SpawnAsync(bulletRef, position);
    }
}
```

이 구조의 핵심은 전투 중마다 컨테이너를 다시 탐색하지 않는다는 점입니다. 초기화 시점에 필요한 도구를 주입받고, 실제 핫패스에서는 그 도구만 사용합니다.

## 8. 자주 하는 실수

### 실수 1. `Resolve`를 어디서나 허용하는 것

말단 액터가 컨테이너를 직접 들고 의존성을 찾아가기 시작하면 자동 주입의 장점이 사라집니다.

### 실수 2. 씬 스코프에 전역 서비스를 넣는 것

씬 전환마다 재생성되면 안 되는 서비스는 전역 스코프에 남겨야 합니다.

### 실수 3. 프리팹 내부에 깊은 중첩 주입을 남발하는 것

프리팹 하이어라키 전역에 `[Inject]`를 퍼뜨리면 생성 비용과 추적 난이도가 같이 올라갑니다.

### 실수 4. 전투 중 컨테이너 기반 생성을 반복하는 것

핫패스에서는 풀링과 캐시를 우선해야 합니다.

## 9. 디버깅 포인트

- 어떤 서비스가 어느 스코프에 등록됐는지 먼저 확인합니다.
- 의존성 누락이 있으면 등록 위치와 수명주기부터 봅니다.
- 씬 전환 후 `Scoped` 객체가 의도대로 정리되는지 확인합니다.
- 말단 객체가 컨테이너를 직접 들고 있는지 확인합니다.
- 핫패스에서 `Resolve`가 반복 호출되는지 확인합니다.
