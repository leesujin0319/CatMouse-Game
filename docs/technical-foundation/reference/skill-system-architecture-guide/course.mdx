## [기술 기획안] 데이터 주도형 스킬 및 버프 시스템 (Skill System)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 도입 배경

`SkillSystem`은 스킬과 버프 로직을 개별 하드코드가 아니라 **데이터 기반 조합 구조**로 관리하기 위한 문서입니다. 목표는 프로그래머가 모든 스킬을 일일이 구현하는 데 있지 않습니다. 공통 실행 엔진은 코드로 두고, 스킬별 차이와 성장 데이터, 효과 조합은 테이블에서 관리할 수 있게 만드는 데 있습니다.

이 문서는 특히 `SceneDI`와 연결되는 로딩 시점, `EventBus`와 연결되는 반응 구조, 버프/상태이상 수명주기까지 포함해, 스킬 시스템이 어디까지 데이터로 닫히고 어디서 코드가 개입해야 하는지 정리합니다.

**이 문서가 바로 답하는 질문**

- 왜 스킬을 데이터 주도 구조로 분리해야 하는가
- 어떤 데이터는 공통 스킬 정의이고, 어떤 데이터는 레벨/효과 정의인가
- 로딩 씬에서 무엇을 미리 파싱하고 런타임에는 무엇을 조회해야 하는가
- 애니메이션 타이밍, 버프 수명주기, 상태이상 중첩은 어디서 통제해야 하는가

---

## 2. 문제 정의

스킬을 하드코딩으로 운영하면 새 스킬을 추가할 때마다 클라이언트 코드가 수정됩니다. `if (skillId == ...)`, `switch (effectType)`가 계속 늘어나고, 밸런스 조정과 기획 변경은 점점 느려집니다. 특히 액션 게임에서는 애니메이션 타이밍, 자원 소모, 버프 수명주기, 상태이상 조합까지 한데 묶이기 때문에, 코드에 로직이 많이 박힐수록 유지보수가 급격히 어려워집니다.

반대로 모든 것을 순수 데이터만으로 해결하려 하면 또 다른 문제가 생깁니다. 실제 연산 엔진, 애니메이션 재생, 타겟 판정, 버프 스케줄링, 이펙트 실행은 결국 코드가 맡아야 하기 때문입니다.

따라서 `SkillSystem`의 핵심 문제는 "코드냐 데이터냐"의 이분법이 아니라, **어디까지를 데이터로 일반화하고 어디서부터 실행 엔진이 책임질 것인가**를 분명히 정하는 데 있습니다.

---

## 3. 설계 목표

- 스킬 정의와 실행 엔진의 책임을 분리한다.
- 공통 스킬 구조는 데이터로, 실제 실행은 코드 엔진으로 유지한다.
- 로딩 씬에서 필요한 데이터를 한 번 파싱하고 런타임에는 빠르게 조회한다.
- 애니메이션 타이밍과 효과 적용 시점을 안정적으로 맞춘다.
- 버프와 상태이상의 중첩, 유지시간, 틱 주기를 수명주기 기준으로 관리한다.
- 기획 변경이 코드 수정 없이 가능한 영역과 아닌 영역을 구분한다.

---

## 4. 핵심 데이터 구조

스킬 데이터는 역할별로 분리하는 편이 관리하기 쉽습니다.

### 4.1 `Skill_Base`

스킬의 정체성과 공통 실행 뼈대를 가집니다.

- `SkillID`
- `AnimStateName`
- `ActionNormalizedTime`
- `TotalNormalizedTime`
- `NextComboSkillID`
- `ComboInputStart`, `ComboInputEnd`
- `IsShowUI`, `ReqSkillID`

### 4.2 `Skill_Level`

레벨별로 바뀌는 수치를 가집니다.

- `SkillID`
- `Level`
- `RequiredPlayerLevel`
- `CostMP`
- `Cooldown`

### 4.3 `Skill_Effect`

실제 효과 단위를 가집니다.

- `EffectType`
- `TargetStat`
- `ValueType`
- `Value`
- `Duration`
- `Interval`
- `Condition`

이 분리는 "스킬 정체성", "성장 수치", "실제 효과"를 अलग 운영할 수 있게 해 줍니다. 기획자가 수치를 조정할 때도 어느 표를 건드려야 하는지 분명해집니다.

---

## 5. 로딩과 런타임 경계

이 시스템은 로딩 단계와 전투 단계의 역할이 다릅니다.

- 로딩 단계: 테이블 파싱, 데이터 조립, 검증, 캐시 생성
- 런타임 단계: 조립된 데이터를 조회해 실행

이 경계는 `SceneDI`와 직접 연결됩니다. 스킬 데이터 파싱은 전역 부트스트래퍼보다 로딩 UI가 있는 SceneDI 단계가 더 적합한 경우가 많습니다. 데이터가 크고, 검증 실패나 재시도 UX가 필요할 수 있기 때문입니다.

---

## 6. 코어 캐시 구조

Reference Example: `SkillManager`

```csharp
using System.Collections.Generic;

public class SkillManager : MonoBehaviour
{
    private static readonly Dictionary<int, SkillData> _skillDict = new();

    public static void InitializeData()
    {
        // 1. Base 로드
        // 2. Level 로드
        // 3. Effect 로드
        // 4. SkillData 조립
    }

    public static bool TryGetSkill(int skillID, out SkillData skillData)
    {
        return _skillDict.TryGetValue(skillID, out skillData);
    }
}
```

핵심은 전투 중 CSV를 다시 읽지 않는다는 점입니다. 런타임에서는 이미 조립된 데이터를 조회만 해야 합니다.

---

## 7. 실행 엔진과 애니메이션 동기화

스킬 시스템은 데이터를 읽는 것만으로 끝나지 않습니다. 실제 실행은 `SkillCaster` 같은 전담 엔진이 맡는 편이 좋습니다.

애니메이션 이벤트를 클립마다 수동으로 심는 방식은 배속 변화, 클립 교체, 관리 비용 문제를 만들 수 있습니다. 그래서 `normalizedTime` 기반 타이밍 비교가 더 안정적인 경우가 많습니다.

예를 들어:

- `ActionNormalizedTime`을 넘기는 순간 실제 타격 판정을 넣는다.
- `TotalNormalizedTime`까지는 입력과 후딜을 제어한다.
- 콤보 입력 허용 시간도 동일한 기준으로 비교한다.

이 방식은 애니메이션 재생 속도가 변해도 같은 상대 시점에 효과를 넣기 좋습니다.

---

## 8. 버프와 상태이상 수명주기

버프 시스템은 단순 수치 증가가 아니라 **추가 상태 객체의 생명주기 관리**에 가깝습니다.

중요한 관리 항목은 아래입니다.

- 언제 추가되는가
- 언제 만료되는가
- 틱 간격이 있는가
- 같은 효과가 중첩되는가
- 중첩 시 갱신, 누적, 무시 중 어떤 규칙을 따르는가

이 규칙이 문서에 없으면, 독 데미지나 회복 효과 같은 기본 기능조차 프로젝트마다 다르게 구현되기 쉽습니다.

---

## 9. 코드가 맡아야 하는 영역

다음은 데이터만으로 닫기 어렵고 실행 엔진이 책임져야 하는 경우가 많습니다.

- 실제 타겟 판정
- 피해 공식 계산
- 애니메이션 재생과 타이밍 비교
- 버프 상태 객체 수명주기 갱신
- 특수 조건 처리의 실제 해석기

즉, 데이터는 "무엇을 할지"를 설명하고, 코드는 "그걸 어떻게 실행할지"를 맡습니다.

---

## 10. 실패 경로와 안티 패턴

### 10.1 스킬별 하드코드 분기 증가

`if (skillId == ...)` 분기가 계속 늘어나면 데이터 주도 구조의 장점이 사라집니다.

### 10.2 파싱 실패와 FK 불일치

`Skill_Base`, `Skill_Level`, `Skill_Effect` 사이 키가 어긋나면 런타임에서 조회 실패가 납니다. 이 구조는 빌드 전 검증기가 같이 가야 합니다.

### 10.3 런타임 중 반복 조회 남발

지속 피해나 버프 틱에서 매 프레임 중앙 딕셔너리를 계속 뒤지면 비용이 누적될 수 있습니다. 최초 적용 시 로컬 참조를 잡는 편이 낫습니다.

### 10.4 중첩 규칙 미정

독, 화상, 공격력 증가 같은 효과가 중첩될 때 기준이 없으면 밸런스와 실행 결과가 둘 다 흔들립니다.

---

## 11. 검증 포인트

- 로딩 단계와 런타임 단계의 역할이 분리되어 있는가
- 스킬 데이터가 조립 후 캐시로 조회되는가
- 애니메이션 타이밍과 효과 적용 시점이 같은 기준으로 맞아 있는가
- 버프/상태이상 중첩 규칙이 정의되어 있는가
- 기획 변경 가능 영역과 코드 수정 필요 영역이 분리되어 있는가

---

## 12. 리뷰 체크리스트

- 스킬 정의와 실행 엔진의 경계가 분명한가
- 로딩 시점이 SceneDI 기준과 충돌하지 않는가
- 데이터 구조가 역할별로 분리되어 있는가
- 런타임 조회와 상태이상 수명주기 규칙이 보이는가
- 하드코드 분기가 다시 침투하지 않는가

## 📌 1. 개요 및 기획자-프로그래머 협업 스탠스
본 문서는 기획 파트가 **프로그래머의 코드 개입 없이 순수 엑셀(Excel)/CSV 조작만으로 수백 개의 스킬, 연계 콤보, 상태이상을 무한 생성하고 배포** 하기 위한 데이터 설계 기준서입니다.

기획팀이 신규 전투 컨텐츠를 기획할 때 어떤 속성을 어떤 레이어 테이블(Base, Level, Effect)에 귀속시켜야 하는지에 대한 **엄격한 데이터 배치(Data Placement) 규칙** 을 제시하여, 파편화와 시스템 병목을 원천 차단합니다.

## 📌 3. 실무 규약: 테이블 확장(Column 추가) 및 데이터 배치 패러다임
초기 설계 이후 새로운 기획 요구사항이 생겼을 때, 개발팀 전원은 **"특정 데이터를 어떤 원칙에 따라 분산 배치할 것인가"** 에 대한 규약을 철저히 공유해야 시스템 오버헤드를 막을 수 있습니다.

### 💡 규칙 1: "이 데이터가 레벨업에 따라 수치가 성장하는가?" (Base vs Level 설계 위반)
*   **[오류 사례]**: 타격감을 위해 적용된 `CameraShakeIntensity`(카메라 쉐이크 강도) 컬럼을 기획자가 `Skill_Level` 데이블에 신설합니다.
*   **[안티 패턴 발생]**: 카레마 렌더링 수치를 조회하기 위해 선형 루프 연산 비용이 추가되며, 기획자는 하나의 속성을 레벨 1부터 99까지 99칸 중복 복사하는 비효율을 감수해야 합니다.
*   **[모범 해답]**: 물리 타격 및 카메라 렌더링에 관한 외형 변수들은 레벨업 수치와 전혀 무관하므로, 단 한 번만 조회되도록 `Skill_Base` 레이어로 귀속시켜야 파편화를 예방할 수 있습니다.

### 💡 규칙 2: 새로운 '특수 태그 기믹' 의 추가 지점 (Effect vs Level)
*   **[오류 사례]**: "보스 몬스터에게만 2배 데미지 적용" 이라는 조건을 추가하기 위해 `Skill_Level` 스키마 내에 `BossDamageMultiplier` 라는 기믹 전용 컬럼을 통째로 추가해 버립니다.
*   **[모범 해답]**: 특정 대상 타격 비율이나 조건부 기믹은 무조건 `Skill_Effect` 데이터베이스 단락에 포함시킵니다. 해당 테이블 내에 `TargetTag (기본값: All, 입력입력: Boss)` 등의 조건 판별 컬럼을 추가해 샌드박스로 운영해야 Level/Base 메인 스키마가 비대하게 팽창하지 않습니다.

### 💡 규칙 3: 데이터 테이블 열(Column) 스키마 변경 시 파이프라인 합의
1.  **기획팀**: 엑셀 마스터 시트에 신규 컬럼(예: `RequiredItemID` - 특정 아이템 한정 소모 스킬) 증설 후 팀 공표.
2.  **클라이언트팀**: `SkillLevelData.cs` 클래스 변수 매핑을 즉각 1줄 수행(`public int RequiredItemID;`)하여 CSV 파서 결합 동기화.
3.  **런타임 적용**: 스킬 캐스팅 호출 진입점에 거름망(판단) 로직 조건(`if (!Inventory.HasItem(levelData.RequiredItemID)) return;`) 두 줄을 배치하여 예외 처리를 확정.

## [개발 가이드] 데이터 주도형 스킬 및 버프 시스템 (Skill System)

> 최종 수정일: 2026-04-27
> 문서 상태: `Reviewable`

---

## 1. 개요 및 읽는 순서

이 가이드는 로딩 씬에서 스킬 데이터를 준비한 뒤, 실제 전투 액터와 실행 엔진에서 어떻게 붙이는지 설명합니다.

읽는 순서는 아래가 자연스럽습니다.

1. `SceneDI`와 연결된 초기화 흐름을 봅니다.
2. 플레이어 액터가 스킬 실행 엔진을 어떻게 주입받는지 봅니다.
3. `SkillCaster`가 애니메이션 타이밍과 효과 적용을 어떻게 처리하는지 봅니다.
4. 콤보, 도트, UI 연결 같은 실무 패턴을 봅니다.

---

## 2. 이 가이드가 전제하는 계약

- 스킬 데이터는 로딩 단계에서 이미 조립되어 있다.
- 액터는 스킬 테이블을 직접 파싱하지 않는다.
- 실행 엔진이 실제 타이밍과 효과 적용을 맡는다.
- 버프/상태이상은 전담 수명주기 관리자에서 유지한다.

이 계약이 무너지면 플레이어 액터 안에 파싱, 연출, 버프 수명주기, UI 반응이 다시 섞이기 시작합니다.

---

## 3. SceneDI와 연결된 초기화

Reference Example: `PlayerCombat`

```csharp
public class PlayerCombat : BaseEntity
{
    private SkillCaster _caster;

    public void Init(SkillCaster caster)
    {
        _caster = caster;
        CompleteInitialization();
    }

    public void UseSkill(int skillID, int currentLevel)
    {
        if (!SkillManager.TryGetSkill(skillID, out var skillData))
        {
            return;
        }

        var levelData = skillData.GetLevel(currentLevel);
        if (!ConsumeResource(levelData.CostMP))
        {
            return;
        }

        StartCoroutine(_caster.RoutineSkillExecute(skillData.Base, levelData));
    }
}
```

이 구조에서 중요한 점은 액터가 테이블 파서를 직접 모르고, 이미 조립된 스킬 데이터와 실행 엔진만 사용한다는 것입니다.

---

## 4. 실행 엔진 예시

Reference Example: `SkillCaster`

```csharp
using System.Collections;
using UnityEngine;

public class SkillCaster : MonoBehaviour
{
    [SerializeField] private Animator _animator;
    [SerializeField] private MonoBehaviour _targetSource;

    public IEnumerator RoutineSkillExecute(SkillBaseData baseData, SkillLevelData levelData)
    {
        _animator.Play(baseData.AnimStateName, 0, 0f);

        while (_animator.GetCurrentAnimatorStateInfo(0).normalizedTime < baseData.ActionNormalizedTime)
        {
            yield return null;
        }

        foreach (var effect in levelData.Effects)
        {
            ApplyEffect(effect);
        }

        while (_animator.GetCurrentAnimatorStateInfo(0).normalizedTime < baseData.TotalNormalizedTime)
        {
            yield return null;
        }
    }

    private void ApplyEffect(SkillEffectData effect)
    {
        // 피해, 버프, 디버프를 effect 타입에 따라 실행
    }
}
```

이 엔진은 실제 실행 타이밍을 맡습니다. 데이터는 스킬이 무엇인지 설명하고, 엔진은 그 설명을 실제 동작으로 바꿉니다.

## 5. 콤보 입력 처리

콤보는 일반적으로 애니메이션 진행도 기준으로 입력 허용 구간을 두는 편이 안정적입니다.

```csharp
private void Update()
{
    if (!_isCasting)
    {
        return;
    }

    var currentTime = GetCurrentNormalizedTime();

    if (currentTime >= _currentSkillBase.ComboInputStart &&
        currentTime <= _currentSkillBase.ComboInputEnd)
    {
        if (Input.GetButtonDown("Fire1"))
        {
            _isComboReserved = true;
        }
    }

    if (currentTime >= _currentSkillBase.ComboEnd && _isComboReserved)
    {
        UseSkill(_currentSkillBase.NextComboSkillID, 1);
    }
}
```

이 방식은 콤보 입력 가능 시간을 데이터로 제어하기 좋습니다.

---

## 6. 버프와 도트 처리

버프와 도트는 적용 시점보다 **유지와 만료**가 더 중요합니다. 일반적으로 `BuffManager` 같은 전담 컴포넌트에서 관리하는 편이 낫습니다.

```csharp
private void Update()
{
    for (var i = _activeBuffs.Count - 1; i >= 0; i--)
    {
        var buff = _activeBuffs[i];

        if (buff.EffectData.Interval > 0 && Time.time >= buff.NextTickTime)
        {
            ApplyDamage(buff.EffectData.Value);
            buff.NextTickTime += buff.EffectData.Interval;
        }

        if (Time.time >= buff.ExpireTime)
        {
            _activeBuffs.RemoveAt(i);
        }
    }
}
```

중요한 점은 `buff.EffectData` 같은 로컬 참조를 유지해, 틱마다 중앙 테이블을 다시 찾지 않게 하는 것입니다.

## 7. 스킬 트리 UI 연결

스킬 UI도 하드코드보다 데이터 기반 렌더링이 낫습니다.

```csharp
public class SkillTreeUIManager : MonoBehaviour
{
    public void RenderTree()
    {
        foreach (var skill in SkillManager.GetAllSkills())
        {
            if (!skill.IsShowUI)
            {
                continue;
            }

            CreateSkillNode(skill);

            if (skill.ReqSkillID != 0)
            {
                DrawLine(skill.ReqSkillID, skill.SkillID);
            }
        }
    }
}
```

이 구조를 쓰면 UI 레이아웃과 선행 스킬 관계도 데이터 기준으로 표현할 수 있습니다.

## 8. 자주 하는 실수

### 실수 1. 플레이어 액터가 파싱과 실행을 모두 떠안는 것

액터는 입력과 시작 지시까지만 맡고, 실행 엔진과 데이터 관리자에 역할을 넘기는 편이 좋습니다.

### 실수 2. 스킬 효과마다 하드코드 분기를 추가하는 것

새 효과가 생길 때마다 조건문이 늘면 시스템이 금방 굳습니다.

### 실수 3. 버프 틱마다 중앙 딕셔너리를 다시 조회하는 것

최초 적용 시 필요한 참조를 로컬에 잡는 편이 낫습니다.

### 실수 4. 콤보 입력 시간과 애니메이션 타이밍을 코드에 박아 두는 것

기획 조정이 어려워집니다.

---

## 9. 디버깅 포인트

- 로딩 단계에서 스킬 데이터가 실제로 조립되는지 확인합니다.
- 특정 스킬이 조회 실패하면 키와 레벨 데이터부터 봅니다.
- 애니메이션 진행도와 효과 발동 시점이 어긋나는지 확인합니다.
- 버프 중첩과 만료가 의도대로 동작하는지 확인합니다.
- UI가 스킬 데이터와 다른 기준으로 렌더링되고 있지 않은지 확인합니다.
