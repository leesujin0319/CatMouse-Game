## [기술 기획안] Scene 로드 및 종속성 주입 (SceneDI)

> 최종 수정일: 2026-04-27
> 문서 상태: `Draft`

---

## 1. 개요 (Overview) 및 프레임워크 관점

> SceneDI는 **씬 조립 권한**을 **중앙 디렉터**에 모아 초기화 순서와 책임 경계를 고정하는 규약입니다.

SceneDI는 씬이 열린 뒤 필요한 시스템을 누가 어떤 순서로 붙이는지 명시적으로 통제하는 규약입니다. 목표는 `Init()` 메서드 몇 개를 정리하는 데 있지 않습니다. 씬 단위 게임 제작에서 반복되는 **생성, 로드, 주입, 활성화, 종료** 흐름을 같은 골격으로 유지해, 새 씬과 새 액터, 새 서브 매니저를 붙여도 같은 방식으로 조립되게 만드는 데 있습니다.

이 규약이 다루는 범위는 씬 디렉터, 액터, 하위 매니저, 로딩 씬, 전역 부트스트랩 사이의 조립 경계입니다. 특히 로딩 씬에서 어떤 준비를 끝내고, 어느 시점부터 액터를 켜며, 실패하면 어디서 멈추는지를 씬 단위 기준으로 닫는 데 초점을 둡니다.

---

## 2. 문제 정의 (Problem Statement)

> 문제는 의존성이 없는 것이 아니라, **누가 언제 연결하는지**가 보이지 않는다는 점입니다. `Awake`, `Start`, 전역 참조에 의존하면 **단독 씬 실행**, **Additive 조합**, **로딩 중 취소** 같은 실패가 반복적으로 재현됩니다.

Unity 프로젝트에서 씬 진입 직후의 장애는 대부분 같은 지점에서 시작됩니다. 씬 내부 오브젝트가 각자 `Awake`, `Start`, `OnEnable`에서 필요한 시스템을 찾기 시작하면, 실행 순서는 엔진 콜백에 흩어지고 **의존성 획득 지점**은 액터 내부로 분산됩니다. 이 상태에서는 어떤 객체가 먼저 준비되어야 하는지 코드에서 보이지 않으며, 단독 씬 실행이나 Additive 조합 시 상위 컨텍스트 누락이 바로 `NullReferenceException`으로 이어집니다.

문제의 본질은 "의존성이 존재하는가"가 아니라 "누가 언제 의존성을 연결할 권한을 갖는가"입니다. 액터가 스스로 전역 시스템을 찾아가기 시작하면 게임이 커질수록 초기화 순서와 소유권이 보이지 않게 되고, 결국 씬마다 임시 방어 로직과 예외 처리가 분산됩니다.

SceneDI는 이 문제를 씬 진입 시점의 조립 권한을 중앙 디렉터로 끌어올려 해결합니다. 액터는 자신의 도메인 로직만 소유하고, 씬 디렉터는 로드, 준비, 주입, 활성화 순서를 통제합니다. 이 구조를 프레임워크 규약으로 고정해야만 새 씬이 추가되더라도 같은 실패를 반복하지 않습니다.

---

## 3. 설계 목표 (Design Goals)

> SceneDI의 목표는 특정 씬 하나를 안전하게 여는 데서 끝나지 않고, 다른 씬에도 같은 조립 흐름을 반복 적용할 수 있게 만드는 데 있습니다.

- 씬 진입 직후의 초기화 순서를 중앙에서 통제한다.
- 액터가 `Manager.Instance`, `FindObjectOfType`, 전역 검색으로 의존성을 직접 획득하지 않게 한다.
- 생성과 활성화를 분리하여, 주입 완료 전 액터 로직 진입을 차단한다.
- 씬 종료 시 비동기 작업 취소와 자원 정리 지점을 문서 차원에서 닫는다.
- 단독 씬 실행, Additive 씬, 에디터 테스트, 하위 매니저 위임 같은 실무 시나리오를 프레임워크 규약으로 흡수한다.
- 새 씬, 새 액터, 새 하위 매니저에도 같은 조립 규약을 반복 적용할 수 있게 한다.

따라서 이 문서는 씬별 예외 처리 모음이 아니라, 다음 씬을 추가할 때 그대로 복제할 수 있는 조립 규칙을 남겨야 합니다.

---

## 4. 비채택 대안 (Rejected Alternatives)

가장 흔한 대안은 각 액터가 `Awake`나 `Start`에서 직접 `GameManager.Instance`, `SkillManager.Instance`, `NetworkManager.Instance`를 참조하는 방식입니다. 구현 초반에는 빠르지만, 씬 수가 늘어날수록 **초기화 순서**가 엔진 콜백과 전역 상태에 묶입니다. 이 구조에서는 단독 씬 실행, 테스트 환경, 로딩 중 취소 같은 실패 조건을 문서 차원에서 통제하기 어렵습니다.

또 다른 대안은 거대한 `GameManager`가 씬 오브젝트를 모두 직접 들고 초기화하는 구조입니다. 이 방식은 초기에 단순하지만, 로딩 UI, 데이터 파싱, 풀링, 군집 제어, UI 갱신이 한 클래스에 섞이면서 God object로 비대화됩니다. 프레임워크가 커질수록 "전역이 다 안다"는 가정은 유지되지 않습니다.

SceneDI는 씬 진입 시점의 조립 책임만 상위 디렉터가 갖고, 하위 구현과 최적화는 각 액터 및 서브 매니저로 위임하는 방식을 채택합니다. 이후 VContainer 같은 컨테이너를 도입하더라도 "조립 권한은 상위에 있고 액터는 직접 찾지 않는다"는 계약은 유지됩니다.

---

## 5. 범위와 비범위 (In Scope / Out of Scope)

> SceneDI는 **씬 조립 범위**를 다루며, 전역 부트스트랩과 컨테이너 정책은 필요한 지점에서만 연결합니다.

### In Scope

- 씬 진입 시점의 로드, 준비, 주입, 활성화 순서 통제
- 씬 단위 데이터 준비와 의존성 연결
- 액터 초기화 완료 전 Update 계열 진입 차단
- 씬 종료 시 비동기 작업 취소
- 단독 씬 실행을 위한 에디터 목업 경로
- 하위 서브 매니저로의 책임 위임 규칙

### Out of Scope

- 앱 전체 부트스트랩과 전역 시스템 생성
- Addressables 참조 카운트 정책 자체
- DI 컨테이너 구현과 자동 등록 메커니즘
- 수백~수천 개 객체를 대상으로 한 런타임 최적화 상세 구현

`GlobalBootstrapper`가 앱 전체의 최소 코어를 준비한다면, SceneDI는 그 위에서 "이 씬을 어떤 단계로 조립할 것인가"를 정의합니다. 예를 들어 로그인 세션, 공용 설정, 플랫폼 서비스는 전역 부트스트랩 쪽에 남고, 로딩 UI를 보여주며 읽어야 하는 월드 번들, 씬 특화 데이터, 서브 매니저 조립은 SceneDI가 맡는 식입니다. Addressables, SkillSystem, VContainer는 각각 별도 문서에서 세부 정책을 다루고, SceneDI는 그들을 씬 안에서 어떤 순서로 연결할지에 집중합니다.

---

## 6. 프레임워크 핵심 계약 (Framework Contracts)

> 액터는 **직접 찾지 않고**, 디렉터는 **조립 순서만 통제하며**, 종료 시 **비동기 경로를 씬 단위로 닫아야** 합니다.

SceneDI 프레임워크는 아래 **핵심 계약**이 동시에 성립할 때만 유지됩니다.

### 6.1 액터는 의존성 획득 권한을 갖지 않는다

액터는 자신의 도메인 로직을 소유하지만, 필요한 시스템을 어디서 어떻게 찾을지는 결정하지 않습니다. 필요한 인터페이스, 데이터, 서비스 묶음은 상위 조립부가 넘겨줍니다.

### 6.2 씬 디렉터는 조립 권한을 갖는다

씬 디렉터는 로드, 준비, 주입, 활성화, 취소의 순서를 결정합니다. 다만 디렉터가 도메인 구현 자체를 모두 흡수해서는 안 됩니다. 디렉터의 본질은 순서 통제와 조립이며, 세부 동작은 하위 서비스와 매니저가 맡습니다.

### 6.3 생성과 활성화는 분리된다

씬에 액터가 존재한다고 해서 바로 로직이 실행되면 안 됩니다. 액터는 이미 하이어라키에 배치되어 있을 수 있지만, 주입이 끝나기 전까지는 논리적으로 "꺼진 상태"여야 합니다.

### 6.4 씬 종료는 비동기 경로를 반드시 종료시킨다

SceneDI는 로딩과 파싱을 자주 동반합니다. 씬이 파괴된 뒤에도 비동기 작업이 계속 살아 있으면, 완료 콜백이 파괴된 오브젝트를 건드리며 예외를 만듭니다. 따라서 씬 디렉터는 씬 단위 취소 토큰의 소유자여야 합니다.

### 6.5 단독 씬 실행은 프레임워크 차원에서 지원한다

실무에서는 전투 씬, 보스 씬, UI 씬만 따로 돌려보는 경우가 반복됩니다. 이 경로를 문서에서 빼면 각 개발자가 임시 더미 생성 코드를 씬마다 흩뿌리게 됩니다. SceneDI 프레임워크는 에디터 전용 목업 경로를 공식 확장 포인트로 포함해야 합니다.

## 7. 코어 프레임워크 구현 코드 (Core Systems)

### 7.1 생명주기 통제 코어: `BaseEntity`

Reference Example: `BaseEntity`

```csharp
using UnityEngine;

/// <summary>
/// 씬 조립이 끝나기 전까지 액터의 실행을 유예하는 최상위 코어
/// </summary>
public abstract class BaseEntity : MonoBehaviour
{
    protected bool IsInitialized { get; private set; }

    protected virtual void Awake()
    {
        // 주입 완료 전 Update 계열 진입 차단
        enabled = false;
    }

    protected virtual void CompleteInitialization()
    {
        IsInitialized = true;
        enabled = true;
    }
}
```

`BaseEntity`의 책임은 액터의 생성 시점과 실행 가능 시점을 분리하는 것입니다. 이 클래스는 의존성을 만들지 않으며, 상위 조립부가 주입을 끝냈는지 여부만 관리합니다. 따라서 액터는 "어디서 가져올지"를 몰라도 되고, "언제 켜질지"도 상위 조립부가 결정합니다.

### 7.2 씬 조립 통제관: `BaseSceneDirectorAsync`

Reference Example: `BaseSceneDirectorAsync`

```csharp
using Cysharp.Threading.Tasks;
using System.Threading;
using UnityEngine;

/// <summary>
/// 씬 진입 시점의 로드, 준비, 주입, 활성화 순서를 통제하는 최상위 디렉터
/// </summary>
public abstract class BaseSceneDirectorAsync : MonoBehaviour
{
    private CancellationTokenSource _sceneCts;

    protected virtual void Awake()
    {
        _sceneCts = new CancellationTokenSource();
    }

    private void Start()
    {
        InitializeProcessAsync(_sceneCts.Token).Forget();
    }

    private void OnDestroy()
    {
        _sceneCts?.Cancel();
        _sceneCts?.Dispose();
    }

    private async UniTask InitializeProcessAsync(CancellationToken token)
    {
#if UNITY_EDITOR
        if (NeedsEditorMockSetup())
        {
            SetupEditorMockData();
        }
#endif
        await InitializeSceneAsync(token);
    }

    protected abstract UniTask InitializeSceneAsync(CancellationToken token);

#if UNITY_EDITOR
    protected abstract bool NeedsEditorMockSetup();
    protected abstract void SetupEditorMockData();
#endif
}
```

`BaseSceneDirectorAsync`의 책임은 씬 파이프라인의 시작점, 취소 지점, 에디터 목업 분기, 하위 조립 순서를 통제하는 데 있습니다. 이 클래스는 전투 로직, UI 세부 제어, 대규모 풀링 같은 하위 구현을 직접 품지 않습니다. 이 선을 지켜야 프레임워크가 씬마다 다시 복제 가능해집니다.

## 8. 생명주기와 호출 순서 (Lifecycle and Initialization Order)

> SceneDI는 **생성된 오브젝트**와 **실제로 켜진 오브젝트**를 구분합니다. 이 분리가 있어야 로딩 씬, Additive 씬, 취소 경로를 같은 규칙으로 다룰 수 있습니다.

SceneDI는 Unity 엔진 콜백을 제거하려는 구조가 아닙니다. 엔진 콜백 위에 **"논리적 초기화 완료 시점"**이라는 별도 계약을 올리는 구조입니다.

1. `GlobalBootstrapper`가 앱 전체 최소 코어를 준비하고, 대상 씬 또는 로딩 씬을 연다.
2. SceneDI 디렉터와 액터가 생성된다. 액터는 `BaseEntity`의 `Awake`에서 논리적 비활성 상태로 들어간다.
3. 디렉터는 `Start`에서 초기화 파이프라인을 시작하고, 필요하면 에디터 목업을 먼저 채운다.
4. 디렉터는 로딩 UI에 현재 단계와 진행률을 노출하면서 네트워크, 데이터, 에셋 준비를 수행한다.
5. 준비 결과를 서비스 묶음이나 하위 매니저 단위로 조립한 뒤 액터에 주입한다.
6. 액터와 하위 매니저는 `CompleteInitialization()` 또는 동등한 완료 지점 이후에만 활성화된다.
7. 씬 파괴나 전환이 시작되면 디렉터는 취소 토큰을 전파하고, 완료되지 않은 결과는 적용하지 않는다.

중요한 점은 `enabled = false`가 모든 Unity 메시지를 막아주지 않는다는 사실입니다. `OnTriggerEnter`, 커스텀 콜백, 일부 엔진 경로는 여전히 호출될 수 있으므로 액터는 필요한 지점에 `if (!IsInitialized) return;` 방어를 둬야 합니다.

## 9. 프레임워크 확장 규칙 (How the Framework Grows)

> **새 씬**, **새 액터**, **새 서브 매니저**를 추가할 때도 같은 조립 규약과 책임 경계를 유지해야 합니다.

SceneDI 규약은 하나의 씬 예제에서 끝나지 않고, 새 씬이나 새 시스템을 붙일 때도 같은 방식으로 **확장**됩니다.

### 9.1 새 씬을 추가할 때

새 씬을 만들 때는 그 씬 전용 디렉터를 `BaseSceneDirectorAsync`에서 파생시킵니다. 이 디렉터는 최소한 아래 항목을 먼저 정리해야 합니다.

- 이 씬 진입 전에 반드시 준비되어야 하는 데이터는 무엇인가
- 전역 부트스트랩에서 이미 준비된 것과 이 씬에서 준비할 것을 어디서 나누는가
- 어떤 액터와 서브 매니저에 어떤 서비스 묶음을 주입할 것인가
- 단독 씬 실행 시 어떤 목업을 제공할 것인가

즉, 새 씬은 "새 MonoBehaviour 하나 추가"가 아니라 "기존 조립 계약 위에 씬별 조립 시나리오 하나를 추가"하는 작업입니다.

### 9.2 새 액터를 추가할 때

새 액터는 `BaseEntity`를 파생하고, 외부에서 주입받는 `Init(...)` 진입점을 명시해야 합니다. 액터 내부에서 전역 시스템을 직접 찾기 시작하면 프레임워크 계약 위반입니다.

### 9.3 새 서브 매니저를 추가할 때

군집 제어, 풀링, UI 허브, 전투 서비스 조립처럼 씬 내 중간 조정자가 필요하다면 디렉터가 직접 모든 세부 구현을 떠안지 말고 별도 서브 매니저로 분리합니다. 디렉터는 그 매니저를 조립하고 초기화 순서를 통제하며, 매니저는 자기 도메인 안의 디테일을 책임집니다.

### 9.4 공통 프레임워크와 게임별 구현의 경계

`BaseEntity`, `BaseSceneDirectorAsync`, 목업 공급 규약, 씬 취소 규약은 공통 프레임워크 영역입니다. 반면 전투 씬에서 어떤 데이터를 준비하고 어떤 액터를 켤지, 로비 씬에서 어떤 UI를 조립할지는 게임별 구현 영역입니다. 이 경계를 지켜야 공통 프레임워크가 다음 프로젝트나 다음 씬에서도 재사용됩니다.

---

## 10. 비동기 표준과 로딩 정책 (Async Policy)

> SceneDI는 로딩 구현을 다 품는 문서가 아니라, **로딩 순서**와 **조립 타이밍**을 통제하는 문서입니다. 다운로드, 파싱, 진행률 갱신은 파이프라인에 들어오되 **세부 구현 책임**은 각 시스템에 남겨야 합니다.

이 문서에서 `UniTask`를 우선하는 이유는 코루틴을 감정적으로 배제하기 위해서가 아니라, 씬 초기화 파이프라인에서 필요한 계약을 더 명시적으로 표현할 수 있기 때문입니다. 씬 조립 단계에서는 **결과 반환, 예외 전파, 취소 토큰 전달, 병렬 대기, 진행률 전달**이 자주 필요합니다. 이런 경로는 `async/await` 기반이 문서화와 리뷰에 더 유리합니다.

반대로 단순한 프레임 지연이나 짧은 연출 제어는 코루틴이 더 자연스러운 경우도 있습니다. 따라서 이 문서의 결론은 "코루틴 전면 금지"가 아니라 "씬 초기화 파이프라인에서는 `UniTask`를 우선 검토한다"입니다.

로딩 정책도 같은 기준으로 봅니다. SceneDI 디렉터는 로딩을 직접 다 구현하는 것이 아니라, 로딩을 어떤 단계로 나눌지와 각 단계 완료 후 무엇을 활성화할지를 통제합니다. `LoadingUI`, Addressables 다운로드, 마스터 데이터 파싱, 서비스 조립은 SceneDI 파이프라인에 들어올 수 있지만, 각 세부 시스템의 내부 구현까지 디렉터가 소유하면 안 됩니다. 특히 네트워크 로그인 실패, 번들 다운로드 실패, 파싱 실패처럼 로딩 화면에서 드러나야 하는 문제는 액터 활성화 전에 감지되어야 하며, 실패한 단계의 재시도나 이탈 UI 역시 그 페이즈 경계에서 닫혀야 합니다.

---

## 11. 성능과 책임 분리 원칙 (Performance and Delegation)

> SceneDI의 성능 포인트는 최적화 자체보다 **"누가 최적화를 책임지는가"**를 나누는 데 있습니다. 디렉터가 모든 하위 최적화를 흡수하면 프레임워크는 곧 다시 **God object**가 됩니다.

SceneDI 문서는 성능 최적화 문서가 아니지만, 프레임워크가 어디까지 **책임지고** 어디서 **위임**해야 하는지는 분명해야 합니다.

`BaseEntity`가 초기 `enabled = false`를 두는 이유는 주입 완료 전 액터가 로직을 실행하지 못하게 하는 것이 첫 번째 목적입니다. 생성 직후 Update 계열이 한꺼번에 돌기 시작하는 상황을 늦추는 부수 효과는 있을 수 있지만, 이것만으로 모든 프레임 스파이크를 해결한다고 서술하면 과장입니다.

더 중요한 기준은 디렉터가 God object가 되지 않는 것입니다. 대규모 탄막, 군집 이동, 풀링 프리웜, UI 세부 상태 머신 같은 하위 최적화는 전담 서브 매니저가 담당해야 합니다. Addressables 핸들 소유권, 월드 오브젝트 해제 시점, 풀 초기화 비용도 해당 로더나 매니저에서 관리하고, SceneDI 디렉터는 조립과 순서 통제에 집중해야 합니다. 최적화는 넘겨준 서비스와 중간 관리자에서 수행합니다.

---

## 12. 시스템 예외 방어 및 엣지 케이스 (Edge Cases)

> **단독 씬 실행**, **씬 파괴 중 비동기 지속**, **Additive 조합**, **초기화 이전 엔진 메시지**는 실무에서 반복되는 대표 실패 경로입니다.

### 12.1 단독 씬 실행

타이틀이나 전역 부트스트랩을 거치지 않고 전투 씬만 직접 실행하면 상위 컨텍스트가 비어 있을 수 있습니다. 이 경우 SceneDI 디렉터는 에디터 전용 목업 경로를 통해 더미 데이터와 필수 서비스의 최소 세트를 준비해야 합니다. 이 규약이 없으면 개발자마다 `if (Application.isEditor)` 방어 코드가 흩어집니다.

### 12.2 씬 파괴 중 비동기 작업 지속

씬이 이미 파괴되고 있는데 로딩이나 파싱이 계속 진행되면, 완료 시점에 파괴된 오브젝트를 참조하면서 예외가 납니다. 따라서 씬 디렉터는 씬 단위 `CancellationTokenSource`를 소유하고, 하위 로드 경로는 그 토큰을 전달받아야 합니다.

### 12.3 Additive 씬 조합

메인 UI 씬과 전투 씬을 Additive로 띄우면 `BaseSceneDirectorAsync`가 둘 이상 존재할 수 있습니다. 이때 각 디렉터가 어떤 오브젝트와 어떤 서비스 묶음을 책임지는지 문서에서 먼저 나눠야 합니다. 같은 액터를 두 디렉터가 동시에 조립하려고 하면 프레임워크 계약이 깨집니다.

### 12.4 엔진 메시지 무단 진입

`enabled = false`는 Update 계열에는 유효하지만 모든 엔진 메시지를 동일하게 차단하지는 않습니다. 물리 이벤트, 커스텀 진입점, 외부 콜백이 초기화 이전에 들어올 수 있으므로 액터는 필요한 지점에 `IsInitialized` 방어를 명시해야 합니다.

### 12.5 로딩 실패 후 부분 활성화

네트워크 세션 획득, 에셋 다운로드, 마스터 데이터 파싱 중 한 단계라도 실패했다면 디렉터는 다음 액터를 켜지 않아야 합니다. 일부 액터만 활성화된 상태에서 실패 화면이 올라오면 책임 경계가 무너지고, 재시도 시 어떤 상태를 되돌려야 하는지도 불명확해집니다. 실패 시점은 로딩 UI의 실패 상태, 재시도, 씬 이탈 중 하나로 명시적으로 닫아야 합니다.

---

## 13. 기획 우려사항 (Planning Concerns)

> SceneDI는 **런타임 구조**이면서 동시에 **기획 데이터의 로딩 위치와 대체 범위**를 정하는 문서입니다.

SceneDI는 런타임 구조처럼 보이지만 실제로는 **기획 데이터 파이프라인**과 강하게 연결됩니다. 어떤 데이터를 전역 부트스트랩에서 처리하고, 어떤 데이터를 씬 로딩 화면 안에서 처리하며, 어떤 데이터를 단독 씬 실행 시 목업으로 대체할 수 있는지가 정리되지 않으면 씬 구조와 데이터 구조가 함께 흔들립니다. 예를 들어 보스 씬 진입 직전에 패턴 테이블을 읽을지, 로비 진입 전에 미리 읽을지에 따라 로딩 시간, 재시도 UX, 목업 전략이 모두 달라집니다.

기획 관점에서 최소한 아래 질문이 문서에 닫혀 있어야 합니다.

- 이 씬 진입 시점에 반드시 준비되어야 하는 데이터는 무엇인가
- 없으면 바로 런타임 장애가 나는 데이터와, 임시 목업으로 대체 가능한 데이터는 무엇인가
- 로딩 UI를 동반할 만큼 무거운 데이터인가, 아니면 전역에서 미리 준비되어야 하는 데이터인가
- 기획자가 값만 바꿔도 되는 영역과, 파서나 런타임 확장이 필요한 영역은 어디인가

SceneDI 문서에 이 기준이 빠지면 결국 "일단 씬 들어와서 읽자"는 식의 임시 판단이 늘어나고, 로딩 책임이 `GlobalBootstrapper`, SceneDI 디렉터, 하위 매니저 사이에서 계속 흔들리게 됩니다.

---

## 14. 디버깅 및 검증 포인트 (Verification)

> SceneDI의 첫 검증 대상은 성능이 아니라 **초기화 계약 준수 여부**입니다. 계약이 깨진 상태의 최적화는 재사용되지 않습니다.

- 단독 씬 실행 시 목업 경로가 실제로 필요한 최소 서비스를 채우는지 확인한다.
- 씬 전환 직후 취소되지 않은 비동기 작업이 남아 있지 않은지 확인한다.
- 액터가 `Init` 이전에 로직을 실행하지 않는지 확인한다.
- 로딩 단계 실패 시 다음 액터 활성화가 중단되고 재시도 또는 이탈 경로가 남는지 확인한다.
- Additive 씬 조합 시 디렉터 간 책임 경계가 문서와 일치하는지 확인한다.
- 새 액터나 새 서브 매니저를 붙일 때 전역 참조가 다시 침투하지 않는지 확인한다.

SceneDI의 첫 번째 검증 대상은 성능 수치가 아니라 **초기화 계약 준수 여부**입니다. 이 계약이 깨진 상태에서 최적화만 추가하면 프레임워크는 재사용되지 않습니다.

---

## 15. 리뷰 체크리스트 (Review Checklist)

- SceneDI의 책임이 전역 부트스트랩 책임과 겹치지 않는가
- 액터의 생성 시점과 활성화 시점이 분리되어 있는가
- 액터가 직접 전역 시스템을 찾지 않는가
- 디렉터가 순서를 통제하지만 하위 구현까지 흡수하지 않는가
- 단독 씬 실행, Additive 씬, 씬 파괴 중 취소 같은 실패 조건이 드러나 있는가
- 새 씬과 새 서브 시스템을 어디서 확장해야 하는지 문서만으로 판단 가능한가

## [개발 가이드] Scene 로드 및 종속성 주입 (SceneDI)

> 최종 수정일: 2026-04-27
> 문서 상태: `Draft`

---

## 1. 개요 (Overview)

> SceneDI는 실제 게임 씬에서 **로딩 UI**, **서비스 묶음**, **목업**, **Additive**까지 이어지는 조립 흐름 안에서 사용됩니다.

이 가이드는 SceneDI를 실제 게임 씬에 붙일 때 필요한 기본 골격과 확장 지점을 다룹니다. 대상은 단순 `Init()` 예제가 아니라 **로딩 씬 연동**, **서비스 묶음 조립**, **서브 매니저 위임**, **에디터 단독 실행**, **Additive 씬 조합**까지 포함한 실전 파이프라인입니다.

현재 예제는 수동 주입을 기준으로 설명합니다. 이후 프로젝트 규모가 커져 `VContainer` 같은 자동 DI 계층을 도입하더라도, 씬 진입 시점의 조립 권한을 상위 디렉터가 가진다는 계약은 그대로 유지해야 합니다. Gameplay 씬, Lobby 씬, Boss 씬처럼 성격이 다른 씬에도 같은 패턴을 반복 적용할 수 있어야 하기 때문입니다.

---

## 2. 이 가이드가 전제하는 계약

> 액터는 **직접 찾지 않고**, 디렉터는 **순서를 결정하며**, **단독 씬 실행**도 공식 경로로 취급합니다. 이 계약이 있어야 아래 예제들이 모두 같은 구조 위에서 읽힙니다.

이 문서는 아래 계약을 전제로 합니다.

- 액터는 초기화가 끝나기 전까지 자기 로직을 실행하지 않는다.
- 액터는 직접 `Manager.Instance`를 찾아 의존성을 획득하지 않는다.
- 씬 디렉터는 로드, 준비, 주입, 활성화의 순서를 결정한다.
- 씬 종료 시 비동기 작업 취소는 디렉터가 관리한다.
- 단독 씬 실행 경로도 프레임워크 확장 포인트로 취급한다.

이 전제가 무너지면 아래 예제는 동작하더라도 SceneDI 사용 예제로 재사용하기 어렵습니다.

---

## 3. 이 가이드에서 사용하는 코어 코드

기획안에도 코어 코드가 나오지만, 개발 가이드에서는 구현자가 바로 대조할 수 있도록 기준 코드를 다시 보여주는 편이 좋습니다. 아래 두 클래스는 뒤에 나오는 모든 예제의 전제입니다.

### 3.1 생명주기 통제 코어: `BaseEntity`

Reference Example: `BaseEntity`

```csharp
using UnityEngine;

/// <summary>
/// 씬 조립이 끝나기 전까지 액터의 실행을 유예하는 최상위 코어
/// </summary>
public abstract class BaseEntity : MonoBehaviour
{
    protected bool IsInitialized { get; private set; }

    protected virtual void Awake()
    {
        // 주입 완료 전 Update 계열 진입 차단
        enabled = false;
    }

    protected virtual void CompleteInitialization()
    {
        IsInitialized = true;
        enabled = true;
    }
}
```

`BaseEntity`의 목적은 "씬에 배치되어 있음"과 "실제로 동작 가능함"을 분리하는 것입니다. 액터는 이 클래스를 통해 주입 완료 전에는 논리적으로 꺼진 상태를 유지하고, 필요한 엔진 메시지 진입점에서는 `IsInitialized` 방어를 추가합니다.

### 3.2 씬 조립 통제 코어: `BaseSceneDirectorAsync`

Reference Example: `BaseSceneDirectorAsync`

```csharp
using Cysharp.Threading.Tasks;
using System.Threading;
using UnityEngine;

/// <summary>
/// 씬 진입 시점의 로드, 준비, 주입, 활성화 순서를 통제하는 최상위 디렉터
/// </summary>
public abstract class BaseSceneDirectorAsync : MonoBehaviour
{
    private CancellationTokenSource _sceneCts;

    protected virtual void Awake()
    {
        _sceneCts = new CancellationTokenSource();
    }

    private void Start()
    {
        InitializeProcessAsync(_sceneCts.Token).Forget();
    }

    private void OnDestroy()
    {
        _sceneCts?.Cancel();
        _sceneCts?.Dispose();
    }

    private async UniTask InitializeProcessAsync(CancellationToken token)
    {
#if UNITY_EDITOR
        if (NeedsEditorMockSetup())
        {
            SetupEditorMockData();
        }
#endif
        await InitializeSceneAsync(token);
    }

    protected abstract UniTask InitializeSceneAsync(CancellationToken token);

#if UNITY_EDITOR
    protected abstract bool NeedsEditorMockSetup();
    protected abstract void SetupEditorMockData();
#endif
}
```

`BaseSceneDirectorAsync`는 씬 진입 시점의 초기화 파이프라인, 취소 토큰, 에디터 목업 분기를 한곳에 모읍니다. 이후 예제에서 나오는 로딩 UI 연동, 서비스 조합, Additive 씬 처리도 모두 이 코어 위에서 파생됩니다.

## 4. 의존성 주입 규격 (BaseEntity 구현 모델)

> 액터 타입이 달라도 원칙은 동일합니다. **직접 찾지 말고**, **주입받고**, 그 뒤에만 활성화해야 하며, 이 규약이 흐려지면 씬 조립 코드가 빠르게 파편화됩니다.

씬 디렉터로부터 의존성을 하향식으로 주입받는 액터는 책임 성격에 따라 몇 가지 전형적인 패턴으로 정리할 수 있습니다. 중요한 점은 "몇 개를 받는가"가 아니라 **"액터가 직접 찾지 않는가"**입니다.

### 4.1 복합 주입형 액터

Reference Example: `PlayerController`

```csharp
public class PlayerController : BaseEntity
{
    private PlayerData _playerData;
    private ISoundSystem _soundSystem;
    private ISkillCaster _skillCaster;

    public void Init(PlayerData playerData, ISoundSystem soundSystem, ISkillCaster skillCaster)
    {
        _playerData = playerData;
        _soundSystem = soundSystem;
        _skillCaster = skillCaster;

        CompleteInitialization();
    }

    private void Update()
    {
        if (!IsInitialized) return;

        if (Input.GetKeyDown(KeyCode.Space))
        {
            _soundSystem.Play("attack");
            _skillCaster.CastDefault();
        }
    }
}
```

이 패턴은 플레이어, 보스, 복합 UI 허브처럼 여러 서비스와 기획 데이터를 동시에 요구하는 액터에 적합합니다. 핵심은 액터가 필요한 포인터를 모두 주입받은 뒤에만 활성화된다는 점입니다.

### 4.2 단일 인터페이스형 액터

Reference Example: `EnemyUnit`

```csharp
public class EnemyUnit : BaseEntity
{
    private IScoreTracker _scoreTracker;

    public void Init(IScoreTracker scoreTracker)
    {
        _scoreTracker = scoreTracker;
        CompleteInitialization();
    }

    public void ReportDeath()
    {
        if (!IsInitialized) return;
        _scoreTracker.Add(100);
    }
}
```

이 패턴은 점수 집계, UI 통지, 사운드 재생처럼 가벼운 종속성 한두 개만 필요한 액터에 적합합니다. 구현은 단순하지만, 의존성 획득 지점은 여전히 액터 밖에 있어야 합니다.

### 4.3 무주입 기믹형 액터

Reference Example: `MovingPlatform`

```csharp
public class MovingPlatform : BaseEntity
{
    public void Init()
    {
        CompleteInitialization();
    }
}
```

외부 서비스가 필요 없는 씬 기믹도 동일한 초기화 규약을 따르는 편이 좋습니다. 모든 액터가 같은 생명주기 계약을 따르면 디렉터의 조립 코드는 일관성을 유지할 수 있습니다.

## 5. 씬 디렉터 기본 조립 예제

> 최소 예제는 **"찾기"를 "주입"으로 바꾸는 가장 작은 단위**를 보여줍니다. 복잡한 실무 예제로 가기 전에 **기본 계약**을 먼저 눈에 익히는 구간입니다.

최소 예제는 SceneDI가 어떻게 **"찾기"를 "주입"으로 바꾸는지** 보여주는 수준이면 충분합니다. 하지만 프레임워크 관점에서는 최소 예제만으로는 부족하므로, 이 뒤에서 로딩 UI, 서비스 묶음, 서브 매니저 위임까지 확장합니다.

### 5.1 최소 동작 예제

Reference Example: `PlayerCombat`

```csharp

        _skillCaster = skillCaster;
        CompleteInitialization();
    }
```

## 6. 로딩 씬과 연동된 실무형 조립 예제

> 실제 프로젝트에서는 SceneDI가 **로딩 파이프라인**, **서비스 조립**, **액터 활성화**까지 한 흐름으로 이어집니다.

실제 게임에서는 SceneDI가 단순히 액터 몇 개를 `Init()` 하는 수준에서 끝나지 않습니다. **서버 세션 동기화**, **월드 번들 다운로드**, **마스터 데이터 파싱**, **로딩 UI 페이즈 관리**, **서비스 묶음 조립**이 한 파이프라인으로 이어집니다.

### 6.1 로딩 UI 컴포넌트

Reference Example: `LoadingUI`

```csharp
using TMPro;
using UnityEngine;
using UnityEngine.UI;

public class LoadingUI : MonoBehaviour
{
    [SerializeField] private Slider _progressBar;
    [SerializeField] private TextMeshProUGUI _statusText;

    public void UpdateProgress(float value)
    {
        _progressBar.value = value;
    }

    public void SetText(string message)
    {
        _statusText.text = message;
    }
}
```

`LoadingUI`는 로딩 파이프라인을 표현하는 전용 뷰입니다. SceneDI 문서에서 이 클래스를 분리해 두는 이유는, 로딩 UI가 조립 파이프라인의 일부이지 디렉터 내부 구현 세부가 아니라는 점을 드러내기 위해서입니다.

### 6.2 서비스 묶음 조립체

Reference Example: `GameplaySceneServices`

```csharp
public sealed class GameplaySceneServices
{
    public GameplaySceneServices(
        PlayerData playerData,
        ISkillCaster skillCaster,
        IScoreTracker scoreTracker,
        IEnemySpawnPolicy spawnPolicy)
    {
        PlayerData = playerData;
        SkillCaster = skillCaster;
        ScoreTracker = scoreTracker;
        SpawnPolicy = spawnPolicy;
    }

    public PlayerData PlayerData { get; }
    public ISkillCaster SkillCaster { get; }
    public IScoreTracker ScoreTracker { get; }
    public IEnemySpawnPolicy SpawnPolicy { get; }
}
```

실무에서는 개별 인터페이스를 액터마다 흩어 뿌리기보다, 씬에서 반복적으로 쓰는 서비스 조합을 묶어두는 편이 유지보수에 유리합니다. 이 묶음은 컨테이너가 아니며, 씬 조립 결과를 표현하는 DTO에 가깝습니다.

서비스 조합이 커지기 시작하면 `BuildGameplaySceneServicesAsync()` 같은 메서드를 디렉터 안에만 두기보다, 아래처럼 별도 조립 책임으로 빼는 편이 읽기 쉽고 테스트도 쉬워집니다.

### 6.3 서비스 조립 책임 분리 예시

Reference Example: `GameplaySceneServicesFactory`

```csharp
using Cysharp.Threading.Tasks;
using System.Threading;

public sealed class GameplaySceneServicesFactory
{
    private readonly IPlayerDataLoader _playerDataLoader;
    private readonly ISkillCasterFactory _skillCasterFactory;
    private readonly IEnemySpawnPolicyLoader _spawnPolicyLoader;

    public GameplaySceneServicesFactory(
        IPlayerDataLoader playerDataLoader,
        ISkillCasterFactory skillCasterFactory,
        IEnemySpawnPolicyLoader spawnPolicyLoader)
    {
        _playerDataLoader = playerDataLoader;
        _skillCasterFactory = skillCasterFactory;
        _spawnPolicyLoader = spawnPolicyLoader;
    }

    public async UniTask<GameplaySceneServices> CreateAsync(
        INetworkSession networkSession,
        CancellationToken token)
    {
        var playerData = await _playerDataLoader.LoadAsync(networkSession, token);
        var skillCaster = await _skillCasterFactory.CreateAsync(networkSession, token);
        var spawnPolicy = await _spawnPolicyLoader.LoadAsync(token);

        return new GameplaySceneServices(
            playerData,
            skillCaster,
            new ScoreTracker(),
            spawnPolicy);
    }
}
```

이 구조의 핵심은 디렉터가 서비스 조합의 세부 절차까지 품지 않는다는 점입니다. 씬마다 반복되는 데이터 로더, 팩토리, 정책 로더는 별도 책임으로 분리하고, 디렉터는 어느 단계에서 무엇을 기다릴지와 언제 액터를 켤지만 결정합니다.

### 6.4 실무형 씬 디렉터

Reference Example: `GameplaySceneDirectorAsync`

```csharp
using Cysharp.Threading.Tasks;
using UnityEngine;
using UnityEngine.AddressableAssets;

public class GameplaySceneDirectorAsync : BaseSceneDirectorAsync
{
    [SerializeField] private AssetReferenceGameObject _worldRef;
    [SerializeField] private LoadingUI _loadingUI;
    [SerializeField] private PlayerController _playerController;
    [SerializeField] private EnemySwarmManager _enemySwarmManager;

    protected override async UniTask InitializeSceneAsync(CancellationToken token)
    {
        _loadingUI.SetText("서버 세션과 동기화 중입니다...");
        _loadingUI.UpdateProgress(0.0f);

        var networkSession = await ResolveNetworkSessionAsync(token);
        _loadingUI.UpdateProgress(0.2f);

        _loadingUI.SetText("월드 번들 및 환경 데이터를 불러오는 중입니다...");
        var assetProgress = Progress.Create<float>(p =>
        {
            _loadingUI.UpdateProgress(Mathf.Lerp(0.2f, 0.8f, p));
        });

        await Addressables.LoadAssetAsync<GameObject>(_worldRef)
            .ToUniTask(progress: assetProgress, cancellationToken: token);

        _loadingUI.SetText("게임플레이 서비스를 조립 중입니다...");
        var services = await BuildGameplaySceneServicesAsync(networkSession, token);

        _loadingUI.SetText("씬 액터를 활성화하는 중입니다...");
        _playerController.Init(services.PlayerData, ResolveSoundSystem(), services.SkillCaster);
        _enemySwarmManager.Init(services.ScoreTracker, services.SpawnPolicy);
        await _enemySwarmManager.PrewarmAsync(token);

        _loadingUI.UpdateProgress(1.0f);
        _loadingUI.SetText("로딩 완료");
    }
}
```

이 예제의 핵심은 디렉터가 모든 세부 로직을 직접 구현하지 않는다는 점입니다. 디렉터는 페이즈를 나누고, 준비 결과를 조립하고, 액터와 하위 매니저의 활성화 시점을 결정합니다. 네트워크 세션의 내부 구현, 스킬 엔진 내부 로직, 군집 최적화, 서비스 조합 세부는 각 전담 시스템이나 팩토리에 남겨둡니다.

> 디렉터는 **로딩 단계**를 나누고 결과를 조립합니다. **서비스 묶음**은 액터와 매니저에 반복적으로 전달되는 조합을 정리하며, 세부 구현은 각 시스템에 남기고 SceneDI는 **순서와 연결만 책임집니다**.

## 7. 하위 분산 매니저(Sub-Manager)로의 위임

> 디렉터는 모든 세부 구현을 품지 않고, **중간 관리자에게 책임을 넘겨야** 합니다. 이 선을 넘으면 SceneDI는 프레임워크가 아니라 **God object**가 됩니다.

SceneDI 프레임워크가 실전에서 무너지는 가장 흔한 지점은 **디렉터가 모든 것을 직접 품기 시작할 때**입니다. 투사체 풀링, 군집 업데이트, 적 웨이브 스폰, HUD 갱신까지 디렉터 하나가 떠안으면 구조는 곧 God object로 돌아갑니다.

### 7.1 중간 관리자 예시

Reference Example: `EnemySwarmManager`

```csharp
using Cysharp.Threading.Tasks;
using UnityEngine;

public class EnemySwarmManager : MonoBehaviour
{
    private IScoreTracker _scoreTracker;
    private IEnemySpawnPolicy _spawnPolicy;

    public void Init(IScoreTracker scoreTracker, IEnemySpawnPolicy spawnPolicy)
    {
        _scoreTracker = scoreTracker;
        _spawnPolicy = spawnPolicy;
    }

    public async UniTask PrewarmAsync(CancellationToken token)
    {
        await UniTask.Yield(PlayerLoopTiming.Update, token);
        // 실제 프로젝트에서는 풀 생성, 웨이브 테이블 캐시, 초기 적 배치 등을 수행
    }
}
```

이 클래스의 책임은 군집 개체와 웨이브 스폰 정책을 중간 계층에서 통합하는 데 있습니다. 디렉터는 이 매니저를 초기화하고 준비 완료를 기다릴 뿐이며, 적 개체 하나하나를 직접 조종하지 않습니다.

SceneDI를 프레임워크로 쌓아 올린다는 것은 결국 "어떤 세부 책임을 어디까지 디렉터에 두고, 어디서부터 중간 관리자에게 위임하는가"를 반복 가능한 규칙으로 만드는 일입니다.

## 8. 전역 부트스트랩과의 경계

> **전역 부트스트랩**은 앱 전체 코어를, **SceneDI**는 씬 전용 조립을 담당합니다. 이 경계가 흐려지면 어떤 데이터를 어디서 준비하는지 계속 흔들립니다.

SceneDI는 전역 부트스트랩을 대체하지 않습니다. `GlobalBootstrapper`가 앱 전체의 최소 코어를 준비한다면, SceneDI는 그 위에서 **씬 전용 조립**을 수행합니다. 이 경계가 흐려지면 어느 데이터가 언제 준비되어야 하는지 팀 내 판단이 계속 흔들립니다.

실무 기준으로는 아래처럼 나누는 편이 안전합니다.

- 전역 부트스트랩
  - 앱 전체에서 항상 살아 있어야 하는 최소 코어
  - 플랫폼 서비스, 공용 설정, 전역 이벤트 허브 같은 공통 기반
- SceneDI 디렉터
  - 이 씬에서만 필요한 서비스 묶음
  - 씬 진입 시 준비해야 하는 데이터
  - 로딩 UI와 씬 액터 활성화
- 하위 서브 매니저
  - 군집 제어, 풀링, UI 중간 조정, 도메인 최적화

특히 "스킬 마스터 테이블은 전역에서 미리 읽을지, 씬 로딩 화면에서 읽을지" 같은 문제는 문서마다 같은 기준으로 닫혀 있어야 합니다. 이 가이드에서는 무겁고 씬 특화된 조립은 SceneDI 파이프라인으로, 앱 전역에서 반드시 필요한 최소 코어는 부트스트랩으로 분리하는 쪽을 기본선으로 둡니다.

실무에서 중요한 것은 단순 분류가 아니라 핸드오프 시점입니다. 부트스트랩이 끝났다고 해서 씬 액터를 바로 켜는 것이 아니라, SceneDI가 해당 씬의 데이터와 서비스 준비를 끝낸 뒤 활성화해야 합니다. 이 순서가 섞이면 로딩 화면은 지나갔는데 실제 게임은 아직 덜 조립된 상태가 됩니다.

## 9. 레거시 브리지 적용 방식

> 레거시 싱글톤이 남아 있어도 **액터가 아니라 디렉터에서만 접근**하게 해야 합니다. 완전한 전환이 어렵더라도 **조립 권한은 상위에 모아야** 구조가 유지됩니다.

실제 프로젝트에서는 아직 모든 시스템이 주입형으로 정리되어 있지 않을 수 있습니다. 이 경우 중요한 것은 레거시 싱글톤을 영구히 허용하는 것이 아니라, **의존성 획득 지점**을 액터에서 디렉터로 끌어올리는 것입니다.

예를 들어 `NetworkManager.Instance`를 완전히 없애지 못한 상태라면, 액터가 직접 접근하게 두는 대신 디렉터가 세션을 획득하고, 하위 액터에는 세션 또는 서비스 인터페이스만 전달하는 편이 좋습니다. 이 구조는 완전한 DI는 아니지만, 최소한 조립 권한이 상위로 모여 리뷰와 추적이 가능해집니다.

즉, 레거시 브리지는 허용되더라도 아래 순서를 지켜야 합니다.

1. 전역 접근은 액터가 아니라 디렉터나 조립부에서만 수행한다.
2. 하위 액터에는 인터페이스 또는 조립 결과만 전달한다.
3. 동일 기능을 새로 만들 때는 브리지 경로가 아니라 주입 경로를 우선한다.

## 10. 에디터 단독 씬 실행과 MockData 공급

> **단독 씬 실행**은 예외가 아니라 공식 지원 경로로 문서화해야 합니다. 이 규약이 없으면 더미 데이터 생성 코드가 씬마다 흩어집니다.

실무에서는 전투 씬만 직접 실행하는 빈도가 높습니다. 이 경로를 **프레임워크 규약**으로 포함하지 않으면 각 씬이 제각각 더미 데이터를 만들기 시작하고, 데이터 구조가 바뀔 때마다 여러 씬이 동시에 깨집니다.

### 10.1 디렉터 측 조건 분기

Reference Example: `GameplaySceneDirectorAsync` editor hook

```csharp
#if UNITY_EDITOR
protected override bool NeedsEditorMockSetup()
{
    return GameManager.Instance == null || GameManager.Instance.CurrentData == null;
}

protected override void SetupEditorMockData()
{
    MockDataProvider.InjectMockGameManager();
}
#endif
```

디렉터는 더미 데이터를 직접 조립하는 곳이 아니라, 목업 공급이 필요한지 판단하고 공급소를 호출하는 곳으로 두는 편이 좋습니다.

### 10.2 중앙 공급소 예시

Reference Example: `MockDataProvider`

```csharp
#if UNITY_EDITOR
using UnityEngine;

public static class MockDataProvider
{
    public static void InjectMockGameManager()
    {
        if (GameManager.Instance != null && GameManager.Instance.CurrentData != null)
        {
            return;
        }

        var dummyObject = new GameObject("[Mock_GameManager]");
        var dummyManager = dummyObject.AddComponent<GameManager>();

        var mockPlayerData = new PlayerData
        {
            HP = 99999,
            MoveSpeed = 50.0f
        };

        dummyManager.SetData(mockPlayerData);
    }
}
#endif
```

Mock 공급을 중앙화하면 데이터 구조가 바뀌더라도 수정 지점이 한 곳으로 모입니다. 이후 ScriptableObject 기반 테스트 설정이나 에디터 전용 설정 에셋으로 확장하는 것도 이 경로 위에서 자연스럽게 진행할 수 있습니다.

특히 목업은 "없으면 아무 값이나 채운다"가 아니라, 어떤 데이터까지 대체 가능한지 범위를 문서화해야 합니다. 예를 들어 플레이어 스탯은 목업으로 대체해도 스킬 마스터 테이블이나 전투 룰셋은 실제 데이터가 필요할 수 있습니다.

## 11. Additive 씬과 다중 디렉터 조합

> **Additive 씬**에서는 **"누가 무엇을 조립하는가"**를 먼저 나눠야 합니다. 같은 액터를 두 디렉터가 건드리기 시작하면 디버깅 비용이 급격히 커집니다.

UI 씬 위에 전투 씬을 Additive로 올리면 디렉터가 둘 이상 생깁니다. 이때 SceneDI 프레임워크가 유지되려면 **"각 디렉터가 무엇을 조립하는가"**를 먼저 분리해야 합니다.

예를 들어 아래처럼 나누는 편이 안전합니다.

- `MainUISceneDirector`
  - 공용 HUD, 메뉴, 공통 오버레이
- `BattleSceneDirector`
  - 월드 에셋, 전투 액터, 적 스폰 정책, 전투 서비스

중요한 것은 어떤 액터도 두 디렉터의 조립 대상이 되면 안 된다는 점입니다. Additive 씬에서 경계가 흐리면 한쪽은 초기화했고 다른 한쪽은 아직 준비 중인 상태가 발생해 디버깅이 매우 어려워집니다.

## 12. 종료와 예외 처리 규약

> 씬 종료 시 **비동기 경로**와 **엔진 메시지 진입점**을 함께 방어해야 합니다. 파괴된 오브젝트에 늦게 도착한 결과 적용이 초기화 경로의 대표 장애입니다.

씬이 종료될 때 가장 먼저 확인해야 할 것은 **비동기 작업이 계속 살아 있는지 여부**입니다. 로딩, 파싱, 다운로드가 끝난 뒤 결과를 적용하려는 시점에 대상 오브젝트가 이미 파괴되어 있으면, 초기화 경로 자체가 장애 지점이 됩니다.

### 12.1 엔진 메시지 방어 예시

Production Example: `DamageReceiver`

```csharp
public class DamageReceiver : BaseEntity
{
    private IHealthService _healthService;

    public void Init(IHealthService healthService)
    {
        _healthService = healthService;
        CompleteInitialization();
    }

    private void OnTriggerEnter(Collider other)
    {
        if (!IsInitialized) return;
        _healthService.ApplyHit(10);
    }
}
```

이 예제의 핵심은 `enabled = false`만 믿지 않는다는 점입니다. 물리 진입점, 외부 콜백, 애니메이션 이벤트처럼 엔진이 예기치 않게 먼저 진입할 수 있는 경로는 액터 성격에 따라 논리적 방어를 추가해야 합니다.

### 12.2 부분 활성화 방지

초기화 단계 중 하나라도 실패했다면 다음 액터 활성화는 멈춰야 합니다. 예를 들어 월드 번들은 로드됐지만 플레이어 데이터 파싱이 실패했다면, 월드 오브젝트만 남긴 채 플레이어와 적을 켜지 않는 식의 부분 활성화 상태를 허용하면 안 됩니다. 실패 시점은 로딩 UI의 오류 상태, 재시도, 이전 화면 복귀 중 하나로 바로 닫는 편이 안전합니다.

## 13. 자주 하는 실수

> **직접 찾기**, **디렉터 과대화**, **단독 씬 실행 생략**, **데이터 경계 미정리**가 대표적인 실패 패턴입니다. 이 네 가지가 반복되면 SceneDI는 문서에만 남고 실제 구조에서는 사라집니다.

### 실수 1. 액터가 자기 의존성을 직접 찾는 것

이 방식은 씬 초기화 순서 통제를 무너뜨립니다. SceneDI 문서가 존재해도 실제 구조는 다시 전역 참조로 회귀합니다.

### 실수 2. 디렉터가 모든 하위 구현을 떠안는 것

디렉터가 풀링, 군집 업데이트, UI 세부 제어, 파싱 세부 구현까지 모두 품기 시작하면 프레임워크가 아니라 거대한 스크립트 하나만 남습니다.

### 실수 3. 단독 씬 실행 경로를 문서에서 생략하는 것

실무에서는 특정 씬만 따로 실행하는 경우가 자주 생깁니다. 이 실패 경로를 무시하면 각 개발자가 임시 방어 코드를 제각각 만들게 됩니다.

### 실수 4. 로딩 데이터 경계를 문서에서 닫지 않는 것

어떤 데이터는 전역 부트스트랩에서, 어떤 데이터는 SceneDI에서, 어떤 데이터는 목업으로 대체 가능한지 구분이 없으면 로딩 책임이 계속 흔들립니다.

## 14. 쓰지 말아야 하는 경우

> SceneDI는 **씬 조립 프레임워크**이지, 앱 전체 라이프사이클이나 컨테이너 자동화 자체를 대체하지는 않습니다. 적합한 범위를 넘어 쓰면 오히려 경계가 흐려집니다.

SceneDI는 씬 진입 시점의 조립과 활성화 순서를 통제하는 데 적합합니다. 반대로 아래 경우에는 다른 구조를 먼저 검토하는 편이 맞습니다.

- 앱 전체 부트스트랩과 전역 시스템 생성을 다루는 경우
- 런타임 중 대규모 자동 주입이 이미 프로젝트 표준인 경우
- 씬 단위 조립보다 컨테이너 등록/해석 정책이 중심인 경우

즉, SceneDI는 씬 프레임워크의 상위 조립 규약에는 강하지만, 앱 전체 라이프사이클이나 컨테이너 자동화 문제를 혼자 해결하는 구조는 아닙니다.

## 15. 기획 우려사항

> **기획 데이터의 로딩 위치**와 **대체 가능 범위**를 정의하지 않으면 SceneDI 경계도 흔들립니다. 데이터 준비 책임이 전역 부트스트랩과 씬 디렉터 사이에서 계속 흔들리기 때문입니다.

씬 진입 시점에 어떤 데이터를 반드시 준비해야 하는지 정의하지 않으면, 구현 단계에서 "일단 씬 들어와서 읽자"는 식의 임시 판단이 늘어나기 쉽습니다. 이 판단은 곧 로딩 시간, 실패 처리, 목업 전략, QA 범위를 함께 흔듭니다.

기획 관점에서 문서에 닫혀 있어야 하는 질문은 아래와 같습니다.

- 이 씬에 진입하기 전에 반드시 준비되어야 하는 데이터가 무엇인가
- 누락 시 목업으로 대체 가능한 데이터와 절대 대체할 수 없는 데이터가 무엇인가
- 로딩 UI가 필요할 정도로 무거운 데이터인가
- 전역 부트스트랩에서 처리할 데이터와 SceneDI에서 처리할 데이터의 경계가 명확한가
- 기획자가 값만 바꿔도 되는 항목과, 신규 런타임 처리가 필요한 항목이 분리되어 있는가

기획 데이터와 씬 조립 규약은 같은 문맥에서 함께 정리되어야 합니다.

---

## 16. 디버깅 포인트

> 디버깅은 **"누가 먼저 실행됐는가"**와 **"누가 조립 대상인가"**를 보는 데서 시작합니다. SceneDI 장애는 대부분 순서와 경계에서 시작됩니다.

- `Init` 호출 전 액터가 동작하는지 확인한다.
- 단독 씬 실행 시 목업 경로가 실제로 필요한 최소 서비스를 채우는지 확인한다.
- 씬 전환 시 취소되지 않은 비동기 작업이 남아 있지 않은지 확인한다.
- 로딩 UI에 현재 페이즈와 마지막 성공 단계가 남는지 확인한다.
- 디렉터가 하위 시스템 구현까지 과도하게 흡수하고 있지 않은지 확인한다.
- Additive 씬에서 각 디렉터의 조립 대상이 겹치지 않는지 확인한다.
